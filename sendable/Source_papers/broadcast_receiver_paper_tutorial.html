Detecting Android Malware by Mining Statically Registered Broadcast Receivers

Mohsen, Bisgin, Scott & Strait — IEEE CIC 2017 (DOI: 10.1109/CIC.2017.00021)
Self-contained tutorial: architecture, methodology, and how to read the results — no need to open the PDF first.

Overview — Big Picture

Android malware must often run in the background without the user opening the app — for example to intercept SMS, restart after reboot, or react to connectivity changes. The paper’s core insight is that statically registered broadcast receivers (declared in AndroidManifest.xml under <receiver>) reveal which system events wake the app, while permissions reveal what sensitive resources the app may access. The authors first run a small empirical study (200 benign + 200 malware APKs) comparing manifest patterns and onReceive() Java code, then build a machine-learning detector on a large corpus (5,723 malware + samples from 48,262 benign apps) using binary feature vectors and a C-SVM with RBF kernel — not a deep neural network. They train three feature configurations: receiver actions only, permissions only, and both concatenated, and show that combining receivers with permissions raises average test accuracy from ~96% to ~97% on their main (duplicate-configuration) split.

Important — This Paper Is Not “Model Architecture” in the Deep-Learning Sense

There are no convolutional layers, embeddings, or backpropagation. The “architecture” is a static feature pipeline + SVM. If you are implementing this for a thesis or ONNX deployment, the same vectors can feed a logistic regression or tiny MLP instead of SVM; the features are what the paper contributes.

Android Preliminaries — What the Paper Assumes You Know

Permissions (<uses-permission>)

Each APK declares capabilities in the manifest (e.g. SEND_SMS, READ_PHONE_STATE). Normal permissions are granted silently; dangerous ones are shown to the user at install (older Android) or at runtime (Android 6+). Figure 1 in the paper shows a runtime permission dialog — the ML part of the paper still uses static manifest declarations, not runtime grants.

Broadcast receivers — static vs dynamic

A broadcast receiver runs code when a system or app event fires (boot completed, SMS received, etc.). Static registration: <receiver> in the manifest — the OS can deliver broadcasts even if the app is not running. Dynamic registration: registerReceiver() in Java — only active while the registering context (e.g. an Activity) lives. This paper mines only static (manifest) receivers, and specifically the android:name strings on <action> tags inside <intent-filter> that match known system actions.

Key novelty: Prior malware work (Drebin, PUMA, etc.) focused heavily on permissions. Mohsen et al. treat which system events the app listens for as a first-class feature and show it improves detection when fused with permissions — receivers were mentioned in rule-based work (e.g. Kirin) but not studied at this scale.

Example manifest snippet (Listing 1 in paper)

AndroidManifest.xml
  ├─ <uses-permission android:name="CALL_PHONE" />
  ├─ <uses-permission android:name="READ_SMS" />
  └─ <receiver android:name=".ExternalBroadcastReceiver" exported="true">
        <intent-filter>
          <action android:name="BOOT_COMPLETED" />
          <action android:name="ACTION_AIRPLANE_MODE_CHANGED" />
        </intent-filter>
     </receiver>

Component A — Permission Binary Feature Vector

What it analyzes

Every android:name in <uses-permission> elements from the decoded manifest.

Why this input was chosen

Permissions are the dominant static signal in Android malware literature (e.g. PUMA). The paper includes them as a strong baseline and to test whether receivers add information beyond permissions (Section IV, scenario ii and iii).

Step-by-step process

  1. Reverse-engineer each APK (Apktool) and obtain AndroidManifest.xml.
  2. Collect the set of permission strings declared by that app.
  3. From the training corpus, build vocabulary \(\mathcal{P} = \{\text{perm}_1, \ldots, \text{perm}_P\}\) — all distinct permissions observed (order fixed for all experiments).
  4. For each app \(i\), set bit \(p_{i,j} = 1\) if \(\text{perm}_j\) is declared, else \(0\).
  5. Use the same \(\mathcal{P}\) at test time (missing permissions in vocab → dimension stays 0).

Mathematical formulation

\[ p_{i,j} = \begin{cases} 1 & \text{if } \text{perm}_j \in \text{Manifest}(i) \\ 0 & \text{otherwise} \end{cases} \qquad \mathbf{p}_i \in \{0,1\}^{P} \]
  • \(i\) — index of one APK in the dataset
  • \(P\) — number of unique permissions in the global vocabulary (implicitly defined by all manifests in the study; not a single fixed number in the paper)
  • \(p_{i,j}\) — presence bit for permission \(j\) in app \(i\)
  • \(\mathbf{p}_i\) — permission feature row vector for app \(i\)

Architecture flowchart

Raw APK │ └─► Apktool ──► AndroidManifest.xml │ └─► <uses-permission> names │ ▼ Permission vector p (1 × P) [binary]

Output and connection to next stage

Output \(\mathbf{p}_i \in \{0,1\}^{P}\). Used alone in the “permissions only” experiment, or concatenated with \(\mathbf{r}_i\) for the combined model.

Component B — Broadcast Receiver “Action Items” Vector

What it analyzes

For each <receiver> in the manifest, every <action android:name="…"> under <intent-filter> that matches a system action from a compiled list of Android OS broadcast actions (paper: one master file of system actions per OS release family). Custom app-specific actions are not the focus — only system-level intent actions.

Why this input was chosen

Static receivers can wake the app without user interaction — ideal for persistence and interception. The empirical study showed malware registers more receivers for sensitive events (boot, SMS, phone state). The paper calls these features “action items” in Section IV (same as intent action strings).

Step-by-step process

  1. Parse the same manifest as Component A.
  2. Enumerate all <receiver> blocks.
  3. Within each receiver, read all <action android:name> under <intent-filter>.
  4. Keep actions that appear in the predefined system action list.
  5. Build vocabulary \(\mathcal{A} = \{\text{action}_1, \ldots, \text{action}_R\}\) from the training corpus.
  6. Set \(r_{i,k}=1\) if action \(k\) appears in any static receiver for app \(i\), else \(0\).

Mathematical formulation

\[ r_{i,k} = \begin{cases} 1 & \text{if } \text{action}_k \in \text{StaticReceivers}(i) \\ 0 & \text{otherwise} \end{cases} \qquad \mathbf{r}_i \in \{0,1\}^{R} \]
  • \(R\) — number of distinct system actions in vocabulary \(\mathcal{A}\)
  • \(r_{i,k}\) — presence bit for system action \(k\)
  • \(\mathbf{r}_i\) — receiver/action feature vector

Architecture flowchart

AndroidManifest.xml │ └─► <receiver> ──► <intent-filter> ──► <action> names │ │ │ └─► filter: system action list ▼ Receiver-action vector r (1 × R) [binary]

Output and connection to next stage

Output \(\mathbf{r}_i\). Alone: “action items only” experiment (~76–79% accuracy). Fused: \(\mathbf{x}_i = [\mathbf{p}_i \| \mathbf{r}_i]\).

Why this is different from standard permission-only detectors: Permissions say what the app may do; receiver actions say when background logic runs. A benign app may declare INTERNET without pairing BOOT_COMPLETED + SMS_RECEIVED — a pattern more typical of trojans.

Early Fusion — Combining Permissions and Receiver Actions

The paper does not use late fusion (separate classifiers + vote). It concatenates features before a single SVM.

\[ \mathbf{x}_i = [\mathbf{p}_i \| \mathbf{r}_i] \in \{0,1\}^{P+R} \]
  • \(\|\) — vector concatenation (permissions first, then actions — order must match training)
  • \(\mathbf{x}_i\) — joint input to the SVM for the combined scenario
p (1 × P) ──┐ ├──► x (1 × (P+R)) ──► single C-SVM ──► ŷ ∈ {malware, benign} r (1 × R) ──┘

Component C — C-SVM with RBF Kernel (The Classifier)

What it analyzes

The fused or single-domain binary vector \(\mathbf{x}_i\) for each APK, labeled malware (\(y_i = +1\)) or benign (\(y_i = -1\)).

Why SVM was chosen

High-dimensional sparse binary features are common in text-like malware work. SVMs with kernels handle non-linear boundaries without explicit neural layers; the paper cites Vapnik and prior text-mining use (Section IV-B).

Step-by-step training process

  1. Build one of three feature matrices: actions-only, perms-only, or combined (see preprocessing).
  2. Split data ~80% train / ~20% test (paper: approximately 4:1).
  3. On the training fold, run 10-fold cross-validation grid search over \(C \in \{10^1,\ldots,10^5\}\) and \(\gamma \in \{10^{-6},\ldots,10^{-1}\}\) for RBF kernel.
  4. Select best \((C, \gamma)\); paper’s average optimum: \(C = 10^1\), \(\gamma = 10^{-1}\) for both duplicate and unique pipelines.
  5. Train final C-SVM on full training split; evaluate on held-out test split.
  6. Repeat for 10 random balanced datasets; report mean accuracy and standard deviation.

Mathematical formulation

Primal margin hyperplanes (binary labels \(y_i \in \{-1,+1\}\)):

\[ \mathbf{w}^T \mathbf{x} + b \geq 1 \quad \text{if } y_i = +1 \qquad \mathbf{w}^T \mathbf{x} + b \leq -1 \quad \text{if } y_i = -1 \] \[ \text{Maximize margin } \rho = \frac{2}{\|\mathbf{w}\|} \quad \Leftrightarrow \quad \min_{\mathbf{w},b} \frac{1}{2}\mathbf{w}^T\mathbf{w} \quad \text{s.t. } y_i(\mathbf{w}^T \mathbf{x}_i + b) \geq 1 \]
  • \(\mathbf{w}, b\) — weight vector and bias defining the separating hyperplane
  • \(y_i\) — class label (+1 malware, −1 benign in the paper’s notation)
  • \(\rho\) — margin between classes

C-SVM: soft margin with penalty \(C\) for misclassified points (trade-off margin vs errors).

RBF kernel (Eq. 2 in paper):

\[ K(\mathbf{x}_i, \mathbf{x}_j) = \exp\left(-\gamma \|\mathbf{x}_i - \mathbf{x}_j\|_2^2\right) \]
  • \(K\) — kernel function mapping inputs to a higher-dimensional space implicitly
  • \(\gamma\) — RBF width; large \(\gamma\) → tighter, more complex decision boundary
  • \(C\) — regularization; large \(C\) → fewer training errors allowed

Decision function (dual form):

\[ f(\mathbf{x}) = \mathrm{sign}\left( \sum_{i \in SV} \alpha_i y_i K(\mathbf{x}_i, \mathbf{x}) + b \right) \]
  • \(SV\) — support vectors (training points that define the boundary)
  • \(\alpha_i\) — dual coefficients learned during optimization

Architecture flowchart

Feature vector x (1 × D) where D = P, R, or P+R │ ▼ 10-fold CV grid on train (C, γ) for RBF kernel │ ▼ Trained C-SVM ──► f(x) ──► malware / benign

Evaluation metrics (Section V)

\[ \text{Sensitivity} = \frac{TP}{TP + FN} \qquad \text{Specificity} = \frac{TN}{TN + FP} \]
  • TP, FN, TN, FP — from confusion matrix (Table IX): actual M/B vs predicted \(\hat{M}\)/\(\hat{B}\)
  • Sensitivity — true positive rate (catch malware)
  • Specificity — true negative rate (accept benign)

Figure 5: box plots of sensitivity/specificity over 10 runs. Median sensitivity for actions-only models: 64% (duplicate) and 75% (unique) — actions alone favor missing some malware; combining with permissions raises sensitivity.

Data Preprocessing — Two Pipelines (Figure 4)

Source pool: 5,723 malware APKs and 48,262 benign APKs. Manifests parsed for permissions and system action items.

Pipeline 1 — “Duplicate configurations” (upper path in Figure 4)

  1. Randomly sample 5,723 benign apps to match malware count.
  2. Form balanced set of 11,446 apps (5,723 + 5,723).
  3. Repeat random sampling 10 times → ten datasets.
  4. Many APKs can share the exact same permission+action bit pattern → duplicates remain in train/test splits.

Pipeline 2 — “Unique configurations” (lower path in Figure 4)

  1. Collapse APKs that share identical feature vectors: keep one representative per configuration.
  2. Pool shrinks to 960 malware and 8,708 benign unique configs.
  3. Sample benign to match malware count per scenario → balanced sizes in Table VII.

Why duplicate vs unique matters for interpreting results: When the same \((\mathbf{p}, \mathbf{r})\) pattern appears in both train and test, accuracy is inflated (memorization of configurations). Unique-configuration experiments drop accuracy (~96% → ~86% for permissions) but better reflect generalization to unseen combinations of features.

Manual Java Analysis — onReceive() (Section III-C, Table VI)

On a subset with receivers (138 malware, 92 benign), the authors inspect decompiled onReceive(Context, Intent) for API calls: start service, register another receiver, goAsync(), start activity, create notification, or none.

Interpretation: Malware “uses” receivers — 92.5% implement something in onReceive vs 65.33% benign; malware often jumps to an Activity (UI or further payload). This analysis does not feed the SVM; it supports the narrative that receivers are actively exploited, while the classifier stays manifest-only for scalability.

What improved over what — and why

ComparisonObservationExplanation
Actions vs permissions (duplicate) 78% vs 96% Permissions alone are very discriminative on this corpus; many malware families request distinctive dangerous permissions.
Permissions vs combined (duplicate) 96% → 97% Receiver actions add complementary signal: event-driven behavior not fully captured by permission bits. Small but consistent gain; paper highlights improved sensitivity (Figure 5).
Actions-only duplicate vs unique 78% vs 79% Stable — action patterns generalize similarly.
Permissions duplicate vs unique 96% → 86% Duplicate APKs with identical feature vectors leak into train and test; unique collapse exposes harder generalization.
Combined duplicate vs unique 97% → 86% Same configuration leakage effect; combined model on unique data matches permissions-only unique (~86%).

Takeaway for your thesis: Quote 97% only with the duplicate-configuration caveat. For honest generalization, emphasize the unique row (~86%) or the independent test (below).

Independent Test Set — Table X & Figure 6

398 apps (199 malware + 199 benign), more recent than the main corpus. Features restricted to the intersection of actions/permissions seen in the original training vocab (new permissions/actions in newer apps are dropped → “missing features”). The ten models trained earlier are applied without retraining.

Features Duplicate models — Accuracy Unique models — Accuracy
Actions only71%72%
Permissions only76%74%

Why accuracy drops (97% → 77% for permissions+combined)

  • Temporal drift: Newer malware/benign apps use permissions and actions not in the old vocabulary → zeros in the feature vector.
  • Feature intersection only: Deliberate design for fair comparison, but it weakens signal on new APKs.
  • Actions still help: Combined (77%) beats permissions alone (76%) on duplicate models — consistent with the main claim under harder conditions.
  • Sensitivity vs specificity: On this set, catching malware (sensitivity) is harder than labeling benign (specificity) — opposite tendency to the main test (Figure 6).
