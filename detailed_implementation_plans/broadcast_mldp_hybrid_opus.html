Prerequisites (beginner)

MLDP-pruned permissions: Instead of the ~135-permission Android space, an offline procedure keeps only ~16–25 highly discriminative permissions. Paper #7 publishes the resulting list (e.g. SEND_SMS, READ_SMS, RECEIVE_BOOT_COMPLETED, INSTALL_PACKAGES, READ_CONTACTS, CAMERA, DISABLE_KEYGUARD, …). See ../rough_model_explanations/mldp_pruned_permission_classifier.html.

Statically registered broadcast receiver (system action): a <receiver> declared in the manifest whose <intent-filter><action> names a built-in Android system event (e.g. android.intent.action.BOOT_COMPLETED). It is an entry point the OS can invoke even when the app is not running — which is exactly why malware likes them (Mohsen 2017).

Concatenation [a ‖ b]: put vector a first, then b, forming one longer vector — early fusion (\([\mathbf{a} \,\|\, \mathbf{b}]\)).

Tiny MLP: a small neural net (e.g. \(d \to 64 \to 1\)) that learns mild nonlinear conjunctions like “SMS permission AND SMS_RECEIVED receiver together.” It is the ONNX-deployable stand-in for the papers’ RBF-SVM.

1. Overview

On the thesis corpus (year-split 2020–2021 train / 2022–2023 test), we want a manifest-only detector that is tiny enough for mid-range phones yet richer than permissions alone. The cross-paper hybrid concatenates a ~16–25-dim MLDP-selected permission block (paper #7) with a ~30–80-dim statically-registered broadcast system-action block (paper #12) into one vector of roughly 50–100 dimensions, then classifies it.

Why combine them? Paper #12 empirically showed permissions and receiver actions are complementary: action items lift sensitivity (catching malware) when added to permissions, and “combined > either alone” on its independent test set. Paper #7 showed that pruning the permission space removes noise that otherwise dilutes a linear separator and keeps accuracy stable as the dataset grows. The hybrid’s one genuine modification over #12 is swapping #12’s full permission vector for #7’s pruned one — fewer, cleaner dimensions for the same behavioral signal.

Correction M5: with \(|\mathcal S|\approx 22\) and \(R\approx 30\text{–}80\), the fused width is \(d\approx 50\text{–}100\), not 80–120. No Dex decompilation, no 2500-d bag-of-words — two orthogonal manifest signals in one pass.

2. Component A — MLDP permission sub-vector corrected

What it analyzes

Only the permissions in the frozen MLDP set \(\mathcal{S}\), derived offline from the train split only.

Why this input was chosen

The full ~135-permission space is redundant and noisy. #7 shows a small curated set keeps F-measure ≈94–97% even as the corpus grows to 60k apps, where unpruned permission models degrade. It is the compact “what can this app do?” signal.

Correction M2 — which algorithm? Paper #7 actually describes two pruning pipelines and the original rough plan blended them:
  • Variant 1 (SigPID / MLDP, lit-review §II-D, attributed to Li [10]): three layers — (i) PRNR Permission Ranking with Negative Rate, (ii) SPR Support-based Permission Ranking, (iii) PMAR Permission Mining with Association Rules. Reduction: 135 → 95 (PRNR) → 25 (SPR) → 22 (PMAR). The 22 permissions are listed in Table I.
  • Variant 2 (#7’s own “Proposed Framework”, §IV): data-skew correction → TF-IDF permission ranking → PCA → Kaiser + Cumulative factor analysis → intersect with Li’s list & Google’s dangerous list. Result: 16 dangerous permissions (Table VI), experiments report “20 selected permissions”.
Recommendation: implement Variant 1 (PRNR→SPR→PMAR) — it is deterministic, cheap, and reproducible on our own train split — and keep #7’s published 16/22-permission list as a fixed fallback / sanity baseline. Variant 2’s PCA+factor-analysis is harder to reproduce exactly and is not needed for a binary presence vector.

Step-by-step (Variant 1, recommended)

  1. Offline on split=train APKs build matrices \(M\) (malware) and \(B\) (benign), \(M_{ij},B_{ij}\in\{0,1\}\) = permission \(j\) declared by app \(i\).
  2. Data-skew correction: scale the supports so class sizes are comparable (#7 eq. 1/3) before ranking.
  3. PRNR: compute the negative-rate score \(R(P_j)\in[-1,1]\) (below); drop permissions with \(R(P_j)\approx 0\) (used equally by both classes). 135 → ~95.
  4. SPR: rank survivors by overall support; keep the most-supported. ~95 → ~25.
  5. PMAR (Apriori, conf ≥ 96.5%, min-sup 10%): collapse permissions that co-occur as rules (e.g. WRITE_SMS⇒READ_SMS). ~25 → ~22. Freeze as \(\mathcal S\).
  6. At inference: parse manifest; \(x^{(S)}_j=1\) iff \(\text{perm}_j\in\mathcal S\) is declared.

Mathematical formulation M4 added the PRNR formula

Per-class support of permission \(P_j\) (fraction of class apps declaring it), with skew correction so \(|M|\) and \(|B|\) are comparable:

\[ S_M(P_j)=\frac{1}{|M|}\sum_i M_{ij}, \qquad S_B(P_j)=\frac{1}{|B|}\sum_i B_{ij} \]

Permission Ranking with Negative Rate (range \([-1,1]\)):

\[ R(P_j)=\frac{S_M(P_j)-S_B(P_j)}{S_M(P_j)+S_B(P_j)} \]

\(R\!\to\!+1\): malware-indicative (dangerous); \(R\!\to\!-1\): benign-indicative; \(R\!\approx\!0\): non-discriminative → dropped. (Correction M4: the original plan said PRNR “keeps malware-skewed” permissions; in fact both extremes are kept because both help separate the classes — only \(R\approx0\) is pruned.)

Final inference encoding:

\[ x^{(S)}_j = \begin{cases} 1 & \text{if } \text{perm}_j \in \mathcal{S} \text{ and declared} \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|},\ \ |\mathcal S|\approx 22 \]

  • \(\mathcal{S}\) — MLDP-frozen permission subset (train-only)
  • \(\mathbf{x}^{(S)}\) — pruned permission feature block

Architecture flowchart

OFFLINE (train split only)
  M,B matrices → skew-correct → PRNR(135→95) → SPR(95→25) → PMAR(25→22) → freeze S
INFERENCE
  Manifest → x^(S)  (1×|S|)   e.g. 1×22
Key novelty: curated permission dimensions (train-frozen) instead of #12’s full ~98–178-permission space — same capability signal, far less noise.

3. Component B — Broadcast receiver (system-action) sub-vector corrected

What it analyzes

The android:name of <action> elements under statically registered <receiver><intent-filter> in the manifest.

Correction M3 — system actions only. The original plan said “collect all <action> names”. Mohsen 2017 is explicit: “we are only concerned with the receivers of the system actions. The set of system actions of Android OS releases are compiled in one file.” So \(\mathcal A\) must be built against a fixed allow-list of Android system broadcast actions (the android.intent.action.*, android.net.conn.*, android.provider.Telephony.*, … families), not custom/third-party action strings. This matters for (a) faithfulness to #12 and (b) Python↔Java parity (same allow-list shipped to the device).

Empirical grounding from #12: malware collectively used 28 distinct system actions, benign 57; top malware actions = BOOT_COMPLETED, USER_PRESENT, PHONE_STATE, SMS_RECEIVED, NEW_OUTGOING_CALL. So \(R\approx 30\text{–}80\) is the right magnitude.

Why this input was chosen

Receivers capture event-driven behavior orthogonal to permissions: statically registered receivers wake the app on system events without user interaction. #12 found 74% of malware vs 65% of benign declare a receiver, and 70% vs 46% declare one for a system action — the gap is the signal.

Step-by-step

  1. Parse the same AndroidManifest.xml.
  2. Collect <action> names under every static <receiver>…<intent-filter>.
  3. Filter to the Android system-action allow-list (drop custom actions).
  4. Build vocabulary \(\mathcal{A}\) from the train split system actions (\(R\approx 30\text{–}80\)).
  5. Set \(x^{(R)}_k = 1\) iff system action \(k\in\mathcal A\) present in this APK (set semantics — duplicates collapse to one bit).

Mathematical formulation

\[ x^{(R)}_k = \begin{cases} 1 & \text{if } \text{action}_k \in \mathcal{A}\ \cap\ \text{StaticReceivers}(\text{APK}) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{x}^{(R)} \in \{0,1\}^{R} \]

  • \(\mathcal A\) — train-frozen Android system-action vocabulary
  • \(R=|\mathcal A|\) — receiver-action vocabulary size (~30–80)

Architecture flowchart

Manifest
  └─► <receiver>/<intent-filter>/<action>
         └─► keep only Android system actions (allow-list ∩ train vocab A)
                └─► x^(R)  (1×R)   e.g. 1×50
Key point (kept): receiver domain is unchanged from Mohsen — proven complementary to permissions — but we now enforce the system-action restriction the paper actually used.

4. Component C — Early fusion (concatenation) faithful

What it analyzes

A single manifest feature vector combining the MLDP permission block and the receiver system-action block.

Why

Mohsen’s “combined” scenario concatenated permissions + actions into one vector for a single SVM — i.e. early fusion. It lets the classifier learn cross-domain conjunctions (dangerous permission ∧ boot receiver) in one weight set.

Mathematical formulation

\[ \mathbf{x} = [\mathbf{x}^{(S)} \,\|\, \mathbf{x}^{(R)}] \in \{0,1\}^{|\mathcal{S}| + R},\qquad d=|\mathcal S|+R\approx 50\text{–}100 \]

Architecture flowchart

x^(S) (1×|S|) ──┐
                ├──► x (1×d)   e.g. 1×72  (22 + 50)
x^(R) (1×R)   ──┘
Key advantage: roughly 3× smaller than #12’s full perm+receiver vector while keeping both signal types; one classifier, one score, no late merge.

5. Component D — Classifier head SVM baseline added

Deployment head — tiny MLP (ONNX)

\[ \mathbf{h} = \max(0,\ \mathbf{W}_1 \mathbf{x} + \mathbf{b}_1),\quad \mathbf{W}_1\in\mathbb R^{64\times d}; \qquad \hat{y} = \sigma(\mathbf{w}_2^\top \mathbf{h} + b_2) \]

Trained with binary cross-entropy and a class-imbalance weight (Correction M7):

\[ \mathcal{L} = -\,\big[\, w_+\, y \log \hat{y} + (1-y)\log(1-\hat{y})\,\big],\quad w_+ = \tfrac{N_\text{neg}}{N_\text{pos}} \]

Architecture \(d\to 64\to 1\) (e.g. \(72\to64\to1\)); logistic regression \(d\to1\) is an even smaller alternative if it matches the MLP on validation.

Correction M6 — paper-faithful baseline. Both source papers classify with an RBF-kernel C-SVM, not an MLP: \[ f(\mathbf{x})=\operatorname{sign}\!\Big(\textstyle\sum_{i\in SV}\alpha_i y_i K(\mathbf{x}_i,\mathbf{x})+b\Big),\quad K(\mathbf{x},\mathbf{x}')=e^{-\gamma\|\mathbf{x}-\mathbf{x}'\|_2^2}. \] #12 grid-searched \(C\in\{10^1..10^5\}\), \(\gamma\in\{10^{-6}..10^{-1}\}\) and reported the optimum at \(\gamma=0.1,\ C=10\); #7 used SVM + Decision Tree with an 80/20 split. Run the RBF-SVM as the reproducibility baseline (sklearn, offline only) and export the MLP/logistic to ONNX. The MLP is justified because RBF-SVM is nonlinear and a single hidden layer is the cheapest ONNX-friendly way to recover those conjunctions.

Architecture flowchart

x (1×d)  e.g. 1×72
   │
   ▼  Linear d→64 + ReLU
   │
   ▼  Linear 64→1 + σ
   ▼
P(malware) ∈ [0,1]      (offline twin: RBF-SVM, γ=0.1, C=10)
Key advantage: model size typically < 20 KB; inference < 1 ms after manifest parse.

Why the hybrid should win: MLDP removes the permission noise that drags down a linear/RBF separator (#7), while system-action receivers add the behavioral-timing signal #12 demonstrated empirically.
