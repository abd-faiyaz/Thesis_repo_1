Prerequisites (beginner)

MLDP-pruned permissions: instead of the ~135-permission Android space, an offline procedure keeps only ~16–25 highly discriminative permissions (paper #7 publishes the list — e.g. SEND_SMS, READ_SMS, RECEIVE_BOOT_COMPLETED, INSTALL_PACKAGES, READ_CONTACTS, CAMERA, DISABLE_KEYGUARD). Manifest-only — no Dex needed. See ../rough_model_explanations/mldp_pruned_permission_classifier.html.

Dex header \(\mathbf H\) (104-d): every classes*.dex file starts with a fixed 112-byte header. Bytes 0–7 are the magic (dex\n035\0); bytes 8–111 hold the checksum, SHA-1 signature, and a series of uint32 section sizes/offsets (file_size, map_off, string_ids_size, …). Reading just these 104 bytes captures the structural “shape” of the code without scanning any bytecode. This is exactly the deployed MLP(H) input.

Cascade / multistep detection: run the cheapest model first; early-exit if the score \(s < t_{\mathrm{low}}\) (confidently benign) or \(s > t_{\mathrm{high}}\) (confidently malware); otherwise escalate to a more expensive model (thesis Task 2).

Fused single-pass variant: alternatively concatenate \(\mathbf x^{(S)}\) and \(\mathbf H\) into one vector and run a single tiny MLP — simpler to deploy as one ONNX graph than tuning two cascade thresholds.

Two-stage normalization (Dex): “min–max” here means scaling each feature \(x\to(x-\min)/(\max-\min)\) using fixed mins/maxs computed once on the training corpus — never recomputed on a single phone APK (that would break parity).

1. Overview

Problem: running ByteCNN, ASCNN(C), and XGBoost on every APK wastes battery. Solution: combine the two cheapest static domains in the thesis — (1) MLDP-pruned permissions \(\mathbf x^{(S)}\in\{0,1\}^{|\mathcal S|}\), \(|\mathcal S|\approx22\) (paper #7), and (2) the Dex header \(\mathbf H\in[0,1]^{104}\) (deployed MLP(H)). Deploy as Mode A (fused vector \(\mathbf x\in\mathbb R^{d},\ d\approx126\) → one tiny MLP) or Mode B (cascade: MLDP logistic → reuse MLP(H) → expensive stack). Goal: cheaply gate a large fraction of APKs in one early pass before manifest BoW or raw-byte models.

Correction M5: with \(|\mathcal S|\approx22\) and the header \(=104\), the fused width is \(d=|\mathcal S|+104\approx126\) (range 120–134), not “~150”. Bias terms do not count toward input width.

Why these two domains are complementary: permissions are declared capability/intent (what the app says it can do); the Dex header is structural evidence (how the compiled code is laid out — oversized string pools, odd offsets). A trojan with a near-empty manifest can still have an anomalous header, and vice-versa. Orthogonal, both cheap.

2. Component A — MLDP permission sub-vector \(\mathbf x^{(S)}\) corrected

What it analyzes

Only the permissions in the frozen MLDP set \(\mathcal S\), derived offline from the train split only.

Why this input was chosen

The full ~135-permission space is redundant and noisy. Paper #7 shows a small curated set keeps F-measure ≈94–97% even as the corpus grows to 60k apps, where unpruned permission models degrade (their Table II/VIII–X). It is the compact “what can this app do?” signal, and it requires only a manifest parse.

Correction M2 — which algorithm? Paper #7 actually describes two pruning pipelines and the original rough plan blended them:
  • Variant 1 (SigPID / MLDP, §II-D, attributed to Li [10]): three layers — (i) PRNR Permission Ranking with Negative Rate, (ii) SPR Support-based Permission Ranking, (iii) PMAR Permission Mining with Association Rules. Reductions stated in the paper: 135 → 95 (PRNR) → 25 (SPR) → 22 (PMAR). The 22 permissions are in Table I.
  • Variant 2 (#7’s own “Proposed Framework”, §IV): data-skew correction → TF-IDF permission ranking → PCA → Kaiser + Cumulative factor analysis → intersect with Li’s list & Google’s dangerous list. Result: 16 dangerous permissions (Table VI); experiments report “20 selected permissions” (Tables VIII–IX).
Recommendation: implement Variant 1 (PRNR→SPR→PMAR) — deterministic, cheap, reproducible on our own train split — and keep #7’s published 16/22-permission list as a fixed fallback / sanity baseline. Variant 2’s PCA + factor-analysis is harder to reproduce exactly and is unnecessary for a binary presence vector.

Step-by-step (Variant 1, recommended)

  1. Offline on split=train APKs build matrices \(M\) (malware) and \(B\) (benign), entries \(M_{ij},B_{ij}\in\{0,1\}\) = permission \(j\) declared by app \(i\).
  2. Data-skew correction (eq. 1/3): scale the support of the larger class down so \(|M|\) and \(|B|\) are comparable before ranking.
  3. PRNR (eq. 2): compute \(R(P_j)\in[-1,1]\) (below); drop permissions with \(R(P_j)\approx0\) (used equally by both classes). 135 → ~95.
  4. SPR: rank survivors by overall support; keep the most-supported. ~95 → ~25.
  5. PMAR (Apriori, confidence ≥ 96.5%, min-support 10%): collapse permissions that imply each other (e.g. WRITE_SMS ⇒ READ_SMS); paper removed 3. ~25 → ~22. Freeze as \(\mathcal S\).
  6. At inference: parse manifest; set \(x^{(S)}_j=1\) iff permission \(j\in\mathcal S\) is declared.

Mathematical formulation M3 — exact PRNR added

Per-class support of permission \(P_j\) (fraction of class apps declaring it), after skew correction so \(|M|\) and \(|B|\) are comparable:

\[ S_M(P_j)=\frac{1}{|M|}\sum_i M_{ij}, \qquad S_B(P_j)=\frac{1}{|B|}\sum_i B_{ij} \]

Permission Ranking with Negative Rate (paper #7 eq. 2), range \([-1,1]\):

\[ R(P_j)=\frac{S_M(P_j)-S_B(P_j)}{S_M(P_j)+S_B(P_j)} \]

\(R\to+1\): malware-indicative (dangerous); \(R\to-1\): benign-indicative; \(R\approx0\): non-discriminative → dropped. (Correction M3: the cascade plan gave no PRNR formula and the sibling MLDP plan implied a one-sided ratio \(\tfrac{M_j/N_m}{B_j/N_b}\). The paper’s actual score is the symmetric difference-over-sum above, and both extremes are kept because a strongly-benign permission separates classes just as well — only \(R\approx0\) is pruned.)

Final inference encoding:

\[ x^{(S)}_j = \begin{cases} 1 & \text{if } \mathrm{perm}_j \in \mathcal S \text{ and declared} \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf x^{(S)} \in \{0,1\}^{|\mathcal S|},\ \ |\mathcal S|\approx 22 \]

  • \(\mathcal S\) — MLDP-frozen permission subset (train-only)
  • \(\mathbf x^{(S)}\) — pruned permission feature block

Architecture flowchart

OFFLINE (train split only)
  M,B matrices → skew-correct → PRNR(135→95) → SPR(95→25) → PMAR(25→22) → freeze S
INFERENCE
  Manifest → x^(S)  (1×|S|)   e.g. 1×22
Key novelty: ~22 curated, train-frozen dimensions vs the 2500-d deployed XGBoost permission/feature space — an ideal cheap cascade front-end.

3. Component B — Dex header vector \(\mathbf H\) (104-d) corrected

What it analyzes

Bytes 8–111 of every classes*.dex header — checksum, SHA-1 signature, and the uint32 section sizes/offsets (file_size, header_size, map_off, string_ids_size, …). Structural metadata only; no bytecode is read.

Why this input was chosen

Malware often has an abnormal Dex layout (oversized string pools, odd offsets, packed/multidex artifacts) even when the manifest looks minimal. The header is a fixed 112-byte prefix, so parsing it is very cheap.

Correction M10 — cost claim. The original said the header read is “O(1) in file size — no string scan.” More precisely: you still unzip the APK and locate each classes*.dex entry, but only the first 112 bytes per dex are parsed (no bytecode/string-pool scan). So the parse cost is tiny and roughly constant per dex, but not literally O(1) in total APK size.
Correction M4 — normalization is three ordered stages, not one. The rough plan said “bytes/255, min–max normalized, sum-pooled” and wrote \(\mathbf H=\sum_d \mathbf h^{(d)}\in[0,1]^{104}\). The deployed implementation (and therefore the parity-correct definition) is:
  1. Per-byte scale: for each dex, \(h^{(d)}_b=\mathrm{byte}_b/255\in[0,1]\), \(b=8\ldots111\).
  2. Multidex sum-pool: \(\mathbf H_{\text{raw}}=\sum_{d=1}^{D_{\mathrm{dex}}}\mathbf h^{(d)}\). This sum lies in \([0,D_{\mathrm{dex}}]\) per dimension — not in \([0,1]\).
  3. Corpus min–max: \(\mathbf H=(\mathbf H_{\text{raw}}-\boldsymbol{\min})/(\boldsymbol{\max}-\boldsymbol{\min})\), where \(\boldsymbol{\min},\boldsymbol{\max}\) are fixed train-corpus statistics shipped in normalization_header.json; constant dims map to 0.
So the model input is the min–max-of-the-sum, in that order. The maxs are not capped at 1.0 (sum-pooling pushes them to ~tens).

Step-by-step

  1. Unzip APK; enumerate all classes*.dex (regex ^classes(\d*)\.dex$, primary first then numeric suffix).
  2. Verify the 8-byte magic dex\n035\0 (reject otherwise → failed_apks.log).
  3. For each dex: \(h^{(d)}_b=\mathrm{byte}_b/255\) for \(b=8\ldots111\) (104 values).
  4. Sum-pool element-wise across all dex → \(\mathbf H_{\text{raw}}\in[0,D_{\mathrm{dex}}]^{104}\) (default multidex.mode = sum).
  5. Apply saved train-corpus min–max → \(\mathbf H\in[0,1]^{104}\).

Mathematical formulation

\[ h^{(d)}_b=\frac{\mathrm{byte}^{(d)}_b}{255},\qquad \mathbf H_{\text{raw}}=\sum_{d=1}^{D_{\mathrm{dex}}}\mathbf h^{(d)}\in[0,D_{\mathrm{dex}}]^{104} \]

\[ \mathbf H=\frac{\mathbf H_{\text{raw}}-\boldsymbol{\min}_{\text{train}}}{\boldsymbol{\max}_{\text{train}}-\boldsymbol{\min}_{\text{train}}}\in[0,1]^{104} \]

  • \(D_{\mathrm{dex}}\) — number of dex files in the APK
  • \(\boldsymbol{\min}_{\text{train}},\boldsymbol{\max}_{\text{train}}\) — per-dimension train statistics (shipped, frozen)
  • \(\mathbf H\) — final 104-d header feature vector

Architecture flowchart

APK
  ├─ classes.dex  → bytes[8:112]/255 ─┐
  ├─ classes2.dex → bytes[8:112]/255 ─┼─► sum-pool → H_raw (1×104, range [0,D])
  └─ classes3.dex → bytes[8:112]/255 ─┘            │
                                                    ▼
                                  corpus min–max (train stats) → H (1×104, [0,1])
Correction M8 — multidex. Sum-pool is correct and matches the deployed default. The MSFDroid paper itself used the primary classes.dex only; keep primary_only as a documented ablation (multidex_mode recorded in the export manifest for parity).
Why pair with MLDP: permissions = declared risk; header = structural risk — orthogonal cheap signals, both extractable in well under a manifest-BoW or byte-CNN budget.

4. Component C — Fused tiny MLP (Mode A) dims & head corrected

What it analyzes

A single forward pass on the concatenated MLDP + header vector — one ONNX graph, one score.

Why this mode

When the latency budget allows one network call but you do not want to maintain two-stage threshold logic, fusion is simpler to deploy: one input tensor, one output, no branch.

Step-by-step

  1. Build \(\mathbf x^{(S)}\in\{0,1\}^{|\mathcal S|}\) (manifest) and \(\mathbf H\in[0,1]^{104}\) (dex, 3-stage normalized).
  2. Concatenate \(\mathbf x=[\mathbf x^{(S)}\,\|\,\mathbf H]\in\mathbb R^{d}\), \(d=|\mathcal S|+104\approx126\).
  3. MLP layer 1: \(\mathbf h=\mathrm{ReLU}(\mathbf W_1\mathbf x+\mathbf b_1)\), hidden dim 64 (BatchNorm optional).
  4. Output: \(\hat y=\sigma(\mathbf w_2^\top\mathbf h+b_2)\).
  5. Calibrate \(t_{\mathrm{low}},t_{\mathrm{high}}\) on the val holdout for early-exit; export ONNX (opset 14), target < 30 KB.

Mathematical formulation M5, M6

\[ \mathbf x=[\mathbf x^{(S)}\,\|\,\mathbf H]\in\mathbb R^{d},\quad d=|\mathcal S|+104\approx126,\qquad \hat y=\sigma\!\big(\mathbf W_2\,\mathrm{ReLU}(\mathbf W_1\mathbf x+\mathbf b_1)+b_2\big) \]

Trained with class-imbalance-weighted BCE (Correction M12):

\[ \mathcal L=-\big[\,w_+\,y\log\hat y+(1-y)\log(1-\hat y)\,\big],\qquad w_+=\frac{N_{\text{neg}}}{N_{\text{pos}}} \]

  • \(d\approx126\) — fused dimension \(=|\mathcal S|+104\) (M5; not 150)
  • \(\hat y\) — malware probability from a single pass

Architecture flowchart

x^(S) (1×|S|)  e.g. 1×22 ──┐
                            ├──► x (1×d)  d≈126 ──► MLP(d→64→1) ──► ŷ ∈ [0,1]
H (1×104) ─────────────────┘
Key advantage: one ONNX graph, one manifest + header read — the simplest possible integration for a Step-1 filter.

5. Component D — Two-stage cascade (Mode B) reuse deployed MLP(H)

What it analyzes

Stage 1: logistic/linear on MLDP permissions only (fastest, manifest-only). Stage 2: the already-deployed MLP(H) on \(\mathbf H\), invoked only when Stage 1 is uncertain.

Correction M6 — reuse, don’t reinvent. The deployed mlp_header model is exactly \(104\to128\to128\to1\) (Linear+BatchNorm+ReLU twice, sigmoid head). Mode B Stage 2 should load that shipped ONNX rather than training a new header net — so Mode B’s only new artifact is the Stage-1 MLDP logistic head.

Why this mode

It separates manifest-only cost from dex-header cost: for confident Stage-1 decisions you can skip the unzip-and-read-dex step entirely (an optional latency optimization).

Step-by-step

  1. Stage 1: \(s_1=\sigma(\mathbf w_1^\top\mathbf x^{(S)}+b_1)\) (offline twin: SVM/DT per #7).
  2. If \(s_1<t_{\mathrm{low}}\) → label benign, STOP.
  3. If \(s_1>t_{\mathrm{high}}\) → label malware, STOP.
  4. Else Stage 2: \(s_2=\mathrm{MLP_H}(\mathbf H)\) (deployed \(104\to128\to128\to1\), sigmoid already inside).
  5. If still uncertain → escalate to ByteCNN / ASCNN / XGBoost, etc.

Mathematical formulation

Stage 1: \[ s_1=\sigma(\mathbf w_1^\top\mathbf x^{(S)}+b_1) \]

Stage 2 (reused model, sigmoid in-graph): \[ s_2=\mathrm{MLP_H}(\mathbf H)\in[0,1] \]

  • \(t_{\mathrm{low}},t_{\mathrm{high}}\) — cascade thresholds tuned on the train-holdout val set
  • STOP — early exit that saves average latency

Architecture flowchart

APK → Manifest → x^(S) → s1
                          │
                          ├─ s1 < t_low  ──► BENIGN  (done, no dex read)
                          ├─ s1 > t_high ──► MALWARE (done, no dex read)
                          └─ else → read dex → H → MLP(H) → s2
                                  │
                                  ├─ confident → done
                                  └─ else → expensive models …
Correction M11 — exit rate. The “~70% exit after Step 1” figure is a hypothesis, not a measured result. Calibrate \(t_{\mathrm{low}},t_{\mathrm{high}}\) on the val holdout to hit a target false-omission rate, then report the realized exit rate in P6.
Why different from Mode A: interpretable staging (permission risk first, structural confirm second) and it reuses an existing shipped model — but it needs two thresholds and branch logic on-device.
