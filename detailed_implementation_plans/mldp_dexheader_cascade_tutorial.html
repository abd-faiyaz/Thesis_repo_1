The big picture in one diagram

The model reads two cheap things from the APK — the AndroidManifest.xml (for permissions) and the first 112 bytes of each classes*.dex (the header) — turns them into numbers, and a tiny network outputs a malware probability. No bytecode is ever scanned.

ELI5: Imagine triaging parcels. First you glance at the shipping label (permissions) — that's instant. If the label is obviously fine or obviously dodgy, you're done. Only for the maybe pile do you also weigh and X-ray the box (the Dex header). Most parcels never need the X-ray, so the line moves fast.

Prerequisites — plain-English concepts

What is the AndroidManifest?

Every app ships a manifest declaring the permissions it wants. We never run the app — we just read the declaration. That's static analysis: cheap, fast, safe.

What is a "permission"?

ELI5: A permission is a door key the app requests, e.g. SEND_SMS or CAMERA. More dangerous keys = more risk if the app is bad.

What is "MLDP"?

ELI5: Android has ~135 permissions. Most are useless for spotting malware (almost every app wants INTERNET). MLDP = Multi-Level Data Pruning: a filtering funnel that throws away the useless permissions and keeps ~22 that actually separate good from bad apps.

What is a "Dex header"?

Your app's compiled code lives in classes.dex files. Each one begins with a fixed 112-byte header: the first 8 bytes are a "magic" signature, and the next 104 bytes are numbers describing the code's structure (how many strings, where each section starts, total size…).

Why it helps: malware often has a weird code layout (huge string pools, odd offsets, packers). The header reveals that "shape" instantly — even if the manifest looks innocent.

What is a cascade?

A cascade runs cheap checks first and only escalates to expensive ones when unsure. If the cheap score is very low → benign (stop). Very high → malware (stop). In-between → run the next stage.

What is a tiny MLP?

A Multi-Layer Perceptron: a mini neural network. Small enough (<30 KB) to run on a phone in well under a millisecond.

① MLDP permission row (from Paper #7)

Goal: turn the manifest's permissions into a short, clean checkbox row using only the ~22 permissions that matter. The "which 22?" is decided once, offline, on the training apps, then frozen.

The pruning funnel (Variant 1: PRNR → SPR → PMAR)

135 permissions — everything Android offers
≈ 95 — after PRNR (drop the ones used equally by good & bad apps)
≈ 25 — after SPR (keep the most frequently-used survivors)
≈ 22 — after PMAR (merge permissions that always travel together)

Step 1 — PRNR (Permission Ranking with Negative Rate)

For each permission we measure how "lopsided" it is between malware and benign apps. Let \(S_M(P_j)\) and \(S_B(P_j)\) be the fraction of malware / benign apps that declare permission \(P_j\) (after correcting for class-size imbalance). Then:

\[ R(P_j)=\frac{S_M(P_j)-S_B(P_j)}{S_M(P_j)+S_B(P_j)}\in[-1,1] \]

R → +1malware-only
e.g. SEND_SMS
R ≈ 0used by both
→ DROP
R → −1benign-only
Correction we made (M3): the cascade rough plan gave no PRNR formula, and the sibling MLDP plan implied a one-sided ratio. Paper #7's actual score is the symmetric difference-over-sum above, and it keeps both ends (\(R\to+1\) and \(R\to-1\)) — a strongly-benign permission separates classes just as well. Only the middle (\(R\approx0\)) is dropped.

Step 2 — SPR (Support-based Permission Ranking)

Among the survivors, keep the ones that appear often enough to be statistically reliable (drop ultra-rare permissions). ~95 → ~25.

Step 3 — PMAR (Permission Mining with Association Rules)

Some permissions are redundant twins — e.g. WRITE_SMS nearly always appears with READ_SMS. Using the Apriori algorithm (confidence ≥ 96.5%, support ≥ 10%), we collapse such pairs to one. The paper removed 3. ~25 → ~22. This frozen set is \(\mathcal S\).

At inference (per new app)

\[ x^{(S)}_j=\begin{cases}1 & \text{if }P_j\in\mathcal S\text{ and declared}\\ 0&\text{otherwise}\end{cases},\qquad \mathbf x^{(S)}\in\{0,1\}^{|\mathcal S|},\ |\mathcal S|\approx 22 \]

Correction (M1 / M2): the size is ~16–25 (≈22), not "20–40". And paper #7 has two methods — we use the deterministic PRNR→SPR→PMAR funnel (Table I = 22 perms), not the harder-to-reproduce PCA/Kaiser variant (which gives 16/20).

② Dex header row (MSFDroid / deployed MLP(H))

Goal: turn each classes*.dex header into 104 numbers, combine multidex files, and scale to [0,1]. This is exactly what the already-deployed MLP(H) model eats.

Three ordered steps M4

bytes 8–111 of each dex104 raw bytes (0–255)
① ÷ 255each byte → [0,1]
② sum-pool across classes*.dexHraw ∈ [0, D] (D = #dex)
③ corpus min–max (train stats)H ∈ [0,1]104
Correction (M4): the rough plan said "bytes/255, min–max, sum-pooled" and wrote \(\mathbf H=\sum_d\mathbf h^{(d)}\in[0,1]^{104}\). Order matters! After summing across dex files the values can exceed 1 (range \([0,D]\)). The min–max comes last, using fixed mins/maxs measured once on the training set — never recomputed on a single phone APK (that would break parity).

The math

\[ h^{(d)}_b=\frac{\text{byte}^{(d)}_b}{255},\qquad \mathbf H_{\text{raw}}=\sum_{d=1}^{D_{\text{dex}}}\mathbf h^{(d)}\in[0,D_{\text{dex}}]^{104} \]

\[ \mathbf H=\frac{\mathbf H_{\text{raw}}-\boldsymbol{\min}_{\text{train}}}{\boldsymbol{\max}_{\text{train}}-\boldsymbol{\min}_{\text{train}}}\in[0,1]^{104} \]

ELI5 of multidex sum-pool: big apps split their code into classes.dex, classes2.dex, … We add up each file's header numbers position-by-position so one combined row represents the whole app. (The original MSFDroid paper used only the first dex; our deployed code sums them — we keep "first only" as an optional comparison.)
Correction (M10): "header read is O(1)" is too strong — we still unzip and locate every dex. But we only read the 112-byte header of each (no bytecode scan), so it stays very cheap.

From paper to phone — the build pipeline (P1 → A4)

Two code bases cooperate: a Python project trains and exports; the Android app scans on-device. They must agree on features exactly — that's what the parity checks guard.

Offline — Python (P1–P8)

  1. P1 Index — list every APK with label, year; split train=2020–21, test=2022–23.
  2. P2 Features — parse manifests → MLDP funnel → freeze \(\mathcal S\); read dex headers → fit train min/max; write tensors. owns M1–M4
  3. P3 DataLoaders — feed \(x_S\), \(H\), \(x\) in batches.
  4. P4 Model — Mode A MLP (d→64→1), Mode B Stage-1 logistic; Stage-2 = load deployed MLP(H).
  5. P5 Train — fit with pos_weight; run ablations (perm-only / header-only / fused).
  6. P6 Evaluate — accuracy/F1/AUC on 2022–23; calibrate \(t_{low},t_{high}\) on val; report exit rate.
  7. P7 Export — Mode A onnx + Stage-1 onnx + copy of deployed MLP(H) + vocab + normalization_header.json.
  8. P8 Parity — PyTorch vs ONNX scores agree within 1e-4.

On-device — Android (A1–A4)

  1. A1 Extractor — Java builds the same \(x_S\) and \(H\), using the shipped vocab + the same min/max file.
  2. A2 Inference — ONNX Runtime runs Mode A, or Mode B (Stage 1 → maybe Stage 2).
  3. A3 Orchestration — log parse/dex/vectorize/inference time + scores; record if the dex read was skipped.
  4. A4 Parity test — device scores match Python within 1e-4 before release.
🖥️ Python: train + export ONNX
📦 export bundlemode_a · mode_b · vocab · normalization_header.json · parity_samples
📱 Android app: scan APKs on-device
Golden rule (M9): if the Java \(H\) uses different min/max than Python, your offline accuracy is meaningless. Ship one normalization_header.json and have both sides load it. For Mode B Stage 2, use the deployed MLP(H)'s own normalization (the stats it was trained with).

One-sentence takeaway: keep the few permissions that matter (MLDP), add the cheap "code shape" fingerprint (Dex header), and either fuse them into one tiny network (Mode A) or check permissions first and only X-ray the dex when unsure (Mode B) — fast enough for any phone, and Mode B even reuses a model you already shipped.
