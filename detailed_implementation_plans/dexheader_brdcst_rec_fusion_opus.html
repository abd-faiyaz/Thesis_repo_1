Prerequisites (beginner)

Dex header (112 bytes): every classes*.dex starts with an 8-byte magic (dex\n035\0, also 037/038/039) followed by 104 bytes encoding checksum, SHA-1 signature, and the section sizes/offsets (strings, types, methods, classes, data). Packing and multidex anomalies perturb these numbers before any string or manifest field is read.

Header tower \(\text{MLP}(H)\): the deployed Base-Model-1 net 104→128→128→1 (Linear+BatchNorm+ReLU per block, sigmoid head). For fusion we keep its 104→128→128 trunk and use the 128-d activation as an embedding.

Statically-registered broadcast receiver (system action): a <receiver> in the manifest whose <intent-filter><action> names a built-in Android event (e.g. android.intent.action.BOOT_COMPLETED). The OS can invoke it even when the app is not running — exactly why malware uses them (#12).

Concatenation [a ‖ b]: place embedding a then b into one longer vector before a joint head — intermediate (embedding) fusion \(([\mathbf a\,\|\,\mathbf b])\).

1. Overview

On the thesis corpus (year split: 2020–2021 train / 2022–2023 test) we want a detector richer than the header-only MLP(H) but far lighter than a 4380-d manifest bag-of-words or a full bytecode scan. The hybrid runs two towers: a 104-d Dex-header tower (structural signal, MSFDroid) and a ~30–80-d broadcast receiver system-action tower (event-subscription signal, #12). Each tower produces an embedding; we concatenate the embeddings and a joint head emits a single malware probability. No permissions, no API strings, no raw tail bytes — the manifest parse is limited to <receiver> actions and the Dex read is header-only.

Correction M6: the original called this “late fusion”. Concatenating two embeddings and then learning a joint FC head is intermediate (embedding) fusion. True late fusion would train two classifiers and average/vote their scores. We keep the embedding-fusion design (it lets the head learn cross-modal conjunctions) and use the precise term.

2. Component A — Dex header feature \(\mathbf H\) (104-d) corrected

What it analyzes

Bytes 8–111 of each classes*.dex after magic verification — checksum, SHA-1 signature, link segment, map offset, and the ID-section sizes/offsets.

Why this input was chosen

The header reflects compiler/linker layout; packers and multidex anomalies perturb offsets and sizes before any readable string exists — a structural signal orthogonal to the manifest receivers.

Correction M1/M2/M3 — the normalization order was wrong. The original listed ÷255 → min–max → sum-pool and wrote \(\mathbf H=\sum_d\mathbf h^{(d)}\in[0,1]^{104}\). The deployed implementation (dex_header.py, multidex.py, normalization.py) does three ordered stages:
  1. ÷255 per dex → each byte to \([0,1]\): \(h^{(d)}_b=\text{byte}^{(d)}_b/255\).
  2. sum-pool across all valid classes*.dex → \(\mathbf H_{\text{raw}}\in[0,D_{\text{dex}}]^{104}\) (NOT \([0,1]\)).
  3. corpus min–max LAST using frozen train statistics → \(\mathbf H\in[0,1]^{104}\).
The min/max are fit once on the train split and shipped as normalization_header.json; the device loads the same file (parity — never recompute per-APK).

Step-by-Step Process

  1. Unzip APK; enumerate all classes*.dex (^classes(\d*)\.dex$, primary first).
  2. Verify the first 8 bytes are a valid Dex magic (dex\n035\0 / 037 / 038 / 039); on failure log and skip that dex.
  3. Read bytes 8–111 → raw uint8[104]; encode \(h^{(d)}_b=\text{byte}^{(d)}_b/255\).
  4. Sum-pool element-wise across all valid dex → \(\mathbf H_{\text{raw}}\).
  5. Then apply corpus min–max with frozen train mins/maxs → \(\mathbf H\in[0,1]^{104}\).

Mathematical Formulation

\[ h^{(d)}_b=\frac{\text{byte}^{(d)}_b}{255},\qquad \mathbf H_{\text{raw}}=\sum_{d=1}^{D_{\text{dex}}}\mathbf h^{(d)}\in[0,D_{\text{dex}}]^{104} \]

\[ \tilde H_j=\frac{H_{\text{raw},j}-\min^{\text{train}}_j}{\max^{\text{train}}_j-\min^{\text{train}}_j+\epsilon}\in[0,1],\qquad \mathbf H=\tilde{\mathbf H}\in[0,1]^{104} \]

  • \(\mathbf H\) — pooled, normalized header (104-d), the tower input
  • \(D_{\text{dex}}\) — number of valid dex files in the APK
  • \(\min^{\text{train}}_j,\max^{\text{train}}_j\) — per-dimension stats frozen on the train split
  • \(\epsilon\) — numerical stability (constant dimensions map to 0)

Architecture Flowchart

classes*.dex (each)
    │  bytes [8:112]  → 104 raw values (0–255)
    ▼  ÷255
 h^(d) ∈ [0,1]^104   (per dex)
    │  Σ over dex  (sum-pool)
    ▼
 H_raw ∈ [0, D_dex]^104
    │  corpus min–max  (frozen TRAIN stats, normalization_header.json)
    ▼
 H ∈ [0,1]^104

Output and how it connects to the next stage

Outputs \(\mathbf H\). Fed to the header tower (Component C).

Correction M10: the “O(1) in Dex size” claim is overstated — we still unzip and locate every dex; we read only the 112-byte header (no bytecode/entropy scan). Cheap and roughly constant per dex, not literally O(1) overall. Correction M11: multidex_mode defaults to sum (deployed); primary_only is the MSFDroid-faithful ablation, recorded in the export manifest.

3. Component B — Broadcast receiver system-action vector \(\mathbf R\) corrected

What it analyzes

The android:name of <action> elements under statically registered <receiver><intent-filter> in AndroidManifest.xml.

Why this input was chosen

Receivers capture when code runs without a user launch. #12 found 74% of malware vs 65% of benign declare a receiver, and 70% vs 46% declare one for a system action — that gap is the signal. Malware over-registers BOOT_COMPLETED, USER_PRESENT, PHONE_STATE, SMS_RECEIVED, NEW_OUTGOING_CALL.

Correction M4 — system actions only. The original said “collect all <action> names”. Mohsen 2017 is explicit: “we are only concerned with the receivers of the system actions. The set of system actions of Android OS releases are compiled in one file.” So \(\mathcal A\) must be built against a fixed allow-list of Android system broadcast actions (the android.intent.action.*, android.net.conn.*, android.provider.Telephony.*, … families), not custom/third-party strings. This matters for (a) faithfulness to #12 and (b) Python↔Java parity — the same system_actions.json is shipped to both. #12 saw malware use 28 distinct system actions vs benign 57, so \(R\approx 30\text{–}80\).

Step-by-Step Process

  1. Parse AndroidManifest.xml (binary XML decode).
  2. Enumerate every static <receiver> → child <intent-filter> → child <action android:name>.
  3. Filter to the Android system-action allow-list (drop custom actions).
  4. Build vocabulary \(\mathcal A\) from the train split system actions (\(R\approx 30\text{–}80\)); freeze ordered.
  5. Set \(R_k=1\) iff system action \(k\in\mathcal A\) present in a static receiver of this APK (set semantics — duplicates collapse to one bit).

Mathematical Formulation

\[ R_k = \begin{cases} 1 & \text{if } \text{action}_k \in \mathcal A\ \cap\ \text{StaticReceivers}(\text{APK}) \\ 0 & \text{otherwise} \end{cases},\qquad \mathbf R \in \{0,1\}^{R} \]

  • \(\mathcal A\) — train-frozen Android system-action vocabulary (∩ allow-list)
  • \(R=|\mathcal A|\) — receiver-action vocabulary size (~30–80)
  • \(R_k\) — binary presence bit for system action \(k\)

Architecture Flowchart

AndroidManifest.xml
    └─► <receiver>/<intent-filter>/<action> names
           └─► keep only Android system actions (allow-list ∩ train vocab A)
                  └─► R ∈ {0,1}^R   e.g. 1×50

Output and how it connects to the next stage

Outputs \(\mathbf R\). Fed to the receiver tower (Component D).

Why different from Pattern A/B BoW: ~30–80 dims vs ~4381 — same manifest-parse family as #12 but fused with the Dex header instead of permissions, and restricted to the system-action allow-list the paper actually used.

4. Component C — Header tower \(\text{MLP}(H)\) trunk → \(\mathbf z_H\) corrected

What it analyzes

The normalized header vector \(\mathbf H\in[0,1]^{104}\).

Why this input was chosen

Two FC blocks map the continuous structural layout into a 128-d embedding suited to fusion.

Correction M5 — match the deployed MLP(H). The original wrote a bespoke 104→h1→128 ReLU tower. The deployed Base-Model-1 (src/models/mlp_header.py) is precisely: 
Linear(104→128) → BatchNorm1d → ReLU      (block1)
Linear(128→128) → BatchNorm1d → ReLU      (block2)
Linear(128→1)   → Sigmoid                 (head — DROPPED for fusion)
For fusion, reuse the trunk (block1+block2) and take the 128-d activation as \(\mathbf z_H\); discard the standalone →1→σ head. You may warm-start the trunk from the shipped mlp_header weights, then fine-tune end-to-end with the fusion head.

Mathematical Formulation

\[ \mathbf z_H=\text{ReLU}\big(\text{BN}_2(\mathbf W_{H2}\,\text{ReLU}(\text{BN}_1(\mathbf W_{H1}\mathbf H+\mathbf b_{H1}))+\mathbf b_{H2})\big)\in\mathbb R^{128} \]

  • \(\mathbf z_H\) — header-branch embedding (128-d penultimate activation)
  • \(\mathbf W_{H1},\mathbf W_{H2}\) — learned weight matrices; \(\text{BN}_i\) batch norm

Architecture Flowchart

H (1×104)
  ▼  Linear 104→128 · BN · ReLU
  ▼  Linear 128→128 · BN · ReLU
z_H (1×128)        [deployed →1→σ head removed for fusion]

Output and how it connects to the next stage

Outputs \(\mathbf z_H\). Concatenated with \(\mathbf z_R\) in the fusion head.

Key advantage: proven, cheap MSFDroid stream; reusing the deployed trunk gives a strong warm start and a guaranteed parity baseline for the header branch.

5. Component D — Receiver tower → \(\mathbf z_R\) faithful

What it analyzes

The sparse binary receiver vector \(\mathbf R\in\{0,1\}^{R}\).

Why this input was chosen

Sparse binary inputs need only a shallow map to embedding space before fusion.

Step-by-Step Process

  1. Linear(\(R\) → \(d_R\)) + ReLU (optionally BN), or a tiny MLP \(R\to 32\to d_R\).
  2. Output \(\mathbf z_R\in\mathbb R^{d_R}\), \(d_R\approx 32\text{–}64\).

Mathematical Formulation

\[ \mathbf z_R=\text{ReLU}(\mathbf W_R\mathbf R+\mathbf b_R)\in\mathbb R^{d_R},\qquad d_R\approx 32\text{–}64 \]

  • \(\mathbf z_R\) — receiver-branch embedding
  • \(d_R\) — receiver embedding dimension
Correction M7 — branch balance. Keep \(d_R\approx32\text{–}64\) (not necessarily 64). With a 128-d header embedding, a too-large receiver embedding is unnecessary and a too-small one is fine because \(\mathbf R\) is low-rank; pick \(d_R\) on validation so neither branch dominates the joint head.

Architecture Flowchart

R (1×R)  e.g. 1×50
  ▼  Linear R→d_R · ReLU
z_R (1×d_R)   e.g. 1×64

Output and how it connects to the next stage

Outputs \(\mathbf z_R\). Concatenated with \(\mathbf z_H\) in the fusion head.

Key advantage: captures the event-driven persistence/interception behavior #12 showed is complementary to structural features — without a 4380-d BoW.

6. Fusion mechanism (embedding fusion) retermed

What it analyzes

The two embeddings \(\mathbf z_H\) (structural) and \(\mathbf z_R\) (manifest behavioral).

Why

Each tower applies its own inductive bias (BN-MLP for continuous header bytes; shallow net for sparse binary actions) before a joint decision. Concatenation lets the head learn cross-modal conjunctions like “odd header layout AND BOOT_COMPLETED receiver”.

Step-by-Step Process

  1. Compute \(\mathbf H\) and \(\mathbf R\) from the APK.
  2. Forward \(\mathbf H\) through the header trunk → \(\mathbf z_H\) (128-d).
  3. Forward \(\mathbf R\) through the receiver tower → \(\mathbf z_R\) (\(d_R\)-d).
  4. Concatenate \(\mathbf z=[\mathbf z_H\,\|\,\mathbf z_R]\in\mathbb R^{128+d_R}\).
  5. Joint FC head \((128{+}d_R)\to 64\to 1\) + sigmoid → \(\hat y\).

Mathematical Formulation

\[ \mathbf z=[\mathbf z_H\,\|\,\mathbf z_R]\in\mathbb R^{128+d_R},\qquad \hat y=\sigma\big(\mathbf w_2^\top\,\text{ReLU}(\mathbf W_1\mathbf z+\mathbf b_1)+b_2\big) \]

Trained with class-weighted BCE (Correction M8):

\[ \mathcal L=-\big[\,w_+\,y\log\hat y+(1-y)\log(1-\hat y)\,\big],\qquad w_+=\frac{N_{\text{neg}}}{N_{\text{pos}}} \]

  • \(\mathbf z\) — fused embedding (e.g. 192-d if \(d_R=64\))
  • \(\hat y\) — malware probability \(\in[0,1]\)
  • \(w_+\) — positive-class weight for imbalance
Correction M7: the original used a bare linear \(\hat y=\sigma(\mathbf w^\top\mathbf z+b)\). A one-hidden-layer FC head \((128{+}d_R)\to64\to1\) recovers the nonlinear conjunctions that a single linear layer cannot — at negligible ONNX cost. A bare linear remains the smallest fallback.

                                 │
                                 ▼
                 z = [z_H ‖ z_R]  (1×(128+d_R))   e.g. 1×192
                                 ▼

                                 ▼

Output and how it connects to the next stage

Single malware score for the ensemble / multistep policy. Can run as a Step-2 detector after a cheaper manifest gate when uncertain.
