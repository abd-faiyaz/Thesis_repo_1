ELI5: Imagine a security guard who only looks at an app's "permission slip" (what doors it asked for) and its "alarm subscriptions" (which building events it wants to be paged about). Malware tends to ask for suspicious doors and page itself on sneaky events like "phone just booted." We tick checkboxes for both lists, glue them into one row, and a small calculator says how suspicious it looks.

Prerequisites — plain-English concepts

What is the AndroidManifest?

Every Android app ships a manifest: a declaration of permissions it wants, components it has (activities, services, receivers), and more. We never run the app — we just read this declaration. That is static analysis: cheap, fast, safe.

What is a "permission"?

ELI5: A permission is a door key the app requests, e.g. SEND_SMS (send texts) or CAMERA. More dangerous keys = more risk if the app is bad.

What is a "broadcast receiver (system action)"?

Android constantly broadcasts events: "phone finished booting", "an SMS arrived", "screen unlocked". An app can register a statically registered receiver in the manifest to be launched even when it is not running. The specific event it listens for is the action (e.g. android.intent.action.BOOT_COMPLETED).

Key paper-faithful detail: Paper #12 only counts system actions (a fixed Android list), not random custom strings. Malware loves BOOT_COMPLETED, USER_PRESENT, SMS_RECEIVED because they let it run silently.

What is a binary feature vector?

A row of 0/1 checkboxes. Position j = 1 means "this app has feature j". Example with 4 permission slots + 3 receiver slots:

What is "MLDP"?

ELI5: Android has ~135 permissions. Most are useless for spotting malware (almost everyone asks for INTERNET). MLDP = Multi-Level Data Pruning: a filtering funnel that throws away the useless permissions and keeps ~22 that actually separate good from bad apps.

What is a tiny MLP?

A Multi-Layer Perceptron: a mini neural network. Ours is d → 64 → 1 — one hidden layer of 64 neurons, then a single output squashed to a probability. It is small enough (<20 KB) to run on a phone in under a millisecond.

① MLDP permission sub-vector (from Paper #7)

Goal: turn the manifest's permissions into a short, clean checkbox row using only the ~22 permissions that matter. The "which 22?" is decided once, offline, on the training apps, then frozen.

The pruning funnel (Variant 1: PRNR → SPR → PMAR)

135 permissions — everything Android offers
≈ 95 — after PRNR (drop the ones used equally by good & bad apps)
≈ 25 — after SPR (keep the most frequently-used survivors)
≈ 22 — after PMAR (merge permissions that always travel together)

Step 1 — PRNR (Permission Ranking with Negative Rate)

For each permission we measure how "lopsided" it is between malware and benign apps. Let \(S_M(P_j)\) and \(S_B(P_j)\) be the fraction of malware / benign apps that declare permission \(P_j\) (after correcting for class-size imbalance). Then:

\[ R(P_j)=\frac{S_M(P_j)-S_B(P_j)}{S_M(P_j)+S_B(P_j)}\in[-1,1] \]

R → +1malware-only
e.g. SEND_SMS
R ≈ 0used by both
→ DROP
R → −1benign-only
Correction we made (M4): the original rough plan said PRNR "keeps malware-skewed permissions". Actually it keeps both ends (\(R\to+1\) and \(R\to-1\)) because a strongly-benign permission is just as useful for telling the two apart. Only the middle (\(R\approx 0\)) is dropped.

Step 2 — SPR (Support-based Permission Ranking)

Among the survivors, keep the ones that appear often enough to be statistically reliable (drop ultra-rare permissions). ~95 → ~25.

Step 3 — PMAR (Permission Mining with Association Rules)

Some permissions are redundant twins — e.g. WRITE_SMS nearly always appears with READ_SMS. Using the Apriori algorithm (confidence ≥ 96.5%, support ≥ 10%), we collapse such pairs to one. ~25 → ~22. This frozen set is \(\mathcal S\).

At inference (per new app)

\[ x^{(S)}_j=\begin{cases}1 & \text{if }P_j\in\mathcal S\text{ and declared}\\ 0&\text{otherwise}\end{cases},\qquad \mathbf x^{(S)}\in\{0,1\}^{|\mathcal S|},\ |\mathcal S|\approx 22 \]

Correction (M1 / M2): the size is ~16–25 (≈22), not "20–40". And we use the deterministic PRNR→SPR→PMAR funnel (paper Table I = 22 perms) rather than the harder-to-reproduce PCA/Kaiser variant the paper also describes.

Correction (M3): the original plan collected all action strings. Paper #12 is explicit — only system actions (a compiled Android list) count. We ship that exact list (system_actions.json) to both the Python trainer and the Android app so they always agree.

The math

\[ x^{(R)}_k=\begin{cases}1 & \text{if action}_k\in\mathcal A\ \cap\ \text{StaticReceivers(APK)}\\ 0 & \text{otherwise}\end{cases} \]

where \(\mathcal A\) is the system-action vocabulary frozen from training apps.

Why this helps: In paper #12, 70% of malware vs 46% of benign apps registered a receiver for a system event. Malware wants to wake up on BOOT_COMPLETED (survive reboots) or SMS_RECEIVED (intercept texts). That timing behavior is invisible to permissions alone.

③ Early fusion — glue the two rows together

We simply place the receiver row right after the permission row to make one longer row. This is called early fusion (fuse the features, then classify once) — the opposite of late fusion (classify twice, then average).

Correction (M5): with \(|\mathcal S|\approx22\) and \(R\approx30\text{–}80\), the fused width is \(d\approx52\text{–}102\) — round to 50–100, not "80–120".
Why early fusion? A single classifier can now learn a combo rule like "SEND_SMS permission AND SMS_RECEIVED receiver = very suspicious" inside one set of weights. Paper #12's best result came exactly from this combined vector.

④ Classifier — the tiny MLP

x (1 × d)e.g. 1 × 72
Linear d → 64W₁ x + b₁
ReLUmax(0, ·) — adds nonlinearity
Linear 64 → 1w₂ᵀh + b₂
σ (sigmoid) → P(malware)

The math

\[ \mathbf h=\max(0,\ \mathbf W_1\mathbf x+\mathbf b_1),\qquad \hat y=\sigma(\mathbf w_2^\top\mathbf h+b_2),\qquad \sigma(z)=\frac{1}{1+e^{-z}} \]

Training minimizes weighted binary cross-entropy (the weight \(w_+\) fixes the fact that there are usually far more benign apps than malware):

\[ \mathcal L=-\big[\,w_+\,y\log\hat y+(1-y)\log(1-\hat y)\,\big],\qquad w_+=\frac{N_\text{neg}}{N_\text{pos}} \]

Correction (M7): the rough plan never mentioned imbalance. Both papers handle it — Mohsen subsampled benign apps to a 50/50 mix; #7 rescaled supports. We use the pos_weight term above.

The paper-faithful baseline you should also run M6

Both papers actually used a Support Vector Machine with an RBF kernel, not a neural net:

\[ f(\mathbf x)=\operatorname{sign}\!\Big(\sum_{i\in SV}\alpha_i y_i\,K(\mathbf x_i,\mathbf x)+b\Big),\qquad K(\mathbf x,\mathbf x')=e^{-\gamma\|\mathbf x-\mathbf x'\|^2} \]

ELI5 of the kernel: an RBF kernel measures "how similar are two apps' checkbox rows?" and draws a curvy boundary between good and bad. Paper #12 found the best settings at \(\gamma=0.1,\ C=10\). We keep this as an offline yardstick, but ship the MLP because it converts cleanly to ONNX for the phone.

From paper to phone — the build pipeline (P1 → A4)

Two code bases cooperate: a Python project trains and exports; the Android app scans on-device. They must agree on features exactly (that's what the parity checks guard).

Offline — Python (P1–P8)

  1. P1 Index — list every APK with label, year; split train=2020–21, test=2022–23.
  2. P2 Features — parse manifests; run MLDP funnel → freeze \(\mathcal S\); build system-action vocab \(\mathcal A\); write 0/1 tensors. owns M1–M4
  3. P3 DataLoaders — feed tensors in batches.
  4. P4 Model — define tiny MLP (+ SVM baseline).
  5. P5 Train — fit on train split with pos_weight; run 3 ablations (perm-only / receiver-only / fused).
  6. P6 Evaluate — accuracy/F1/AUC on the 2022–23 test set only.
  7. P7 Export — write model.onnx + vocabs + system_actions.json bundle.
  8. P8 Parity — PyTorch vs ONNX scores agree within 1e-4.

On-device — Android (A1–A4)

  1. A1 Extractor — Java reads the manifest and builds the same 0/1 vector, using the same shipped vocab + system-action list.
  2. A2 Inference — ONNX Runtime runs model.onnx, reads malware_prob, applies threshold.
  3. A3 Orchestration — log parse/vectorize/inference time + score per scan.
  4. A4 Parity test — device scores match the Python reference within 1e-4 before release.
🖥️ Python: train + export ONNX
📦 export bundlemodel.onnx · vocabs · system_actions.json · parity_samples
📱 Android app: scan APKs on-device
Golden rule: if the Java feature vector differs from Python's by even one bit, the accuracy you reported offline is meaningless. The shared system_actions.json + frozen vocab order + float32 0/1 encoding + parity tests (P8/A4) exist to prevent that.

Be honest in the thesis (M9): Paper #12's famous "97%" is on duplicate configurations where train and test share identical rows. On a fresh, newer dataset it dropped to ~76–77%. Our temporal 2022–23 test is the "fresh data" case, so expect realistic numbers (~75–90%), and sell the model on its tiny size + strong size-to-accuracy ratio, not a headline 97%.
One-sentence takeaway: keep the few permissions that actually matter (MLDP), add the sneaky wake-up events malware loves (system-action receivers), glue them, and let a sub-20-KB network decide — fast enough for any phone, faithful to both source papers.
