The big picture in one diagram

The model reads two cheap things from the APK — the first 112 bytes of each classes*.dex (the header) and the <receiver> entries in AndroidManifest.xml — turns each into numbers, runs each through its own little network ("tower"), glues the two results together, and a final head outputs a malware probability. No bytecode is ever executed or fully scanned.

ELI5: Two experts look at the same suspicious app. One is a structural engineer who only studies the building's blueprint dimensions (the Dex header). The other is a behaviour analyst who only asks "what alarms does this thing react to?" (the receivers — boot, SMS, calls). Each writes a short summary. A manager reads both summaries together and makes the final call. Neither expert alone is as good as both combined.

Prerequisites — plain-English concepts

What is an APK?

An Android app ships as a .apk file, which is just a ZIP. Inside are the compiled code (classes*.dex) and a manifest (AndroidManifest.xml). We never run the app — we just read these files. That's static analysis: cheap, fast, safe.

What is a "Dex header"?

Your app's compiled code lives in classes.dex files. Each begins with a fixed 112-byte header: the first 8 bytes are a "magic" signature, and the next 104 bytes are numbers describing the code's structure (how many strings, where each section starts, total size…).

Why it helps: malware often has a weird code layout (huge string pools, odd offsets, packers). The header reveals that "shape" instantly — even if the manifest looks innocent.

What is a "broadcast receiver"?

A broadcast receiver is a hook that runs code when a system event fires — phone booted, SMS arrived, a call started. When it is declared statically in the manifest (<receiver>), Android can wake the app even when it isn't running.

ELI5: Think of receivers as tripwires the app sets. A flashlight app tripwired to "SMS received" and "phone booted" is suspicious; those tripwires are how spyware silently springs to life.

What is a "system action"?

Correction (M4): we only count system actions — the official Android event names like android.intent.action.BOOT_COMPLETED. Paper #12 is explicit: it compiles all Android-OS broadcast actions into one allow-list and ignores custom/app-specific actions. The rough plan said "all <action> names" — we restrict to the allow-list, and we ship the same system_actions.json to both the trainer and the phone so they always agree.

What is a "tower" and "fusion"?

A tower is a small neural network branch dedicated to one input type. Fusion means combining the towers' outputs. Here we use embedding fusion: each tower turns its input into a short list of numbers (an "embedding"), we glue the two lists end-to-end, and a final mini-network reads the combined list.

Correction (M6): the rough plan called this "late fusion". Strictly, "late fusion" means training two separate classifiers and averaging their scores. We instead glue the two embeddings before a single head — that's intermediate / embedding fusion, which lets the head learn combinations like "weird header AND boot receiver".

① Dex header row (MSFDroid / deployed MLP(H))

Goal: turn each classes*.dex header into 104 numbers, combine multidex files, and scale to [0,1]. This is exactly what the already-deployed MLP(H) model eats.

Three ordered steps M1

bytes 8–111 of each dex104 raw bytes (0–255)
① ÷ 255each byte → [0,1]
② sum-pool across classes*.dexHraw ∈ [0, D] (D = #dex)
③ corpus min–max (frozen train stats)H ∈ [0,1]104
Correction (M1 / M2): the rough plan listed the steps as "÷255 → min–max → sum-pool" and wrote \(\mathbf H=\sum_d\mathbf h^{(d)}\in[0,1]^{104}\). Order matters! The deployed code sums first, so after summing \(D\) files the values can exceed 1 (range \([0,D]\)). The min–max comes LAST, using fixed mins/maxs measured once on the training set — never recomputed on a single phone APK (that would break parity, M3).

The math

\[ h^{(d)}_b=\frac{\text{byte}^{(d)}_b}{255},\qquad \mathbf H_{\text{raw}}=\sum_{d=1}^{D_{\text{dex}}}\mathbf h^{(d)}\in[0,D_{\text{dex}}]^{104} \]

\[ \mathbf H=\frac{\mathbf H_{\text{raw}}-\boldsymbol{\min}_{\text{train}}}{\boldsymbol{\max}_{\text{train}}-\boldsymbol{\min}_{\text{train}}}\in[0,1]^{104} \]

ELI5 of multidex sum-pool: big apps split their code into classes.dex, classes2.dex, … We add up each file's header numbers position-by-position so one combined row represents the whole app. (The original MSFDroid paper used only the first dex; our deployed code sums them — we keep "first only" as an optional comparison, M11.)
Correction (M10): "header read is O(1)" is too strong — we still unzip and locate every dex. But we only read the 112-byte header of each (no bytecode scan), so it stays very cheap.

② Broadcast receiver row (from Paper #12)

Goal: turn the manifest's static receiver events into a short checkbox row, using only the system actions in our frozen allow-list \(\mathcal A\) (~30–80 of them, decided once on the training apps).

AndroidManifest.xml<receiver>/<intent-filter>/<action>
keep only Android system actions∩ system_actions.json allow-list (M4)
set a 1 for each present actionR ∈ {0,1}R

What the row looks like

BOOTSMSUSER_PRESENTCONNECTIVITYTIME_SET
1 = the app statically listens for that system event, 0 = it doesn't

The math

\[ R_k=\begin{cases}1 & \text{if action}_k\in\mathcal A\ \cap\ \text{StaticReceivers}(\text{APK})\\ 0&\text{otherwise}\end{cases},\qquad \mathbf R\in\{0,1\}^{R} \]

Why it works (from #12's data): 74% of malware vs 65% of benign declare a receiver; 70% vs 46% declare one for a system event. Malware's favourite events are BOOT_COMPLETED, USER_PRESENT, PHONE_STATE, SMS_RECEIVED, NEW_OUTGOING_CALL — the privacy-sensitive ones. Benign apps lean on package install/update events instead.
Honest caveat (M9): receivers alone are a weak detector — #12 reports ~76–79% on its own test and ~71–72% on newer apps. Their value is complementary: they catch event-driven behaviour the header can't see.

Correction (M5): the rough plan invented a generic 104→h1→128 tower. We instead reuse the exact deployed MLP(H) trunk (104→128→128 with BatchNorm), take the 128-d activation as zH, and drop its final →1→sigmoid head (we don't need a per-branch decision, just an embedding). We can even warm-start from the shipped weights.

Receiver tower

Correction (M7): keep dR ≈ 32–64 so the 104-byte structural side doesn't swamp the sparse receiver side. The receiver vector is mostly zeros, so a small embedding is plenty — pick the size on a validation set.
ELI5 of an embedding: a tower squeezes its raw input into a short list of learned "summary numbers". Two very different inputs (104 header bytes vs a sparse on/off receiver row) both become fixed-length lists that the final head can compare and combine fairly.

Correction (M7): the rough plan used a single bare linear layer on z. A one-hidden-layer head (128+dR)→64→1 can learn nonlinear "this AND that" combinations a bare linear cannot — at almost no size cost. Bare linear stays as the smallest fallback.
Training detail (M8): malware and benign counts are unequal, so we weight the loss with \(w_+=N_{\text{neg}}/N_{\text{pos}}\) so the model doesn't just predict the majority class.

From paper to phone — the build pipeline (P0 → A4)

Two code bases cooperate: a Python project trains and exports; the Android app scans on-device. They must agree on features exactly — that's what the parity checks guard.

Offline — Python (P0–P8)

  1. P0 Config — paths, hyperparams, requirements.txt, verify_setup.py.
  2. P1 Index — list every APK with label, year; split train=2020–21, test=2022–23.
  3. P2 Features — read dex headers (÷255 → sum-pool → fit train min/max); parse manifests → freeze receiver vocab \(\mathcal A\) ∩ allow-list; write tensors. owns M1–M4
  4. P3 DataLoaders — feed \(H\) and \(R\) in batches (kept separate — two inputs).
  5. P4 Model — header trunk (warm-start MLP(H)) + receiver tower + fusion head.
  6. P5 Train — fit with pos_weight; run ablations (header-only / receiver-only / fused).
  7. P6 Evaluate — accuracy/F1/AUC on 2022–23; honest temporal numbers.
  8. P7 Export — two-input ONNX + receiver vocab + system_actions.json + normalization_header.json + parity samples.
  9. P8 Parity — PyTorch vs ONNX scores agree within 1e-4.

On-device — Android (A1–A4)

  1. A1 Extractor — Java builds the same \(H\) (same min/max file) and \(R\) (same allow-list + vocab).
  2. A2 Inference — ONNX Runtime feeds two inputs (dex_header, receiver) → score.
  3. A3 Orchestration — log dex/parse/vectorize/inference time + score per scan.
  4. A4 Parity test — device scores match Python within 1e-4 before release.
🖥️ Python: train + export ONNX
📦 export bundlemodel.onnx · receiver_action_vocab.json · system_actions.json · normalization_header.json · parity_samples
📱 Android app: scan APKs on-device
Golden rule (M3/M4): if the Java side uses a different min/max than Python (header) or a different action allow-list (receivers), your offline accuracy is meaningless. Ship one normalization_header.json and one system_actions.json; both sides load the exact same files.

One-sentence takeaway: read the cheap "code shape" fingerprint (Dex header) and the cheap "what wakes this app" fingerprint (system-action receivers), give each its own tower, fuse the two summaries, and a tiny head outputs one malware score — small and fast enough for any phone, and the header tower even reuses a model you already shipped.
