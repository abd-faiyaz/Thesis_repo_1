1. Metrics collected per APK during scan

Each .apk in /sdcard/Download/ produces one JSON object appended to getExternalFilesDir(null)/metrics/all_scan_metrics.json inside the scans[] array. Written by MetricsWriter.writeScan().

1a. Scan metadata (top-level fields)

JSON field Type Source / meaning
scan_id string (UUID) Unique ID per APK scan
timestamp_ms integer System.currentTimeMillis() when metrics are written
device.model string Build.MODEL (e.g. POCO F3)
device.manufacturer string Build.MANUFACTURER
device.api integer Android API level (Build.VERSION.SDK_INT)
apk.name string APK filename in Download/
apk.path string Absolute path on device
apk.size_bytes integer File length on disk
apk.sha256_short string (8 hex chars) First 4 bytes of SHA-256 of name:size_bytes (not full APK hash)
trigger string manual (Start Scan button) or download (broadcast receiver)
stages[] array Per-model results — see table below
ensemble.score float (0–1) Weighted blend of XGBoost + 1D-CNN only
ensemble.decision string malware if score ≥ 0.5, else benign
ensemble.policy string Always weighted_validation_accuracy today
totals object Scan-level resource totals — see section 2

1b. Per-model metrics in stages[]

Up to 8 model pipelines run per APK (if assets load successfully). Each stage entry shares the same field schema. Stages for thesis models are omitted when inference fails (score < 0). Legacy XGBoost and 1D-CNN are always written even on failure.

Stage field Meaning Timer / source
domain Canonical feature domain ID Hardcoded per runner
model_id Canonical model bundle ID Only set for broadcast_mldp_hybrid today; absent for other thesis models
parse_ms Feature extraction / APK parsing time SystemClock.elapsedRealtimeNanos()
vectorize_ms Vectorization / normalization time Same clock; 0 for 1D-CNN (no separate vectorize step)
inference_ms ONNX Runtime inference time Same clock, around session.run()
score Malware probability (0 = benign, 1 = malware) ONNX output (softmax or sigmoid per model)
mem_delta_bytes Native heap change during stage Debug.getNativeHeapAllocatedSize() before/after

Per-model breakdown (what each pipeline logs)

manifest_xgb (none) ZIP open, manifest parse, all classes*.dex token scan Build 2500-d binary feature vector (OR across DEX files) XGBoost ONNX on aggregated vector Estimated: 50% of combined XGB+CNN total delta
bytecnn (none) Read last 1024 APK bytes (+ zero-pad) Always 0 1D-CNN ONNX softmax (malware class) Estimated: other 50% of combined XGB+CNN total delta

Ensemble vs stages: All 8 models write scores to stages[], but ensemble.score / ensemble.decision use only XGBoost + 1D-CNN (weights: acc_xgb = 0.9748, acc_cnn = 0.9607843). Thesis models do not affect the verdict.

2. Metrics collected for the full scan (batch)

Pressing Start APK Scan iterates over every .apk in Download/ sequentially. There is no separate batch/session record in the JSON file — only one object per APK.

2a. What exists at file / batch level

What Collected? Details
Root device block in all_scan_metrics.json Yes Written once on first scan; phone model, manufacturer, API level
scans[] array growth Yes Each APK appends one entry; file accumulates across multiple button presses
Batch session_id No No way to group APKs from a single button press
Batch start / end timestamp No Only per-APK timestamp_ms
Total APKs scanned in run No Not written to JSON; visible only in app log
Batch wall time (whole button press) No Not recorded
Batch CPU time No Not recorded
Batch memory peak / delta No Not recorded
Battery % at start / end of batch No Placeholder battery_pct_delta: null per APK only; never populated
Per-APK UI table row Yes (in-app only) APK name, ensemble verdict, total_ms, total_mem_mb — not persisted as batch summary

2b. Per-APK totals block (labeled “scan-level” in code)

These fields are written per APK under totals. They are not aggregated across the full batch, but they represent the closest thing to “whole APK scan” resource usage.

JSON field Source Scope / caveat
totals.wall_ms SystemClock.elapsedRealtimeNanos() Covers XGB + CNN + Broadcast+MLDP + BM1 only — timers stop before Pattern A, Pattern B, LinReg, MLDP pruned run
totals.cpu_ms Debug.threadCpuTimeNanos() (scan thread) Same partial window as wall_ms; no per-stage CPU anywhere
totals.mem_delta_bytes Debug.getNativeHeapAllocatedSize() delta Same partial window; native heap only (not Java heap, not RSS)
totals.total_dex_files_found Count during XGBoost DEX discovery XGBoost pipeline only
totals.structural_parsing_time_ms Wall time for XGBoost ZIP/manifest/DEX parse XGBoost pipeline only
totals.battery_pct_delta — Always null (not implemented)
UI vs JSON mismatch: The results table shows total_ms and total_mem_mb from the same partial timing window (pre–Pattern A/B/LinReg/MLDP). If all 8 models loaded, actual per-APK cost is higher than what totals and the UI report.

3. Planned model cascade (thesis Task 2)

Not implemented today. The app currently runs all loaded models sequentially on every APK. The tier layout below is the recommended multistep policy from todo_model_ranks.html (usability rank) and opus_suggested_models.md (extract cost + cascade notes). It matches rough_model_explanations/mldp_dex_header_cascade.html and Phase 8 in why_pipeline.md.

3a. Cascade exit rule

ConditionAction
Score < t_low Confident benign → stop, record early exit
Score > t_high Confident malware → stop, record early exit
t_low ≤ score ≤ t_high Uncertain → escalate to next tier

Thresholds t_low / t_high are calibrated on a train-holdout validation set (not hard-coded). Goal: cheap models clear most APKs before expensive parsers run.

4. Current limitations & suggested fixes

  1. Battery not collected (per APK or per batch) totals.battery_pct_delta is hard-coded to null in MetricsWriter.java. No BatteryManager usage exists.
    Suggested fix: Read BATTERY_PROPERTY_CAPACITY (or Intent.ACTION_BATTERY_CHANGED) at batch start and per APK before/after; write battery_pct_start, battery_pct_end, and battery_pct_delta. Add batch-level totals in a new session block.
  2. totals.wall_ms / cpu_ms / mem_delta_bytes exclude 4 models In ScanService.java, cpuEnd, memEnd, and wallEnd are captured at line ~284, but Pattern A, Pattern B, LinRegDroid, and MLDP pruned run afterward (lines ~325–454).
    Suggested fix: Move end-timer capture to after all model pipelines complete, immediately before writeScanMetrics().
  3. No per-stage CPU time Only wall time is split into parse_ms / vectorize_ms / inference_ms. totals.cpu_ms is scan-level only.
    Suggested fix: Wrap each stage with Debug.threadCpuTimeNanos() and add cpu_ms to each stages[] entry; extend device_scan.schema.json.
  4. XGBoost & 1D-CNN memory is estimated, not measured Total native heap delta is split 50/50 between the two legacy stages (xgbMemDelta = memDelta / 2).
    Suggested fix: Measure before/after around each legacy pipeline individually, same as thesis models; or drop per-stage mem for XGB/CNN and only report scan-level total.
  5. Memory metric is native-heap only Uses Debug.getNativeHeapAllocatedSize() — misses Java heap, graphics, ONNX allocator behavior, and system-level RSS.
    Suggested fix: Also log Runtime.getRuntime().totalMemory() - freeMemory() and optionally Debug.getMemoryInfo() (dalvikPss, nativePss) for thesis resource profiling (Phase 10).
  6. No batch / session metrics A 400-APK eval run produces 400 separate JSON entries with no grouping, no batch duration, and no cumulative battery drain.
    Suggested fix: Generate a session_id per button press; write a sessions[] block with apk_count, wall_ms_total, battery_pct_delta, started_ms, ended_ms.
  7. Ensemble ignores 6 of 8 models Thesis models populate stages[] but do not affect ensemble.decision. Only XGBoost + 1D-CNN are fused.
    Suggested fix: Add assets/ensemble_policy.json with pluggable policies (legacy_xgb_cnn, weighted_all, cascade_mldp_header). Log ensemble.policy from config.
  8. Inconsistent model_id in stages[] Only broadcast_mldp_hybrid writes model_id. BM1, Pattern A/B, LinReg, and MLDP pruned write domain only despite ModelRegistry defining canonical IDs.
    Suggested fix: Pass model_id from ModelRegistry for every stage in writeScanMetrics().
  9. No model selection at scan time All loaded pipelines run on every APK. No UI toggle or intent extra to pick models.
    Suggested fix: Optional checkboxes or enabled_models[] in scan intent; needed for cascade experiments and fair per-model benchmarking.
  10. sha256_short is not a real APK hash Hash is SHA-256 of filename:size truncated to 8 hex chars — two different APKs with the same name and size would collide; renaming breaks identity.
    Suggested fix: Compute full-file SHA-256 (streamed read) once per scan; store as apk.sha256; keep short form as optional display field.
  11. Schema allows triggers not implemented device_scan.schema.json lists scheduled and install triggers, but only manual and download are used in code.
    Suggested fix: Either implement scheduled/install scan paths or narrow the schema enum to match reality.
  12. Metrics file rewrite on every APK (scalability) MetricsWriter reads the entire all_scan_metrics.json, parses it, appends one scan, and rewrites the full file — O(n²) for large eval runs.
    Suggested fix: Append newline-delimited JSON (JSONL) per scan, or write individual scan_{id}.json files and merge on pull to PC.
  13. Failed thesis models silently omitted from stages[] Stages with score < 0 are not written — you cannot distinguish “model skipped (asset missing)” from “ran but failed” in JSON.
    Suggested fix: Always emit a stage entry with status (ok / skipped / error) and optional error_message.
  14. UI shows only ensemble verdict, not per-model scores Results table columns: APK name, verdict, total time, total memory. Per-model scores appear only in the scrollable log and JSON export.
    Suggested fix: Expandable row per APK or a detail screen listing all stages[] scores and timings.
