How VigiDroid Works

End-to-end workflow for the VigiDroid Android malware scanner: from offline model training on a PC, through ONNX export and asset staging, to on-device scanning with a four-tier cascading pipeline. Updated for the current codebase (June 2026) after multi-model integration, app restructuring, and cascade deployment.

1. Overview

VigiDroid is an on-device Android APK scanner built for thesis evaluation. It runs multiple malware-detection models trained offline in Python, exported as ONNX bundles, and loaded at app startup. Each APK scan extracts static features from the APK zip, runs one or more ONNX models, and writes structured JSON metrics for thesis plots (accuracy vs latency, resource usage, cascade exit rates).

Two cooperating worlds

PC — training & calibration

APK corpus → feature extraction → PyTorch train → evaluate → ONNX export → parity check → cascade policy build.

Phone — scanning & metrics

Trigger scan → parse APK once → tier-by-tier cascade (or all-models ablation) → verdict + JSONL metrics → pull to PC for plots.

2. What changed since the initial version

The original workflow (documented in whats_going_on.pdf) described a single-model app: XGBoost manifest+DEX features plus a 1D-CNN on tail bytes, with a simple weighted ensemble verdict. Three major upgrades followed:

① Multi-model integration

Six thesis pipelines (MLDP, broadcast hybrid, BM1 header, Pattern A/B, LinRegDroid, MLDP+DEX cascade) were added following Pipeline_full_concept.html phases P0–P8 (PC) and A1–A4 (Android). Each model ships as assets/models/<model_id>/ with ONNX, thresholds, and parity samples.

② App restructuring

Per vigidroid_fix_plan_opus.md: parse-once FeatureContext, StageRunner + ModelRegistry, split JSONL metrics, real SHA-256 dedup, session records, battery sampling, and UI cascade toggle. The monolithic ScanService god-method was decomposed.

③ Cascading detection

Per cascading_fix_opus.md: every model now exports tuned_val plus t_low/t_high bands. ScanOrchestrator runs a four-tier early-exit policy driven by cascade_policy.json — cheap manifest gates first, heavy parsers last.

AspectInitial versionCurrent (2026-06)
Models per scan 2 (XGB + ByteCNN) Up to 11 in ablation mode; 2–8 in cascade mode (early exit)
Verdict policy Fixed XGB+CNN weighted blend Cascade tiers with calibrated bands, or legacy ablation ensemble
APK parsing Each model re-opened the ZIP Single FeatureContext.open() — manifest, DEX, tail bytes cached
Metrics file One JSON rewritten per APK Append-only JSONL (scan_a_all_models.jsonl / scan_b_cascade.jsonl)

Train/serve parity is mandatory. Java feature extractors must match Python preprocessing exactly. Every model ships parity_samples/; P8 (PC) and A4 (Android instrumented tests) verify scores within 1e-4. If features diverge, offline accuracy and on-device scores are not comparable.

Cascade calibration (after all models trained)

  1. Per-model bands — each pipeline runs calibrate_thresholds.py on val scores → t_low / t_high in thresholds.json.
  2. Val score collection — aligned val_scores.json per model copied to Shared_pipeline_Files/calibration/.
  3. Tier policy build — build_cascade_policy.py inner-joins val scores, calibrates per-tier bands, writes cascade_policy.json.
  4. Asset sync — bundles copied to vigidroid/app/src/main/assets/models/; policy to assets/cascade_policy.json.

7. Per-APK scan flow

1
Discover & open APK ScanService resolves target files, opens FeatureContext.open(apk)
2
Parse once (shared) Stream SHA-256, read tail bytes, open ZIP once, decode manifest, list & read all classes*.dex entries
3
Run detection pipeline Cascade: tier-by-tier with early exit. Ablation: all 11 models sequentially.
4
Assemble metrics & verdict ScanMetricsAssembler builds scan record with stages[], cascade{}, totals{}, battery snapshot
5
Persist & notify UI Append JSONL line, mark SHA-256 processed, broadcast result row to MainActivity

Real latency has two parts

TimerWhat it measuresTypical scale
totals.shared_parse_ms One-time FeatureContext open: ZIP, manifest decode, DEX listing, SHA-256, tail bytes ~100–250 ms (dominates for cheap models)
totals.wall_ms Model pipeline only (parse-once already done; per-stage times are vectorize + infer) ~5–500 ms depending on cascade exit tier

End-to-end ≈ shared_parse_ms + wall_ms. The UI results table shows wall_ms; tap a row for the full breakdown including shared parse.

8. Parse once — FeatureContext

Before restructuring, every model independently opened the APK ZIP and re-parsed the manifest — up to 6+ manifest decodes and 4+ DEX header reads per APK. FeatureContext eliminates that waste.

flowchart LR APK[APK file] --> SHA[SHA-256 stream] APK --> TAIL[Last 1024 bytes] APK --> ZIP[ZipFile open once] ZIP --> MAN[Manifest decode] MAN --> PERM[Permissions normalized] MAN --> HYB[Hybrid manifest features] MAN --> BOW[BoW tokens] MAN --> XGBTOK[XGB manifest tokens] ZIP --> DEX[All classes*.dex bytes] SHA & TAIL & PERM & HYB & BOW & XGBTOK & DEX --> CTX[FeatureContext cache] CTX --> M1[Tier 1 runners] CTX --> M2[Tier 2 runners] CTX --> M3[Tier 3 runners] CTX --> M4[ByteCNN]

Each ONNX runner's extractor reads from the cache instead of re-opening the file. Per-stage parse_ms then measures only model-specific vectorization — a fair comparison across models.

9. Two scan modes

The cascade toggle in MainActivity selects which runner ScanService uses. Metrics go to separate JSONL files so ablation and cascade runs don't mix.

Deployed

Cascade mode

ScanOrchestrator · scan_b_cascade.jsonl

  • Four-tier early-exit policy
  • Verdict from cascade score at exit tier
  • Typically 2–5 models run per APK
  • ~40% exit at Tier 1 on val set
  • Thesis "production" configuration
Ablation

All-models mode

LegacyScanRunner · scan_a_all_models.jsonl

  • All 11 stages run every APK
  • Verdict = XGB + ByteCNN weighted fusion (legacy)
  • Full per-model instrumentation
  • Used for model comparison & debugging
  • Higher latency, complete stage coverage

10. Cascading detection pipeline

The cascade runs models from cheapest to most expensive. At each tier, a combined score is compared against calibrated uncertain bands. Confident benign or malware scores stop immediately; uncertain scores escalate to the next tier.

Tier 1 — manifest-only gates
Tier 2 — DEX header escalation
Tier 3 — heavy structural parse
Tier 4 — late fusion

Exit rule (every tier)

ConditionAction
Score ≤ t_lowConfident benign → stop, record early exit
Score ≥ t_high (or any model ≥ its tuned_val when conservative OR enabled)Confident malware → stop
t_low < score < t_highUncertain → escalate to next tier

Tier → model mapping

TierModelsFeature costVal exit rate*
1 mldp_pruned_permission
broadcast_mldp_hybrid		 Manifest only (~20–120 dims) ~40% cumulative
2 mldp_dexheader_cascade_mode_b (→ mlp_header fallback) DEX header bytes 8–111 per DEX, sum-pooled ~41% cumulative

* From cascade_policy.json calibration on 764 aligned val APKs.

Nested early exit — Mode B cascade

Tier 2's mldp_dexheader_cascade_mode_b has its own two-stage logic: Stage 1 runs MLDP logistic on permissions only. If confident, it exits without reading DEX headers at all — a genuine latency win inside Tier 2.

Models not in the live cascade

These run in ablation mode only (instrumentation / comparison):

  • mldp_dexheader_cascade_mode_a — fused single-pass alternative to Mode B
  • dual_branch_dex_manifest — selectable as Tier 3 pattern via policy config
