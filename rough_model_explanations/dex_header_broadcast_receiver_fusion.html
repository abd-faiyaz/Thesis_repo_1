Dex Header + Broadcast Receiver Fusion

Cross-paper: MSFDroid (Dex header H, Peng et al. 2022) + Mohsen et al. 2017 (broadcast receiver intent actions)

Prerequisites

Dex header (104 bytes): After 8-byte magic (dex\n035), bytes 8–111 encode section sizes/offsets (strings, methods, classes). Malware often shows abnormal header statistics without readable manifest changes.

MSFDroid MLP(H): Normalize header bytes to \(\mathbf{H} \in [0,1]^{104}\); sum-pool across multidex; small MLP → 128-d embedding.

Broadcast receivers: Manifest <receiver> components with <action> tags — which system events wake the app (boot, SMS, connectivity).

Late fusion (Pattern B): Separate towers per modality → concat embeddings → final FC + sigmoid (MSFDroid Pattern B style, but BoW replaced by ~50-d receiver vector).

1. Overview

You need a detector richer than header-only MLP(H) (~83.5% ACC alone in MSFDroid Table 6) but lighter than 4380-d manifest BoW or ANASTASIA bytecode scan. This hybrid fuses 104-d Dex header (structural signal) with ~30–80-d broadcast receiver intent actions (event-subscription signal) using late fusion Pattern B: two small towers → concat embeddings → sigmoid. No permissions, no API strings, no raw tail bytes — manifest parse is limited to receivers; Dex read is header-only.

Component A — Dex header feature H (104-d)

What it analyzes

Bytes 8–111 of each classes*.dex file after magic verification (MSFDroid §3.3).

Why this input was chosen

Header reflects compiler/linker layout; malware packing and multidex anomalies perturb offsets/sizes before any string is read — complements manifest receivers.

Step-by-Step Process

  1. Unzip APK; enumerate all classes*.dex.
  2. Verify first 8 bytes match Dex magic.
  3. Read bytes 8–111 → raw vector \(\mathbf{h}^{( ext{dex})}\).
  4. Encode: \(h_b = ext{byte}_b / 255\).
  5. Min–max normalize each dimension using training corpus stats.
  6. Multidex: element-wise sum \(\mathbf{H} = \sum_{ ext{dex}} \mathbf{h}^{( ext{dex})}\).

Mathematical Formulation

\[ h_b = \frac{\text{byte}_b}{255}, \quad \mathbf{H} = \sum_{d=1}^{N_{\text{dex}}} \mathbf{h}^{(d)} \in [0,1]^{104} \]

Corpus normalization: \(\tilde{H}_j = \frac{H_j - \min_j}{\max_j - \min_j + \epsilon}\).

  • \(\mathbf{H}\) — pooled normalized header (104-d)
  • \(N_{\text{dex}}\) — number of dex files in APK
  • \(\epsilon\) — numerical stability in min–max

Output and how it connects to the next stage

Outputs \(\mathbf{H}\). Input to MLP(H) tower (Component C).

Key Advantage / Novelty

Key novelty: O(1) in Dex file size — only fixed header window, not full entropy scan (MLP(M) dropped in MSFDroid-lite).

Component B — Broadcast receiver actions R (~50-d)

What it analyzes

Intent android:name strings under <receiver><intent-filter><action> in manifest (Mohsen et al. 2017).

Why this input was chosen

Receivers capture when code runs without user launch — malware registers BOOT_COMPLETED, SMS_RECEIVED more aggressively than benign apps.

Step-by-Step Process

  1. Parse AndroidManifest.xml.
  2. Find all <receiver> elements.
  3. Collect <action android:name="…"> under each receiver's intent-filter.
  4. Build training vocabulary \(\mathcal{A}\) of distinct actions (\(R pprox 30\)–80).
  5. Set \(R_k = 1\) if action \(k\) present in APK, else 0.

Mathematical Formulation

\[ R_k = \begin{cases} 1 & \text{if } \text{action}_k \in \text{Receivers}(\text{APK}) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{R} \in \{0,1\}^{R} \]

  • \(R\) — receiver-action vocabulary size
  • \(R_k\) — binary bit for action \(k\)
  • \(\mathbf{R}\) — receiver feature vector (~50-d typical)

Architecture Flowchart

AndroidManifest.xml

            ▼
      R  (1×R)  binary  e.g. 1×50

Output and how it connects to the next stage

Outputs \(\mathbf{R}\). Input to receiver tower (Component D).

Key Advantage / Novelty

Why different from Pattern A BoW: ~50 dims vs 4381 — same manifest-parse family as Mohsen but fused with Dex header, not permissions.

Component C — MLP(H) tower (MSFDroid Base Model 1)

What it analyzes

Normalized header vector \(\mathbf{H} \in \mathbb{R}^{104}\).

Why this input was chosen

Two FC+ReLU blocks (paper Fig. 3) map structural layout to 128-d embedding suitable for fusion.

Step-by-Step Process

  1. Input \(\mathbf{H}\) shape (1×104).
  2. Layer 1: Linear(104 → \(h_1\)), ReLU (paper-style FC+BN+ReLU).
  3. Layer 2: Linear(\(h_1\) → 128), ReLU.
  4. Output embedding \(\mathbf{z}_H \in \mathbb{R}^{128}\).

Mathematical Formulation

\[ \mathbf{z}_H = \mathrm{ReLU}\big(\mathbf{W}_{H2}\,\mathrm{ReLU}(\mathbf{W}_{H1}\mathbf{H} + \mathbf{b}_{H1}) + \mathbf{b}_{H2}\big), \quad \mathbf{z}_H \in \mathbb{R}^{128} \]

  • \(\mathbf{z}_H\) — header branch embedding (128-d)
  • \(\mathbf{W}_{H1}, \mathbf{W}_{H2}\) — learned weight matrices

Architecture Flowchart

H  (1×104)
  │
  ▼
 FC → ReLU → FC → ReLU
  │
  ▼
 z_H  (1×128)

Output and how it connects to the next stage

Outputs \(\mathbf{z}_H\). Concatenated with \(\mathbf{z}_R\) in fusion (Component late fusion section).

Key Advantage / Novelty

Key advantage: Proven MSFDroid stream — cheap, no manifest lexicon explosion.

Component D — Receiver tower (linear or tiny MLP)

What it analyzes

Binary receiver vector \(\mathbf{R} \in \{0,1\}^{R}\).

Why this input was chosen

Sparse binary inputs need only a shallow map to embedding space before fusion.

Step-by-Step Process

  1. Option A: Linear(\(R\) → 64) + ReLU.
  2. Option B: MLP \(R\) → 32 → 64 with ReLU.
  3. Output \(\mathbf{z}_R \in \mathbb{R}^{64}\) (typical).

Mathematical Formulation

\[ \mathbf{z}_R = \mathrm{ReLU}(\mathbf{W}_R \mathbf{R} + \mathbf{b}_R), \quad \mathbf{z}_R \in \mathbb{R}^{d_R},\ d_R \approx 32\text{–}64 \]

  • \(\mathbf{z}_R\) — receiver branch embedding
  • \(d_R\) — receiver embedding dimension

Architecture Flowchart

  │
  ▼
 Linear/MLP  →  ReLU
  │
  ▼
 z_R  (1×64)

Output and how it connects to the next stage

Outputs \(\mathbf{z}_R\). Late-fused with \(\mathbf{z}_H\).

Key Advantage / Novelty

Key advantage: Captures event-driven malware behavior Mohsen showed improves over permissions alone — without 4380-d BoW.

6. Late fusion mechanism (Pattern B style)

What it analyzes

Embeddings \(\mathbf{z}_H\) (structural) and \(\mathbf{z}_R\) (manifest behavioral) from separate towers.

Why this input was chosen

Late fusion lets each modality use its own inductive bias — header MLP for continuous layout, shallow net for sparse binary actions — before joint decision. Matches MSFDroid Pattern B (separate ASCNN/MLP branches) but swaps manifest BoW for receivers.

Step-by-Step Process

  1. Compute \(\mathbf{H}\) and \(\mathbf{R}\) from APK.
  2. Forward through MLP(H) → \(\mathbf{z}_H\).
  3. Forward through receiver tower → \(\mathbf{z}_R\).
  4. Concatenate \(\mathbf{z} = [\mathbf{z}_H \| \mathbf{z}_R]\).
  5. Final FC + sigmoid → \(\hat{y}\).

Mathematical Formulation

\[ \mathbf{z} = [\mathbf{z}_H \| \mathbf{z}_R] \in \mathbb{R}^{128 + d_R}, \quad \hat{y} = \sigma(\mathbf{w}^T \mathbf{z} + b) \]

  • \(\mathbf{z}\) — fused embedding (e.g. 192-d if \(d_R=64\))
  • \(\hat{y}\) — malware probability

Architecture Flowchart

APK
 ├─► classes*.dex ──► H (1×104) ──► MLP(H) ──► z_H (1×128)
 │
 └─► Manifest receivers ──► R (1×50) ──► Tower ──► z_R (1×64)
                              │
                              └─► z = [z_H || z_R]  (1×192)
                                        │
                                        ▼
                                   FC + sigmoid
                                        │
                                        ▼
                                   P(malware)

Output and how it connects to the next stage

Single malware score for ensemble / multistep policy. Can run as Step 2 after MLDP+header cascade when uncertain.

Key Advantage / Novelty

vs Pattern B (MSFDroid): Replaces 4380-d manifest BoW with ~50-d receivers — ~90% smaller manifest branch, still adds behavioral manifest signal. vs MLP(H) only: Adds event-subscription semantics MSFDroid header cannot see.
