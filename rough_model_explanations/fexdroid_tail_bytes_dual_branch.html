FexDroid Sparse + Raw APK Tail Dual-Branch

Cross-paper: ICCAI 2018 FexDroid (category-pruned sparse ~3K–5K) + Hasegawa & Iyatomi 2018 (1D-CNN on last 1024 APK bytes)

Prerequisites

FexDroid / Drebin-style sparse features

Binary indicators for named artifacts: permissions, API calls, intents, components — grouped into 10 categories. Full Drebin >500K dims; FexDroid prunes to ~49K; thesis FexDroid-lite caps ~500 terms/category → 3K–5K. See fexdroid_category_sparse_classifier.html.

Raw APK tail bytes (ByteCNN / 1DCNN)

Read the last 1024 bytes of the APK file as integers 0–255. No unzip, no parsing. Packing, zip comment, and dex placement artifacts show up here. Your deployed 1DCNN model uses this domain.

Late fusion (Pattern B style)

Each branch has its own network → embedding vectors → concatenate → final FC layer. Branches see different input modalities.

Dual-branch vs early concat

Early concat would force one tower to mix 3K sparse bits with 1024 raw bytes — poor inductive bias. Late fusion keeps semantic ASCNN/MLP separate from convolutional byte learning.

1. Overview

Problem: Semantic-only detectors (permissions, API names) miss obfuscated packing and zip-level tricks; byte-only 1DCNN models (95–97% accuracy on Drebin/AMD in the tail-bytes paper) miss interpretable “calls sendTextMessage” signals. Solution: Branch 1 = FexDroid-lite \(\mathbf{f} \in \{0,1\}^{D_f}\), \(D_f pprox 3000 ext{–}5000\), through ASCNN or MLP → \(\mathbf{z}_f \in \mathbb{R}^{128}\). Branch 2 = last 1024 bytes \(\mathbf{b}\) through 1DCNN → \(\mathbf{z}_b \in \mathbb{R}^{64 ext{–}128}\). Late fusion: \(\mathbf{z} = [\mathbf{z}_f \| \mathbf{z}_b]\) → FC → sigmoid. Reserve for multistep Stage 3+ when cheap models are uncertain — highest combined extraction cost in the thesis catalog.

2. Component A — FexDroid-lite sparse vector f

What it analyzes

Category-capped Drebin-style binary vector: permissions, API calls, intents, services, receivers, etc., from manifest + Dex static analysis (10 categories; drop noisy URL/activity buckets per FexDroid paper).

Why this input was chosen

Named features are explainable and strong on known families; cap per category keeps mobile deployment feasible vs 500K-d full Drebin.

Step-by-Step Process

  1. Unzip APK; parse manifest and disassemble/string-scan Dex.
  2. For each category \(c\), match APK against frozen vocabulary \(V_c\) (top ~500 terms per category offline).
  3. Set \(f_j = 1\) if feature \(j\) present in APK.
  4. Concatenate category blocks → \(\mathbf{f} \in \{0,1\}^{D_f}\), \(D_f pprox 3000 ext{–}5000\).
  5. Optional: drop categories with high uncertainty (FexDroid category pruning).

Mathematical Formulation

\[ f_j = \mathbb{1}[\text{feature}_j \in \text{APK}], \quad \mathbf{f} \in \{0,1\}^{D_f}, \; D_f \approx 3\text{K–}5\text{K} \]

  • \(D_f\) — total sparse dimension after capping
  • \(V_c\) — frozen vocabulary per category

Architecture Flowchart

APK
 ├─► Manifest ──► category vocab matches
 └─► Dex strings ──► API / intent features
         │
         ▼
    f ∈ {0,1}^(3K–5K)

Output and how it connects to the next stage

Fed to semantic tower: \(\mathbf{z}_f = g_f(\mathbf{f})\) (ASCNN or 2-layer MLP).

Key Advantage / Novelty

Key novelty: Thesis-scale FexDroid — not full 49K paper vector — paired with bytes for orthogonal evidence.

3. Component B — Raw APK tail bytes b (1024-d)

What it analyzes

The last \(N=1024\) byte values of the APK file on disk, read as unsigned integers 0–255, in file order (end of ZIP container).

Why this input was chosen

Tail region often contains zip central directory, comments, and padding — patterns correlated with packers and malware tooling without parsing APK structure.

Step-by-Step Process

  1. Open APK path as binary file (treat as opaque byte stream).
  2. Seek to end; read \(N=1024\) bytes (pad with zeros if file shorter than 1024).
  3. Form sequence \(\mathbf{b} = (b_1, \ldots, b_{1024})\), \(b_i \in \{0,\ldots,255\}\).
  4. Normalize for network: e.g. \(b_i / 255\) or embed as integer channel (match trained 1DCNN).
  5. No decompression, manifest, or Dex required for this branch alone.

Mathematical Formulation

\[ b_i = \mathrm{byte}_{|F|-1024+i}, \quad \mathbf{b} \in \mathbb{Z}^{1024}, \quad b_i \in [0,255] \]

  • \(|F|\) — APK file size in bytes
  • \(b_i\) — \(i\)-th tail byte

Architecture Flowchart

Raw APK file on disk
  │
  └─► read last 1024 bytes
         │
         ▼
    b (1×1024)  values 0–255

Output and how it connects to the next stage

Input to 1DCNN tower only; parallel to semantic branch (no shared layers until fusion).

Key Advantage / Novelty

Why different from Dex header: Tail is container/file bytes, not parsed DexHeader struct — catches packers parsers skip.

4. Component C — 1DCNN byte tower

What it analyzes

1-D convolutional network over sequence \(\mathbf{b}\): multiple Conv1d → BatchNorm → ReLU blocks, MaxPool, fully connected layers (Hasegawa & Iyatomi 2018 / your ByteCNN).

Why this input was chosen

CNNs learn local byte n-grams (packer signatures, alignment patterns) without hand-crafted features.

Step-by-Step Process

  1. Input tensor shape (batch, 1, 1024) after normalization.
  2. Stack 4× Conv1d(kernel≈5, filters 32→128) + BN + ReLU.
  3. MaxPool along sequence length to reduce temporal dimension.
  4. Flatten / FC → embedding \(\mathbf{z}_b \in \mathbb{R}^{64 ext{–}128}\).
  5. Train with BCE or cross-entropy on malware label; freeze for fusion stage if staged training.

Mathematical Formulation

Conv1d: \[ h^{(l+1)} = \mathrm{ReLU}(\mathrm{BN}(W^{(l)} * h^{(l)} + b^{(l)})) \]

\[ \mathbf{z}_b = \mathrm{FC}(\mathrm{Pool}(h^{(L)})) \in \mathbb{R}^{d_b} \]

  • \(*\) — 1-D convolution along byte index
  • \(\mathbf{z}_b\) — byte-branch embedding (\(d_b pprox 64 ext{–}128\))

Architecture Flowchart

  ▼

  │
  ▼

Output and how it connects to the next stage

Outputs \(\mathbf{z}_b\). Concatenated with \(\mathbf{z}_f\) at fusion layer.

Key Advantage / Novelty

Paper result: Tail-only 1DCNN reported 95–97% accuracy on Drebin/AMD — strong single-branch baseline.

5. Component D — Late fusion head

What it analyzes

Concatenated embeddings from semantic and byte towers; small fully connected classifier produces final malware probability.

Why this input was chosen

Each modality needs different inductive bias (sparse high-d vs dense local patterns); fusion layer learns when to trust semantics vs tail artifacts.

Step-by-Step Process

  1. Compute \(\mathbf{z}_f = g_f(\mathbf{f})\) and \(\mathbf{z}_b = g_b(\mathbf{b})\) (forward both branches).
  2. Concatenate: \(\mathbf{z} = [\mathbf{z}_f \| \mathbf{z}_b]\).
  3. Apply \(\hat{y} = \sigma(\mathbf{W}_z \mathbf{z} + \mathbf{b}_z)\) or 1-hidden-layer MLP on \(\mathbf{z}\).
  4. Train end-to-end or fine-tune fusion after freezing branch weights.
  5. At inference: run both extractions; if either branch unavailable, abstain or fall back to single branch (document policy).

Mathematical Formulation

\[ \mathbf{z} = [\mathbf{z}_f \| \mathbf{z}_b] \in \mathbb{R}^{d_f + d_b}, \quad \hat{y} = \sigma(\mathbf{W}\mathbf{z} + \mathbf{b}) \]

  • \(d_f pprox 128\) — semantic embedding size
  • \(d_b pprox 64 ext{–}128\) — byte embedding size
  • \(\hat{y}\) — final malware probability

Architecture Flowchart

z_f (128-d) ──┐
                    ├──► z (192–256-d) ──► FC/MLP ──► σ ──► P(malware)
z_b (64–128-d) ─┘

Output and how it connects to the next stage

Final score for multistep pipeline Stage 3+ or offline high-confidence path.

Key Advantage / Novelty

Key advantage: Orthogonal errors — semantic misses novel packing; bytes miss semantic intent — fusion reduces both failure modes.

Why fusion helps: Packers change zip layout (tail) while leaving some API strings visible (sparse), or obfuscate strings while tail signature remains — joint decision boundary in \((\mathbf{z}_f, \mathbf{z}_b)\) space catches samples either branch misses alone.

Deployment note: Not for every APK — use after MLDP+header cascade and Pattern A disagree or score near threshold.
