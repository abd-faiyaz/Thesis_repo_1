Broadcast Receiver + Permission Classifier

Paper: Mohsen et al., CIC 2017 — Detecting Android Malwares By Mining Statically Registered Broadcast Receivers

Prerequisites (beginner)

APK: A ZIP archive containing AndroidManifest.xml (what the app declares) and classes.dex (compiled code). You can scan APKs without running them — that is static analysis.

Permissions (<uses-permission>): capabilities such as SEND_SMS or READ_CONTACTS. Each declared permission is visible in the manifest.

Broadcast receiver: An Android component that runs code when a system event fires — e.g. BOOT_COMPLETED (phone finished booting), SMS_RECEIVED (new text). Malware often registers receivers so it wakes in the background.

Feature vector: A fixed-length list of 0/1 values — one bit per permission or intent action in a vocabulary learned from your training set.

Binary classification: The model outputs a malware probability; if it exceeds a threshold (usually 0.5), the APK is labeled malware.

1. Overview

Imagine you must screen 50,000 APK files before they reach users’ phones. Most detectors use only manifest permissions, but benign games and banking apps often request INTERNET and READ_PHONE_STATE just like trojans — so permission-only models plateau. Mohsen et al. (CIC 2017) add a second manifest signal: which broadcast receivers and intent actions each app registers statically. Malware disproportionately listens for boot, SMS, and connectivity events to persist and intercept data. The architecture has three blocks: (1) a permission binary vector, (2) a receiver-action binary vector, (3) early fusion via concatenation plus an SVM with RBF kernel in the paper (logistic regression or tiny MLP for ONNX deployment). Everything is manifest-only — no Dex decompilation.

2. Component A — Permission feature vector

What it analyzes

Every android:name in <uses-permission> tags inside AndroidManifest.xml.

Why this input was chosen

Permissions are Android’s primary static security declaration: malware that sends premium SMS, steals contacts, or records audio must often declare dangerous permissions visible to users and stores.

Step-by-Step Process

  1. Unzip the APK (it is a ZIP archive); locate AndroidManifest.xml (binary XML on disk — decode with AAPT2, Apktool, or an AxmlReader).
  2. Enumerate all <uses-permission android:name="…"> strings for this APK.
  3. From the training corpus only, build vocabulary \(\mathcal{P} = \{\text{perm}_1,\ldots,\text{perm}_P\}\) (typically \(P \approx 150\)–300 over ~50k APKs).
  4. For each APK \(i\), set \(p_{i,j}=1\) if \(\text{perm}_j\) appears in its manifest, else \(0\).
  5. Freeze \(\mathcal{P}\) at inference; permissions not in the vocabulary are ignored or optionally bucketed as “other.”

Mathematical Formulation

\[ p_{i,j} = \begin{cases} 1 & \text{if } \text{perm}_j \in \text{Manifest}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{p}_i \in \{0,1\}^{P} \]

  • \(P\) — permission vocabulary size (number of dimensions)
  • \(p_{i,j}\) — bit for permission \(j\) on APK \(i\)
  • \(\mathbf{p}_i\) — permission feature row for one APK

Output and how it connects to the next stage

Outputs \(\mathbf{p} \in \{0,1\}^{P}\). This vector is the first half of the fused input \(\mathbf{x}\) before the classifier.

Key Advantage / Novelty

Key novelty: Standard baseline domain; the paper includes it so receiver features can be proven to add value beyond permissions alone.

3. Component B — Broadcast receiver intent-action vector

What it analyzes

Intent android:name strings under <receiver><intent-filter><action> — statically registered broadcast receivers only.

Why this input was chosen

Receivers define when code runs without the user opening the app. Malware uses BOOT_COMPLETED to survive reboots and SMS_RECEIVED to intercept texts. The paper’s manual study (400 APKs) and large-scale experiments show malware registers more receivers and more sensitive actions than benign apps.

Step-by-Step Process

  1. Parse the same AndroidManifest.xml as Component A.
  2. Find every <receiver> element (exported or not; static registration only).
  3. For each receiver, collect all <action android:name="…"> inside nested <intent-filter> blocks.
  4. Build training vocabulary \(\mathcal{A}\) of distinct action strings from the corpus (\(R \approx 50\)–100).
  5. Set \(r_{i,k}=1\) if action \(k\) appears in any receiver filter for APK \(i\), else \(0\).
  6. Freeze \(\mathcal{A}\) for inference.

Mathematical Formulation

\[ r_{i,k} = \begin{cases} 1 & \text{if } \text{action}_k \in \text{Receivers}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{r}_i \in \{0,1\}^{R} \]

  • \(R\) — receiver-action vocabulary size
  • \(r_{i,k}\) — bit for intent action \(k\)
  • \(\mathbf{r}_i\) — receiver feature vector for APK \(i\)

Architecture Flowchart

AndroidManifest.xml
  │
  └─► <receiver> → <intent-filter> → <action>
         │
         ▼
   Receiver-action vector  (1×R)
   e.g. 1×80  binary

Output and how it connects to the next stage

Outputs \(\mathbf{r} \in \{0,1\}^{R}\). Concatenated with \(\mathbf{p}\) to form the classifier input \(\mathbf{x}\).

Key Advantage / Novelty

Why this is different from standard permission-only detectors: Drebin-style work rarely treats receiver actions as a dedicated feature block; Mohsen et al. show they improve accuracy when combined with permissions.

4. Component C — Fusion and classifier

What it analyzes

The concatenated vector \(\mathbf{x} = [\mathbf{p} \| \mathbf{r}]\). Paper: C-SVM with RBF kernel; thesis/ONNX: logistic regression or a 1-hidden-layer MLP.

Why this input was chosen

After concatenation, the joint space is still sparse and moderate-dimensional; a linear boundary often works, but SVM with RBF handles mild nonlinear interactions (e.g. rare permission + boot receiver together).

Step-by-Step Process

  1. Concatenate: \(\mathbf{x} \leftarrow [\mathbf{p}; \mathbf{r}]\) → dimension \(P+R\) (e.g. \(1 \times 280\)).
  2. Train on labeled APKs (malware = 1, benign = 0) with stratified cross-validation.
  3. Paper: grid-search SVM hyperparameters \(C\) (margin penalty) and \(\gamma\) (RBF width).
  4. ONNX path: train \(\mathbf{w}, b\) for logistic regression or small MLP; export to mobile runtime.
  5. At inference: build \(\mathbf{x}\) for a new APK → score → compare to threshold \(\tau\) (often 0.5).

Mathematical Formulation

SVM decision (paper):

\[ f(\mathbf{x}) = \mathrm{sign}\left(\sum_{i \in SV} \alpha_i y_i K(\mathbf{x}_i, \mathbf{x}) + b\right) \]

RBF kernel: \[ K(\mathbf{x}, \mathbf{x}') = \exp\left(-\gamma \|\mathbf{x} - \mathbf{x}'\|_2^2\right) \]

Logistic regression (ONNX-friendly):

\[ \hat{y} = \sigma(\mathbf{w}^T \mathbf{x} + b) = \frac{1}{1 + e^{-(\mathbf{w}^T \mathbf{x} + b)}} \]

  • \(SV\) — support vectors (training points that define the SVM boundary)
  • \(\alpha_i, y_i\) — dual coefficients and labels for support vectors
  • \(C\) — SVM regularization (trade-off margin vs misclassification)
  • \(\gamma\) — RBF kernel width
  • \(\mathbf{w}, b\) — logistic weights and bias
  • \(\hat{y}\) — estimated malware probability

                        ├──► Concat  x (1×(P+R))  ──► Classifier  ──► P(malware)
Receiver r (1×R) ─────┘
              e.g. (1×200)+(1×80) = (1×280)

Output and how it connects to the next stage

Final output: malware probability or hard label. In a multistep VigiDroid stack, this score is one domain among others (Dex header, tail bytes, etc.).

Key Advantage / Novelty

Key advantage: Manifest-only parsing; typical extraction < 100 ms; model < 50 KB. Complements structural (Dex header) and raw-byte models without overlapping their feature domains.

5. Ensemble or fusion mechanism

This model uses early fusion (feature-level concatenation before a single classifier), not late fusion or score voting:

\[ \mathbf{x} = [\mathbf{p} \| \mathbf{r}], \quad \hat{y} = f(\mathbf{x}) \]

  • \(\|\) — vector concatenation (append \(\mathbf{r}\) after \(\mathbf{p}\))
  • \(f\) — SVM or logistic/MLP; one joint decision boundary in \((P+R)\)-dimensional space
  • There is no separate score per branch averaged at the end — both domains are learned jointly.
p (1×P) ──┐
          ├──► x (1×(P+R))  e.g. 1×280 ──► f(·) ──► ŷ ∈ [0,1]

MLDP-Pruned Permission Classifier

Paper: IJACSA 2020 — Permission Extraction Framework for Android Malware Detection (Multi-Level Data Pruning, MLDP)

Prerequisites (beginner)

Android permissions: Listed in AndroidManifest.xml via <uses-permission>. There are ~135 official permission types (plus vendor-specific names). A naive detector uses all of them — many appear equally in benign and malware apps and add noise.

Feature selection: Choosing only the most useful inputs before training. Fewer dimensions → faster inference, smaller models, and often higher accuracy because irrelevant bits are removed.

Association rules: Patterns like “if apps request both SEND_SMS and RECEIVE_BOOT_COMPLETED, they are usually malware.” Rule mining finds such co-occurrences automatically from labeled data.

Support: Fraction of APKs in the dataset that contain a permission (or set). Very rare permissions are dropped so the model generalizes.

PRNR (Permission Ranking with Negative Rate): Ranks permissions by how much more often they appear in malware than in benign apps.

1. Overview

Suppose you train on 50,000 APKs and represent each app with a binary vector over all ~135+ manifest permissions — many dimensions are almost always zero or equally common in benign and malware sets, which hurts generalization and wastes phone CPU. The IJACSA 2020 Permission Extraction Framework applies Multi-Level Data Pruning (MLDP): three offline filters (PRNR → support → association rules) shrink the permission set to roughly 20–40 high-discriminative permissions, then a simple classifier (linear SVM in the paper; tiny MLP for ONNX) runs on that short vector. No Dex parsing, no broadcast receivers — pure manifest, but semantically different from a 2500-d bag-of-words because every dimension was chosen for separability, not vocabulary coverage.

2. Stage 1 — PRNR (Permission Ranking with Negative Rate)

What it analyzes

Per-permission counts in malware vs benign training APKs.

Why this input was chosen

Permissions requested equally by both classes carry no class signal. PRNR keeps permissions that skew toward malware (high ‘negative rate’ in benign, or elevated malware prevalence).

Step-by-Step Process

  1. For each permission \(j\), count \(M_j\) = number of malware APKs that declare it; \(B_j\) = number of benign APKs that declare it.
  2. Compute malware rate \(\rho_j^M = M_j / N_m\) and benign rate \(\rho_j^B = B_j / N_b\) where \(N_m, N_b\) are class totals.
  3. Define PRNR-style score (paper uses negative-rate ranking): e.g. \(\text{PRNR}_j = \rho_j^M / (\rho_j^B + \epsilon)\).
  4. Sort permissions by \(\text{PRNR}_j\) descending; keep top tier (e.g. top 50–80 candidates for next stages).
  5. Drop permissions with near-equal class rates (\(|\rho_j^M - \rho_j^B| < \delta\)).

Mathematical Formulation

\[ \text{PRNR}_j = \frac{M_j / N_m}{B_j / N_b + \epsilon} \]

Alternative discriminative form used in related work:

\[ \text{score}_j = \frac{\rho_j^M}{\rho_j^B + \epsilon}, \quad \rho_j^M = \frac{M_j}{N_m},\; \rho_j^B = \frac{B_j}{N_b} \]

  • \(M_j, B_j\) — malware/benign counts for permission \(j\)
  • \(N_m, N_b\) — total malware and benign APKs in training
  • \(\epsilon\) — small constant (e.g. \(10^{-6}\)) to avoid division by zero
  • \(\text{PRNR}_j\) — higher means more malware-skewed

         │

Output and how it connects to the next stage

Outputs a ranked candidate list passed to Stage 2 (support filter). Not used directly at inference.

Key Advantage / Novelty

Key novelty: First pruning level removes ‘ubiquitous’ permissions (e.g. INTERNET) that appear everywhere and do not separate classes.

3. Stage 2 — Support-based filtering

What it analyzes

Frequency of each permission (and permission sets) in the full training corpus.

Why this input was chosen

A permission appearing in only 2 APKs cannot generalize; support filtering removes ultra-rare noise while keeping statistically stable dimensions.

Step-by-Step Process

  1. For each permission \(j\) surviving PRNR, compute support: \(\text{supp}_j = \frac{\#\{\text{APKs with perm } j\}}{N}\).
  2. Set minimum support threshold \(\theta_{\min}\) (e.g. 0.01 = appears in at least 1% of APKs).
  3. Remove permissions with \(\text{supp}_j < \theta_{\min}\).
  4. Optionally cap maximum support \(\theta_{\max}\) to drop permissions present in >95% of both classes.
  5. Pass surviving permissions to association-rule mining.

Mathematical Formulation

\[ \text{supp}(j) = \frac{|\{i : \text{perm}_j \in \text{APK}_i\}|}{N} \]

For a set \\(X\\) of permissions:

\[ \text{supp}(X) = \frac{|\{i : X \subseteq \text{Perms}(i)\}|}{N} \]

  • \(N\) — total training APKs
  • \(\text{supp}(j)\) — fraction of APKs declaring permission \(j\)
  • \(\theta_{\min}\) — minimum support threshold

PRNR candidates

         ▼
   Filter: supp(j) ≥ θ_min
         │
         ▼

Output and how it connects to the next stage

Narrows the candidate pool for Stage 3. Ensures each retained permission has enough observations to learn stable rules.

Key Advantage / Novelty

Key novelty: Bridges statistical frequent-pattern mining with security — rare one-off permissions from packers do not enter the final model.

4. Stage 3 — Association-rule mining

What it analyzes

Co-occurrence of permission sets in malware-labeled APK transactions.

Why this input was chosen

Malware often requests combinations (SMS + boot + install) that benign apps rarely use together; association rules capture these joint patterns beyond single-bit permissions.

Step-by-Step Process

  1. Represent each APK as a transaction: set of declared permissions.
  2. Mine frequent itemsets in malware transactions with minimum support \(\sigma\).
  3. Generate rules \(X \Rightarrow Y\) where \(X, Y\) are permission subsets; compute confidence \(\text{conf}(X \Rightarrow Y) = \text{supp}(X \cup Y) / \text{supp}(X)\).
  4. Keep rules with \(\text{conf} \geq \theta_{\text{conf}}\) and lift indicating malware skew.
  5. Union all permissions appearing in high-confidence malware-associated rules → final set \(\mathcal{S}\), \(|\mathcal{S}| \approx 20\)–40.
  6. Freeze \(\mathcal{S}\) for all future inference.

Mathematical Formulation

\[ \text{conf}(X \Rightarrow Y) = \frac{\text{supp}(X \cup Y)}{\text{supp}(X)} \]

\[ \text{lift}(X \Rightarrow Y) = \frac{\text{conf}(X \Rightarrow Y)}{\text{supp}(Y)} \]

Example rule retained: \(\{\texttt{SEND\_SMS}, \texttt{RECEIVE\_BOOT\_COMPLETED}\} \Rightarrow \text{malware}\) with high confidence.

  • \(X, Y\) — antecedent and consequent permission sets (or class label)
  • \(\text{conf}\) — conditional probability that \(Y\) holds given \(X\)
  • \(\text{lift}\) — how much more often \(Y\) occurs with \(X\) than by chance
  • \(\mathcal{S}\) — final pruned permission list

Architecture Flowchart

Malware transactions (permission sets)

  └─► Apriori / FP-Growth frequent itemsets
         │
         ▼
   Rules X ⇒ malware  (conf ≥ θ_conf)
         │
         ▼

Output and how it connects to the next stage

Produces fixed \(\mathcal{S}\) used to define inference-time vector dimension \(|\mathcal{S}|\).

Key Advantage / Novelty

Why this is different from standard full-permission vectors: Dimensions are data-mined for malware co-occurrence, not the full Android permission enum.

5. Component — Inference feature vector

What it analyzes

Only permissions in the frozen MLDP set \(\mathcal{S}\) for each new APK.

Why this input was chosen

At inference you never use 135+ dimensions — only the pruned list learned offline from the 50k training corpus.

Step-by-Step Process

  1. Parse AndroidManifest.xml for the target APK.
  2. For each \(\text{perm}_j \in \mathcal{S}\), set \(x_j = 1\) if declared, else \(0\).
  3. Result: \(\mathbf{x} \in \{0,1\}^{|\mathcal{S}|}\), typically \(1 \times 20\) to \(1 \times 40\).
  4. Pass \(\mathbf{x}\) to the classifier.

Mathematical Formulation

\[ x_j = \begin{cases} 1 & \text{if } \text{perm}_j \in \mathcal{S} \text{ and declared in APK} \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{x} \in \{0,1\}^{|\mathcal{S}|} \]

  • \(\mathcal{S}\) — MLDP-selected permission set (frozen after training)
  • \(x_j\) — \(j\)-th dimension of the pruned vector
  • \(|\mathcal{S}|\) — final dimension count (~20–40)

6. Component — Classifier (SVM / tiny MLP)

What it analyzes

The pruned binary vector \(\mathbf{x}\).

Why this input was chosen

Paper reports strong results with linear SVM on ~20–40 dims; ONNX deployment uses equivalent linear layer or 1-hidden-layer MLP.

Step-by-Step Process

  1. Train SVM or MLP on \(\mathbf{x}\) with labels (malware/benign).
  2. For SVM: solve quadratic program for maximum-margin separator in \(\mathbb{R}^{|\mathcal{S}|}\).
  3. For MLP: \(\mathbf{h} = \text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)\), \(\hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h} + b_2)\).
  4. Export weights to ONNX for on-device inference.
  5. Threshold \(\hat{y} > 0.5\) → malware.

Mathematical Formulation

Linear SVM: minimize \(\frac{1}{2}\|\mathbf{w}\|^2 + C \sum_i \xi_i\) subject to \(y_i(\mathbf{w}^T \mathbf{x}_i + b) \geq 1 - \xi_i\).

Logistic / MLP head:

\[ \hat{y} = \sigma(\mathbf{w}^T \mathbf{x} + b) \quad \text{or} \quad \hat{y} = \sigma(\mathbf{w}_2^T \,\text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1) + b_2) \]

  • \(C\) — SVM regularization constant
  • \(\xi_i\) — slack variables for soft margin
  • \(\hat{y}\) — malware probability

7. Ensemble or fusion mechanism

The base MLDP paper uses a single-domain pipeline — no multi-branch fusion. The three stages (PRNR, support, rules) are a sequential filter cascade on the permission space, not an ensemble of classifiers:

\[ \mathcal{P}_{ ext{all}} \xrightarrow{ ext{PRNR}} \mathcal{P}_1 \xrightarrow{ ext{supp}} \mathcal{P}_2 \xrightarrow{ ext{rules}} \mathcal{S} \]

Full perm space (135+)
  │ PRNR
  ▼ (~50–80)
  │ Support filter
  ▼ (~40–60)
  │ Association rules
  ▼
S (20–40) ──► x ──► classifier ──► ŷ

Cross-paper hybrids (e.g. Broadcast + MLDP) concatenate MLDP \(\mathbf{x}^{(S)}\) with other manifest vectors — see broadcast_mldp_hybrid.html.

Broadcast Receiver + MLDP Permission Hybrid

Cross-paper: Mohsen et al. 2017 (broadcast receivers) + IJACSA 2020 Permission Extraction Framework (MLDP)

Prerequisites (beginner)

MLDP-pruned permissions: Instead of ~135 permission bits, offline training selects ~20–40 “dangerous” permissions using PRNR, support, and association rules (see mldp_pruned_permission_classifier.html).

Broadcast receiver actions: Binary flags for system events the app listens to via <receiver> in the manifest (e.g. BOOT_COMPLETED). See Mohsen et al. 2017.

Concatenation [a | b]: Place vector a first, then b, forming one longer vector — early fusion (same as \([\mathbf{a} \| \mathbf{b}]\) in math notation).

Tiny MLP: A small neural network (e.g. 80 → 64 → 1) that can learn mild nonlinear combos like “SMS permission AND boot receiver together.”

1. Overview

On a corpus of 50,000 APKs, you want a manifest-only detector that is small enough for mid-range phones yet more expressive than permissions alone. Full permission vectors (~200–400 dims with receivers) are noisy; MLDP-only (~30 dims) misses when the app wakes up; receiver-only models miss curated dangerous permissions. This cross-paper hybrid concatenates ~20–40 MLDP-selected permission bits (IJACSA 2020) with ~30–80 broadcast receiver action bits (Mohsen 2017) into one vector of roughly 80–120 dimensions, then classifies with a tiny MLP (~80 → 64 → 1) exported to ONNX. No Dex decompilation, no 2500-d bag-of-words — two orthogonal manifest signals in one pass.

ANASTASIA Behavioral Feature Classifier (ANASTASIA-lite)

Paper: Fereidooni et al., NTMS 2016 — ANASTASIA: Android mAlware detection using STAtic analySIs of Applications · Thesis variant: top-128 + MLP-lite

Prerequisites (beginner)

Static vs dynamic analysis: Static inspection reads APK files without running them (safe, fast, on-device friendly). Dynamic analysis runs the app in a sandbox (accurate but slow, heavy battery).

Dalvik / Dex: App code lives in classes.dex. Static tools scan Dex strings and API references to see what the code actually calls, not only what the manifest declares.

Declared vs used permissions: Manifest says what the app may request; Dex analysis finds what code references — malware can hide behavior in bytecode.

uniPDroid: Tool used in the paper to extract ~560 binary behavioral features from manifest + Dex.

Feature selection (Extra Trees): Train an ensemble of randomized trees, rank feature importances, keep top \(K\) (e.g. 128) for a smaller mobile model.

XGBoost / MLP: Paper’s best accuracy uses gradient-boosted trees (~97.3% TPR reported); thesis ANASTASIA-lite uses a 2-layer MLP for ONNX size limits.

2. Component — uniPDroid 560-d behavioral extraction

What it analyzes

Manifest + all classes*.dex files: intents, used permissions, system commands, suspicious API calls, malicious-activity boolean flags.

Why this input was chosen

Bytecode captures actual operations; manifest alone under-reports abuse. The paper defines ~560 hand-crafted templates matched by static scanning (no app execution).

Step-by-Step Process

  1. Unzip APK; load AndroidManifest.xml and every classes*.dex.
  2. Disassemble or string-scan Dex (Androguard-style pipeline in paper; lightweight pattern matcher for thesis).
  3. Category 1 — Intents: intent actions/filters in manifest and code → set bits for known IPC/event triggers.
  4. Category 2 — Used permissions: permissions referenced in Dex (may differ from declared list).
  5. Category 3 — System commands: strings like chmod, su, sh, ps in bytecode.
  6. Category 4 — Suspicious APIs: e.g. sendTextMessage, Runtime.exec, getDeviceId.
  7. Category 5 — Activity flags: booleans for IMEI read, dynamic code load, reflection, network socket, etc.
  8. For each of 560 predefined behaviors \(i\), set \(f_i = 1\) if detected, else \(0\).

Mathematical Formulation

\[ \mathbf{f} \in \{0,1\}^{560}, \quad f_i = \mathbb{1}[\text{behavior}_i \text{ detected in APK}] \]

Category partition (conceptual):

\[ \mathbf{f} = [\mathbf{f}^{(\text{intents})} \| \mathbf{f}^{(\text{usedPerm})} \| \mathbf{f}^{(\text{syscmd})} \| \mathbf{f}^{(\text{api})} \| \mathbf{f}^{(\text{flags})}] \]

  • \(\mathbf{f}\) — full 560-d behavioral vector

3. Component — Offline top-K feature selection (Extra Trees)

What it analyzes

Why this input was chosen

LinRegDroid Permission Classifier

Paper: Şahin et al., IEEE Access 2022 — LinRegDroid: Detection of Android Malware Using Multiple Linear Regression Models-Based Classifiers

Prerequisites

APK & manifest: An APK is a ZIP archive; AndroidManifest.xml lists declared <uses-permission> names — no code execution needed for this model.

Linear regression: Fit a weighted sum of inputs to predict a continuous target. Here the target is a class encoding (benign ≈ 1, malware ≈ 0), so regression acts as a linear classifier.

Multiple linear regression (MLR): Many features at once: \(y = \beta_0 + \sum_k \beta_k x_k\). Coefficients \(\beta\) are found by least squares (minimize squared error on training labels).

Bagging: Train several models on random bootstrap samples of the training set; aggregate predictions by majority vote or averaging — reduces variance.

1. Overview

Imagine you have 50,000 APK files and need malware labels before install. Heavy models (deep nets, large SVMs) are accurate but slow on phones and in batch scanners. Şahin et al. ask: for permission-only static detection, is a multiple linear regression model enough? LinRegDroid answers yes: build a binary permission vector from AndroidManifest.xml, learn coefficients \(\boldsymbol{\beta}\) by least squares, map the continuous score to {benign, malware} with LinRegDroid1 (threshold 0.5) or LinRegDroid2 (nearest label 0/1). Optional bagging over linear models, linear-SVM, or decision trees pushes F-measure to 0.956 on the AMD dataset (paper). The architecture is manifest-only, ~135–400 dimensions, and equivalent to one linear layer + decision rule — ideal as an ultra-minimal baseline in your thesis stack.

Component A — Permission feature extraction

What it analyzes

Every android:name in <uses-permission> tags inside AndroidManifest.xml for each APK.

Why this input was chosen

Permissions are the cheapest high-level security signal on Android: malware that sends premium SMS, reads contacts, or installs packages must often declare dangerous permissions visible in the manifest. The paper uses the full permission vocabulary (not pruned subsets) to match classic Drebin-style permission detectors.

Step-by-Step Process

  1. Unzip the APK; locate AndroidManifest.xml (binary XML — decode with AAPT2, Apktool, or equivalent).
  2. Enumerate all <uses-permission android:name="…"> strings.
  3. From the training corpus only, build vocabulary \(\mathcal{P} = \{\text{perm}_1,\ldots,\text{perm}_M\}\) (paper reports \(M \approx 135\)–400 depending on dataset).
  4. For APK \(i\), set \(p_{i,k} = 1\) if \(\text{perm}_k\) appears, else \(0\).
  5. Freeze \(\mathcal{P}\) at inference; permissions not in vocabulary are ignored.

Mathematical Formulation

\[ p_{i,k} = \begin{cases} 1 & \text{if } \text{perm}_k \in \text{Manifest}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{p}_i \in \{0,1\}^{M} \]

Stack \(N\) training APKs into design matrix \(\mathbf{X} \in \mathbb{R}^{N \times M}\) (each row \(\mathbf{p}_i^T\)).

  • \(M\) — permission vocabulary size (feature dimension)
  • \(p_{i,k}\) — bit for permission \(k\) in APK \(i\)
  • \(\mathbf{p}_i\) — permission feature row fed to regression

Component B — Multiple linear regression (coefficient learning)

What it analyzes

Labeled training pairs \((\mathbf{p}_i, y_i)\) where \(y_i \in \{0,1\}\) encodes class (paper: 0 = malware, 1 = benign).

Why this input was chosen

Linear models train in milliseconds, require no GPU, and yield interpretable \(\beta_k\): positive \(\beta_k\) means permission \(k\) pushes the score toward benign. Least squares has a closed-form solution on moderate \(M\).

Step-by-Step Process

  1. Form label vector \(\mathbf{y} \in \mathbb{R}^N\) from training malware/benign flags.
  2. Build \(\mathbf{X}\) with rows \(\mathbf{p}_i^T\) (add column of ones if using intercept \(\beta_0\)).
  3. Solve normal equations for coefficients \(\boldsymbol{\beta}\).
  4. Store \(\beta_0, \beta_1, \ldots, \beta_M\) for deployment (ONNX: single Linear(M,1)).
  5. At inference, compute continuous score \(\hat{y}_i\) for each new APK.

Mathematical Formulation

Model: \[ \hat{y}_i = \beta_0 + \sum_{k=1}^{M} \beta_k \, p_{i,k} = \beta_0 + \boldsymbol{\beta}^T \mathbf{p}_i \]

Training (least squares): \[ \boldsymbol{\beta}^* = \arg\min_{\boldsymbol{\beta}} \|\mathbf{y} - \mathbf{X}\boldsymbol{\beta}\|_2^2 \quad \Rightarrow \quad \boldsymbol{\beta}^* = (\mathbf{X}^T\mathbf{X})^{-1}\mathbf{X}^T\mathbf{y} \]

  • \(\hat{y}_i\) — continuous predicted score (not yet a class label)
  • \(\beta_0\) — intercept bias term
  • \(\boldsymbol{\beta}\) — weight vector over permissions
  • \(\mathbf{X}, \mathbf{y}\) — training design matrix and labels

                ▼
         Deploy:  ŷ = β0 + β^T p

Output and how it connects to the next stage

Why this is different from standard XGBoost/SVM: No kernels, no trees — pure linear boundary in permission space; smallest possible model for ablation vs your 2500-d manifest pipeline.

Component C — LinRegDroid1 (threshold classifier, Algorithm 1)

What it analyzes

Continuous score \(\hat{y}_i\) from Component B for a single test APK.

Why this input was chosen

Regression outputs real numbers, not probabilities. A fixed threshold at 0.5 (midpoint between encoded labels 0 and 1) is the simplest calibration-free decision rule — same spirit as sigmoid + 0.5 cutoff.

Step-by-Step Process

  1. Compute \(\hat{y}_i = \beta_0 + \boldsymbol{\beta}^T \mathbf{p}_i\) for the APK.
  2. Compare \(\hat{y}_i\) to threshold \(t = 0.5\).
  3. If \(\hat{y}_i \geq 0.5\), assign benign; else malware.
  4. Return hard label (and optionally \(\hat{y}_i\) as confidence proxy).

FexDroid Category-Pruned Sparse Classifier

Paper: ICCAI 2018 — Effective and Explainable Detection of Android Malware (FexDroid / ProDroid family)

Prerequisites

Drebin feature space: Famous Android malware benchmark. Each APK maps to a sparse binary vector — one dimension per unique static string (API, permission, URL, activity, …). Joint vocabulary can exceed 545,333 dimensions.

Sparse vector: Almost all entries are 0; only present terms are 1. Storage and dot-products must exploit sparsity.

Linear SVM (LibLinear): Finds a hyperplane \(w^T x + b = 0\) that separates classes with margin; efficient on sparse high-D data in the paper.

Category taxonomy: FexDroid groups features into 10 semantic buckets so pruning is interpretable (drop whole noisy categories, not arbitrary indices).

1. Overview

Imagine 50,000 APK files and a Drebin-style extractor that could produce a vector with 545K+ dimensions — impossible to train or run on a phone. ProDroid/FexDroid (ICCAI 2018) attack this by (1) organizing features into 10 categories (permissions, API calls, intents, …), (2) pruning rare and high-uncertainty categories (URLs, activities), shrinking space toward ~49K, and (3) training a linear SVM for fast sparse classification (~94% TPR reported in the family). Your thesis FexDroid-lite caps each category at ~500 top terms → 3K–5K frozen dimensions + ASCNN or MLP for ONNX. Extraction needs manifest + Dex static analysis — highest cost among single-pass suggestions except full Drebin.

What it analyzes

Paper: Potha et al., Connection Science 2020 — An extrinsic random-based ensemble approach for android malware detection (ERBE)

Prerequisites

Static manifest features: Permissions (<uses-permission>) and intent actions (<action android:name="…"> in intent filters) — all extractable without running the APK.

Binary feature vector: One dimension per distinct permission or intent string in the training corpus; value 1 if present in APK, else 0 (~1K dims on AndroZoo in paper).

MLP: Multi-layer perceptron — fully connected layers with ReLU and sigmoid output for malware probability.

Ensemble vs deployable: Full ERBE runs 15 iterations with random feature/instance subspaces — best offline, 15× inference cost. Thesis uses one MLP base learner on the full vector.

1. Overview

On AndroZoo-scale corpora, manifest permissions alone miss behavior declared via intents (e.g. BOOT_COMPLETED, SMS_RECEIVED). Potha et al. build a joint binary vector over permissions and intent actions (~1002 dimensions), then propose ERBE (Extrinsic Random-based Ensemble): 15 rounds of training on random feature subspaces and random external malware/benign subsets, aggregating base-learner scores (LR, MLP, or SGD). Your thesis deploys ERBE's feature space + one MLP (~1K → hidden → 1) for ONNX parity with other manifest-neural models.

Component A — Permission + intent feature extraction

What it analyzes

Union of all uses-permission names and intent action strings appearing anywhere in the APK manifest (AndroZoo static pipeline in paper).

Why this input was chosen

Intents capture declared interaction with the OS (views, broadcasts, services) beyond capability flags. Joint vocabulary ~1K is compact yet richer than permissions-only LinRegDroid.

Component B — Full ERBE ensemble (paper, reference only)

What it analyzes

Binary vector \(\mathbf{x}\) and labeled training pool; external malware/benign repositories for extrinsic sampling.

Why this input was chosen

Step-by-Step Process

  1. Set iteration count \(T = 15\).
  2. For \(t = 1,\ldots,T\): sample random feature subset at rate \(a\) (e.g. 50% of \(D\)).
  3. Sample random external malware and benign APK subsets (extrinsic data).
  4. Train base learner (LR, MLP, or SGD) on subspace + subset.
  5. Score each test APK; append to list \(\mathcal{S}\).
  6. Aggregate: mean or vote over \(\mathcal{S}\) → final malware score.

Mathematical Formulation

Prerequisites

Dex header (104 bytes): After 8-byte magic (dex\n035), bytes 8–111 encode section sizes/offsets (strings, methods, classes). Malware often shows abnormal header statistics without readable manifest changes.

MSFDroid MLP(H): Normalize header bytes to \(\mathbf{H} \in [0,1]^{104}\); sum-pool across multidex; small MLP → 128-d embedding.

Broadcast receivers: Manifest <receiver> components with <action> tags — which system events wake the app (boot, SMS, connectivity).

Late fusion (Pattern B): Separate towers per modality → concat embeddings → final FC + sigmoid (MSFDroid Pattern B style, but BoW replaced by ~50-d receiver vector).

1. Overview

You need a detector richer than header-only MLP(H) (~83.5% ACC alone in MSFDroid Table 6) but lighter than 4380-d manifest BoW or ANASTASIA bytecode scan. This hybrid fuses 104-d Dex header (structural signal) with ~30–80-d broadcast receiver intent actions (event-subscription signal) using late fusion Pattern B: two small towers → concat embeddings → sigmoid. No permissions, no API strings, no raw tail bytes — manifest parse is limited to receivers; Dex read is header-only.

Component A — Dex header feature H (104-d)

What it analyzes

Bytes 8–111 of each classes*.dex file after magic verification (MSFDroid §3.3).

Why this input was chosen

Header reflects compiler/linker layout; malware packing and multidex anomalies perturb offsets/sizes before any string is read — complements manifest receivers.

Step-by-Step Process

  1. Unzip APK; enumerate all classes*.dex.
  2. Verify first 8 bytes match Dex magic.
  3. Read bytes 8–111 → raw vector \(\mathbf{h}^{( ext{dex})}\).
  4. Encode: \(h_b = ext{byte}_b / 255\).
  5. Min–max normalize each dimension using training corpus stats.
  6. Multidex: element-wise sum \(\mathbf{H} = \sum_{ ext{dex}} \mathbf{h}^{( ext{dex})}\).

Mathematical Formulation

\[ h_b = \frac{\text{byte}_b}{255}, \quad \mathbf{H} = \sum_{d=1}^{N_{\text{dex}}} \mathbf{h}^{(d)} \in [0,1]^{104} \]

Corpus normalization: \(\tilde{H}_j = \frac{H_j - \min_j}{\max_j - \min_j + \epsilon}\).

  • \(\mathbf{H}\) — pooled normalized header (104-d)
  • \(N_{\text{dex}}\) — number of dex files in APK
  • \(\epsilon\) — numerical stability in min–max

Component C — MLP(H) tower (MSFDroid Base Model 1)

What it analyzes

Normalized header vector \(\mathbf{H} \in \mathbb{R}^{104}\).

Why this input was chosen

Two FC+ReLU blocks (paper Fig. 3) map structural layout to 128-d embedding suitable for fusion.

6. Late fusion mechanism (Pattern B style)

What it analyzes

Embeddings \(\mathbf{z}_H\) (structural) and \(\mathbf{z}_R\) (manifest behavioral) from separate towers.

Why this input was chosen

Late fusion lets each modality use its own inductive bias — header MLP for continuous layout, shallow net for sparse binary actions — before joint decision. Matches MSFDroid Pattern B (separate ASCNN/MLP branches) but swaps manifest BoW for receivers.

Step-by-Step Process

  1. Compute \(\mathbf{H}\) and \(\mathbf{R}\) from APK.
  2. Forward through MLP(H) → \(\mathbf{z}_H\).
  3. Forward through receiver tower → \(\mathbf{z}_R\).
  4. Concatenate \(\mathbf{z} = [\mathbf{z}_H \| \mathbf{z}_R]\).
  5. Final FC + sigmoid → \(\hat{y}\).

Mathematical Formulation

\[ \mathbf{z} = [\mathbf{z}_H \| \mathbf{z}_R] \in \mathbb{R}^{128 + d_R}, \quad \hat{y} = \sigma(\mathbf{w}^T \mathbf{z} + b) \]

  • \(\mathbf{z}\) — fused embedding (e.g. 192-d if \(d_R=64\))
  • \(\hat{y}\) — malware probability

ANASTASIA Features + Manifest BoW Fusion

Cross-paper: Fereidooni et al. NTMS 2016 (ANASTASIA 128-d behavioral) + Peng et al. MSFDroid 2022 (manifest BoW I, ASCNN Pattern A)

Prerequisites

APK anatomy: ZIP containing AndroidManifest.xml (declarations) and classes.dex (Dalvik bytecode). Static analysis reads these without executing the app.

Bag-of-words (BoW) on manifest

Fix a training vocabulary of \(N\) terms (permissions + intent keywords). For each APK, dimension \(j\) is 1 if term \(j\) appears. MSFDroid uses \(N=4380\) plus one UNK bucket → 4381-d sparse binary vector I.

ANASTASIA behavioral features

~560 binary flags from manifest + Dex (API calls, shell commands, used permissions, intents). ANASTASIA-lite keeps top \(K=128\) via Extra Trees. See anastasia_behavioral_classifier.html.

MSFDroid Pattern A — ASCNN(C)

Early fusion: concatenate feature vectors, then one Adaptive Shrinkage CNN (3 blocks + AvgPool) compresses high-dimensional sparse input to 128-d embedding → MLP → sigmoid. Paper Fig. 3 / Fig. 7; replaces Dex header H with behavioral b in this hybrid.

Concatenation

\([\mathbf{a} \| \mathbf{b}]\) appends all dimensions of \(\mathbf{b}\) after \(\mathbf{a}\).

1. Overview

Imagine 50,000 APK files on a phone scanner. Pattern A (MSFDroid) concatenates a 104-d Dex header with a ~4381-d manifest BoW and runs ASCNN — strong on declared permissions but blind to what bytecode actually calls. ANASTASIA alone captures API abuse and shell commands but misses broad manifest keyword patterns. This hybrid replaces H with top-128 behavioral bits b, keeps the same BoW I, and feeds x = [b || I] ∈ ℝ4509 into the same ASCNN(C) Pattern A tower. One forward pass; medium–high extraction (manifest + Dex string scan); high F1 potential on API-heavy malware.

2. Component A — ANASTASIA behavioral vector b (128-d)

What it analyzes

Top-\(K\) subset of the 560-d uniPDroid behavioral profile: intents, used permissions in Dex, system commands (su, chmod), suspicious API strings (sendTextMessage, Runtime.exec), and composite activity flags.

Why this input was chosen

Dex header bytes describe structure (section sizes/offsets); behavioral bits describe capabilities the code exercises. Malware may hide SMS fraud in bytecode without honest manifest declarations — ANASTASIA closes that gap relative to Pattern A's H.

Step-by-Step Process

  1. Unzip APK; locate AndroidManifest.xml and all classes*.dex.
  2. Run uniPDroid-style static scan (Androguard pipeline in original paper): match 560 predefined behavior templates.
  3. Set \(b_i = 1\) if behavior \(i\) detected, else \(0\) → full \(\mathbf{f} \in \{0,1\}^{560}\).
  4. Offline on training corpus: Extra Trees feature importance → index set \(\mathcal{K}\), \(|\mathcal{K}|=128\).
  5. At inference: output only \(\mathbf{b} = \mathbf{f}_{\mathcal{K}} \in \{0,1\}^{128}\) (frozen \(\mathcal{K}\)).

Mathematical Formulation

\[ f_i = \mathbb{1}[\text{behavior}_i \text{ detected}], \quad \mathbf{f} \in \{0,1\}^{560} \]

\[ b_j = f_{\mathcal{K}_j}, \quad \mathbf{b} \in \{0,1\}^{128} \]

  • \(f_i\) — indicator for behavior template \(i\)
  • \(\mathcal{K}\) — selected feature indices (128)
  • \(\mathbf{b}\) — behavioral sub-vector fed to fusion

Output and how it connects to the next stage

Outputs \(\mathbf{b}\). Concatenated with manifest BoW \(\mathbf{I}\) before ASCNN: \(\mathbf{x} = [\mathbf{b} \| \mathbf{I}]\).

Key novelty: Swaps cheap structural H for richer bytecode-observed behavior while keeping vector width similar (128 vs 104) for fair comparison to Pattern A.

3. Component B — Manifest BoW I (4381-d)

What it analyzes

Sparse binary bag-of-words over permission names and intent-related keywords from decoded AndroidManifest.xml (MSFDroid §3.5, same lexicon as Pattern A).

Why this input was chosen

Manifest declarations remain the strongest coarse signal for store-visible risk. BoW captures thousands of permission/intent combinations that a 128-d behavioral slice might not encode explicitly.

Step-by-Step Process

  1. Decode binary AndroidManifest.xml to readable XML.
  2. Extract all permission strings and intent keyword strings (actions, categories).
  3. On training set: collect vocabulary; drop terms with frequency < 2.
  4. Cap lexicon at \(N = 4380\); reserve index 4381 for UNK (out-of-vocabulary).
  5. For APK \(t\): \(I_j = 1\) if term \(j\) in manifest, else \(0\); map OOV to UNK bit.

Mathematical Formulation

\[ I_j = \begin{cases} 1 & \text{if term}_j \in \text{Manifest}(t) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{I} \in \{0,1\}^{4381} \]

  • \(N=4380\) — dictionary size before UNK
  • \(I_j\) — BoW dimension \(j\)
  • UNK — single bucket for any OOV term at inference

4. Component C — ASCNN(C) Pattern A tower

What it analyzes

Single neural tower on fused vector \(\mathbf{x}\): three Adaptive Shrinkage Convolution blocks (kernel 3, strides 2,2,1 per MSFDroid Fig. 7) + AvgPool1d → 128-d embedding \(\mathbf{e}\) → MLP head → sigmoid malware probability.

Why this input was chosen

High-dimensional sparse BoW is noisy. ASCNN applies 1-D convolution plus soft-thresholding (adaptive shrinkage) to denoise rare bits before classification — paper Table 5 shows ASCNN beats plain CNN on BoW.

Step-by-Step Process

  1. Reshape \(\mathbf{x}\) as 1×4509 sequence (batch × channels × length).
  2. Block 1: Conv1d → adaptive shrinkage (soft-threshold) → activation; stride 2.
  3. Block 2–3: repeat with strides 2 and 1 (paper Fig. 7).
  4. Global AvgPool1d → \(\mathbf{e} \in \mathbb{R}^{128}\).
  5. MLP: FC + BatchNorm + ReLU blocks → single logit → \(\sigma\) → \(\hat{y}\).

Mathematical Formulation

Shrinkage (conceptual, per channel): \[ y = \mathrm{sign}(x) \cdot \max(|x| - \lambda, 0) \]

Full tower: \[ \mathbf{e} = \mathrm{AvgPool}(\mathrm{ASCNN}_{3}(\mathbf{x})), \quad \hat{y} = \sigma(\mathrm{MLP}(\mathbf{e})) \]

  • \(\lambda\) — learned or adaptive threshold (noise suppression)
  • \(\mathbf{e}\) — 128-d embedding before classifier head
  • \(\hat{y}\) — malware probability

FexDroid Sparse + Raw APK Tail Dual-Branch

Cross-paper: ICCAI 2018 FexDroid (category-pruned sparse ~3K–5K) + Hasegawa & Iyatomi 2018 (1D-CNN on last 1024 APK bytes)

Prerequisites

FexDroid / Drebin-style sparse features

Binary indicators for named artifacts: permissions, API calls, intents, components — grouped into 10 categories. Full Drebin >500K dims; FexDroid prunes to ~49K; thesis FexDroid-lite caps ~500 terms/category → 3K–5K. See fexdroid_category_sparse_classifier.html.

Raw APK tail bytes (ByteCNN / 1DCNN)

Read the last 1024 bytes of the APK file as integers 0–255. No unzip, no parsing. Packing, zip comment, and dex placement artifacts show up here. Your deployed 1DCNN model uses this domain.

Late fusion (Pattern B style)

Each branch has its own network → embedding vectors → concatenate → final FC layer. Branches see different input modalities.

Dual-branch vs early concat

Early concat would force one tower to mix 3K sparse bits with 1024 raw bytes — poor inductive bias. Late fusion keeps semantic ASCNN/MLP separate from convolutional byte learning.

2. Component A — FexDroid-lite sparse vector f

What it analyzes

3. Component B — Raw APK tail bytes b (1024-d)

What it analyzes

The last \(N=1024\) byte values of the APK file on disk, read as unsigned integers 0–255, in file order (end of ZIP container).

Why this input was chosen

Tail region often contains zip central directory, comments, and padding — patterns correlated with packers and malware tooling without parsing APK structure.

Step-by-Step Process

  1. Open APK path as binary file (treat as opaque byte stream).
  2. Seek to end; read \(N=1024\) bytes (pad with zeros if file shorter than 1024).
  3. Form sequence \(\mathbf{b} = (b_1, \ldots, b_{1024})\), \(b_i \in \{0,\ldots,255\}\).
  4. Normalize for network: e.g. \(b_i / 255\) or embed as integer channel (match trained 1DCNN).
  5. No decompression, manifest, or Dex required for this branch alone.

Mathematical Formulation

\[ b_i = \mathrm{byte}_{|F|-1024+i}, \quad \mathbf{b} \in \mathbb{Z}^{1024}, \quad b_i \in [0,255] \]

  • \(|F|\) — APK file size in bytes

4. Component C — 1DCNN byte tower

What it analyzes

1-D convolutional network over sequence \(\mathbf{b}\): multiple Conv1d → BatchNorm → ReLU blocks, MaxPool, fully connected layers (Hasegawa & Iyatomi 2018 / your ByteCNN).

Why this input was chosen

CNNs learn local byte n-grams (packer signatures, alignment patterns) without hand-crafted features.

Step-by-Step Process

  1. Input tensor shape (batch, 1, 1024) after normalization.
  2. Stack 4× Conv1d(kernel≈5, filters 32→128) + BN + ReLU.
  3. MaxPool along sequence length to reduce temporal dimension.
  4. Flatten / FC → embedding \(\mathbf{z}_b \in \mathbb{R}^{64 ext{–}128}\).
  5. Train with BCE or cross-entropy on malware label; freeze for fusion stage if staged training.

Mathematical Formulation

Conv1d: \[ h^{(l+1)} = \mathrm{ReLU}(\mathrm{BN}(W^{(l)} * h^{(l)} + b^{(l)})) \]

\[ \mathbf{z}_b = \mathrm{FC}(\mathrm{Pool}(h^{(L)})) \in \mathbb{R}^{d_b} \]

5. Component D — Late fusion head

What it analyzes

Concatenated embeddings from semantic and byte towers; small fully connected classifier produces final malware probability.

Why this input was chosen

Each modality needs different inductive bias (sparse high-d vs dense local patterns); fusion layer learns when to trust semantics vs tail artifacts.

Step-by-Step Process

  1. Compute \(\mathbf{z}_f = g_f(\mathbf{f})\) and \(\mathbf{z}_b = g_b(\mathbf{b})\) (forward both branches).
  2. Concatenate: \(\mathbf{z} = [\mathbf{z}_f \| \mathbf{z}_b]\).
  3. Apply \(\hat{y} = \sigma(\mathbf{W}_z \mathbf{z} + \mathbf{b}_z)\) or 1-hidden-layer MLP on \(\mathbf{z}\).
  4. Train end-to-end or fine-tune fusion after freezing branch weights.
  5. At inference: run both extractions; if either branch unavailable, abstain or fall back to single branch (document policy).

Mathematical Formulation

\[ \mathbf{z} = [\mathbf{z}_f \| \mathbf{z}_b] \in \mathbb{R}^{d_f + d_b}, \quad \hat{y} = \sigma(\mathbf{W}\mathbf{z} + \mathbf{b}) \]

  • \(d_f pprox 128\) — semantic embedding size
  • \(d_b pprox 64 ext{–}128\) — byte embedding size
  • \(\hat{y}\) — final malware probability

Architecture Flowchart

z_f (128-d) ──┐
                    ├──► z (192–256-d) ──► FC/MLP ──► σ ──► P(malware)
z_b (64–128-d) ─┘

Output and how it connects to the next stage

Final score for multistep pipeline Stage 3+ or offline high-confidence path.

Key Advantage / Novelty

Key advantage: Orthogonal errors — semantic misses novel packing; bytes miss semantic intent — fusion reduces both failure modes.

MLDP Permissions + Dex Header Cascade Filter

Cross-paper: IJACSA 2020 Permission Extraction Framework (MLDP ~30-d) + MSFDroid 2022 (Dex header H 104-d, MLP)

Prerequisites

MLDP-pruned permissions

Three-stage filter (PRNR → support → association rules) reduces ~135 permissions to ~20–40 high-risk bits. See mldp_pruned_permission_classifier.html.

Dex header H (104-d)

Bytes 8–111 of each classes.dex header (after magic), scaled to [0,1], min–max normalized, sum-pooled across multidex. Structural metadata only — no bytecode scan. Same as deployed MLP(H).

Cascade / multistep detection

Run cheapest models first; early exit if \(s < t_{\mathrm{low}}\) (benign) or \(s > t_{\mathrm{high}}\) (malware); else escalate to expensive models (thesis Task 2).

Fused single-pass variant

Alternatively concatenate \(\mathbf{x}^{(S)}\) and \(\mathbf{H}\) → one tiny MLP (\(\sim 150 o 64 o 1\)) — still <1 ms on mid-range phones.

1. Overview

Problem: Running ByteCNN, ASCNN(C), and XGBoost on every APK wastes battery. Solution: Combine the two cheapest static domains in the thesis: (1) MLDP-pruned permissions \(\mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|}\), \(|\mathcal{S}| pprox 30\); (2) Dex header \(\mathbf{H} \in [0,1]^{104}\). Deploy as Mode A fused vector \(\mathbf{x} \in \mathbb{R}^{150}\) through tiny MLP, or Mode B cascade (MLDP linear → optional MLP(H) → expensive stack). Goal: filter ~70% of APKs in one pass before manifest BoW or raw bytes.

2. Component A — MLDP permission vector x^(S)

What it analyzes

Binary vector over frozen permission subset \(\mathcal{S}\) selected by Multi-Level Data Pruning on the training corpus — only high-risk, malware-skewed permissions.

Why this input was chosen

Full permission lists are noisy; MLDP removes permissions common in both classes. Manifest-only parse — no Dex — fastest semantic signal.

Step-by-Step Process

  1. Offline: run MLDP (PRNR → support filter → association rules) on labeled training APKs → set \(\mathcal{S}\), \(|\mathcal{S}| pprox 20 ext{–}40\).
  2. Freeze \(\mathcal{S}\) for deployment.
  3. At inference: decode manifest; list declared permissions.
  4. Set \(x^{(S)}_j = 1\) if permission \(j \in \mathcal{S}\) appears, else \(0\).
  5. Output \(\mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|}\) (typically ~30-d).

Mathematical Formulation

\[ x^{(S)}_j = \mathbb{1}[\mathrm{perm}_j \in \mathrm{Manifest} \cap \mathcal{S}], \quad \mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|} \]

  • \(\mathcal{S}\) — MLDP-selected permission index set
  • \(x^{(S)}_j\) — \(j\)-th pruned permission bit

Architecture Flowchart

Training corpus (offline)
  │
  ▼
MLDP → S (|S|≈30)
  │
Inference: Manifest → x^(S) (1×30)

Output and how it connects to the next stage

Mode A: concatenate with \(\mathbf{H}\). Mode B: feed to Stage-1 linear scorer \(s_1\).

Key Advantage / Novelty

Key novelty: Curated manifest risk in ~30 dims vs 2500-d deployed XGBoost — ideal cascade front-end.

3. Component B — Dex header vector H (104-d)

What it analyzes

Normalized bytes 8–111 from each `classes.dex` header: section sizes, offsets, map_off, link_size, etc. (MSFDroid §3.3).

Why this input was chosen

Malware often has abnormal Dex layout (oversized string pools, odd offsets) even when manifest is minimal. Header read is O(1) in file size — no string scan.

Step-by-Step Process

  1. Unzip APK; enumerate all `classes*.dex`.
  2. Verify 8-byte magic (`dex\n035` or variant).
  3. Read bytes 8–111; encode \(h_b = \mathrm{byte}_b / 255\).
  4. Apply per-dimension min–max normalization from training statistics.
  5. Multidex: element-wise sum-pool \(\mathbf{H} = \sum_{\mathrm{dex}} \mathbf{h}^{(\mathrm{dex})}\).

Mathematical Formulation

\[ h_b = \frac{\mathrm{byte}_b}{255}, \quad \mathbf{H} = \sum_{d=1}^{D_{\mathrm{dex}}} \mathbf{h}^{(d)} \in [0,1]^{104} \]

  • \(D_{\mathrm{dex}}\) — number of dex files in APK
  • \(\mathbf{H}\) — pooled header feature vector

Architecture Flowchart

classes.dex
  │
  └─► bytes [8:112] → normalize
         │
         ▼
    H (1×104)

Output and how it connects to the next stage

Mode A: \(\mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}]\). Mode B: MLP(H) when Stage 1 uncertain.

Key Advantage / Novelty

Why with MLDP: Permissions = declared risk; header = structural risk — orthogonal cheap signals.

4. Component C — Fused tiny MLP (Mode A, 150-d)

What it analyzes

Single forward pass on concatenated MLDP + header vector; 2-layer MLP with sigmoid output.

Why this input was chosen

When latency budget allows one network call but not two-stage logic, fusion is simpler to deploy in ONNX than cascade thresholds.

Step-by-Step Process

  1. Concatenate \(\mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}] \in \mathbb{R}^{|\mathcal{S}|+104}\) (~134–150-d).
  2. MLP layer 1: \(\mathbf{h} = \mathrm{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)\), hidden dim 64.
  3. Output: \(\hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h} + b_2)\).
  4. Calibrate thresholds \(t_{\mathrm{low}}, t_{\mathrm{high}}\) on validation for early exit to rest of stack.
  5. Export ONNX; target model size < 20 KB.

Mathematical Formulation

\[ \mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}] \in \mathbb{R}^{150}, \quad \hat{y} = \sigma(\mathbf{W}_2\,\mathrm{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1) + \mathbf{b}_2) \]

  • 150 — typical fused dimension (\(30 + 104 + bias terms\))
  • \(\hat{y}\) — malware probability from single pass

Architecture Flowchart

x^(S) (30-d) ──┐
                     ├──► x (150-d) ──► MLP(150→64→1) ──► ŷ
H (104-d) ───────┘

Output and how it connects to the next stage

\(\hat{y}\) may trigger early benign/malware exit or escalate if \(t_{\mathrm{low}} < \hat{y} < t_{\mathrm{high}}\).

Key Advantage / Novelty

Key advantage: One ONNX graph, one manifest + header read — simplest integration for Step 1 filter.

5. Component D — Two-stage cascade (Mode B)

What it analyzes

Stage 1: logistic/linear on MLDP only (fastest). Stage 2: MLP(H) only if Stage 1 score in uncertain band.

Why this input was chosen

Splits manifest-only and dex-header costs — skip header read for confident Stage-1 decisions (optional optimization).

Step-by-Step Process

  1. Stage 1: \(s_1 = \sigma(\mathbf{w}_1^T \mathbf{x}^{(S)} + b_1)\).
  2. If \(s_1 < t_{\mathrm{low}}\) → label benign, STOP.
  3. If \(s_1 > t_{\mathrm{high}}\) → label malware, STOP.
  4. Else Stage 2: \(s_2 = \sigma(\mathrm{MLP}(\mathbf{H}))\).
  5. If still uncertain → pass to D2 ByteCNN, D4 Pattern A, ANASTASIA+BoW, etc.

Mathematical Formulation

Stage 1: \[ s_1 = \sigma(\mathbf{w}_1^T \mathbf{x}^{(S)} + b_1) \]

Stage 2: \[ s_2 = \sigma(\mathrm{MLP}(\mathbf{H})) \]

  • \(t_{\mathrm{low}}, t_{\mathrm{high}}\) — cascade thresholds tuned on validation
  • STOP — early exit saves average latency

Architecture Flowchart

APK → x^(S) → s1
              │
              ├─ s1 < t_low  ──► BENIGN (done)
              ├─ s1 > t_high ──► MALWARE (done)
              └─ else → H → MLP → s2
                      │
                      ├─ confident → done
                      └─ else → expensive models...

Output and how it connects to the next stage

Stage outputs gate multistep pipeline; ~70% APKs may exit after Step 1 when well tuned (thesis estimate).

Key Advantage / Novelty

Why different from Mode A: Interpretable staging — permission risk first, structural confirm second.
