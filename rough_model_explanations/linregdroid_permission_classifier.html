LinRegDroid Permission Classifier

Paper: Şahin et al., IEEE Access 2022 — LinRegDroid: Detection of Android Malware Using Multiple Linear Regression Models-Based Classifiers

Prerequisites

APK & manifest: An APK is a ZIP archive; AndroidManifest.xml lists declared <uses-permission> names — no code execution needed for this model.

Linear regression: Fit a weighted sum of inputs to predict a continuous target. Here the target is a class encoding (benign ≈ 1, malware ≈ 0), so regression acts as a linear classifier.

Multiple linear regression (MLR): Many features at once: \(y = \beta_0 + \sum_k \beta_k x_k\). Coefficients \(\beta\) are found by least squares (minimize squared error on training labels).

Bagging: Train several models on random bootstrap samples of the training set; aggregate predictions by majority vote or averaging — reduces variance.

1. Overview

Imagine you have 50,000 APK files and need malware labels before install. Heavy models (deep nets, large SVMs) are accurate but slow on phones and in batch scanners. Şahin et al. ask: for permission-only static detection, is a multiple linear regression model enough? LinRegDroid answers yes: build a binary permission vector from AndroidManifest.xml, learn coefficients \(\boldsymbol{\beta}\) by least squares, map the continuous score to {benign, malware} with LinRegDroid1 (threshold 0.5) or LinRegDroid2 (nearest label 0/1). Optional bagging over linear models, linear-SVM, or decision trees pushes F-measure to 0.956 on the AMD dataset (paper). The architecture is manifest-only, ~135–400 dimensions, and equivalent to one linear layer + decision rule — ideal as an ultra-minimal baseline in your thesis stack.

Key relationships

  • A → B: A produces the input vector 𝐩. B consumes 𝐩 during both training (fit β on many rows) and inference (one dot product per APK).
  • B → C or D: B outputs a single real number ŷ. C and D are mutually exclusive decision policies on the same ŷ — you pick one at deploy time; the paper compares both.
  • C and D are not models: they add no parameters. They only discretize ŷ into {benign, malware}.
  • At inference: A runs on every new APK → B applies stored β → C or D → final label. Vocabulary 𝒫 from A is frozen after training.
  • Optional ensemble (paper): repeat B (and optionally SVM/DT) on bootstrap samples; C/D run per base learner; majority vote aggregates — see Section 8.

Component A — Permission feature extraction

What it analyzes

Every android:name in <uses-permission> tags inside AndroidManifest.xml for each APK.

Why this input was chosen

Permissions are the cheapest high-level security signal on Android: malware that sends premium SMS, reads contacts, or installs packages must often declare dangerous permissions visible in the manifest. The paper uses the full permission vocabulary (not pruned subsets) to match classic Drebin-style permission detectors.

Step-by-Step Process

  1. Unzip the APK; locate AndroidManifest.xml (binary XML — decode with AAPT2, Apktool, or equivalent).
  2. Enumerate all <uses-permission android:name="…"> strings.
  3. From the training corpus only, build vocabulary \(\mathcal{P} = \{\text{perm}_1,\ldots,\text{perm}_M\}\) (paper reports \(M \approx 135\)–400 depending on dataset).
  4. For APK \(i\), set \(p_{i,k} = 1\) if \(\text{perm}_k\) appears, else \(0\).
  5. Freeze \(\mathcal{P}\) at inference; permissions not in vocabulary are ignored.

Mathematical Formulation

\[ p_{i,k} = \begin{cases} 1 & \text{if } \text{perm}_k \in \text{Manifest}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{p}_i \in \{0,1\}^{M} \]

Stack \(N\) training APKs into design matrix \(\mathbf{X} \in \mathbb{R}^{N \times M}\) (each row \(\mathbf{p}_i^T\)).

  • \(M\) — permission vocabulary size (feature dimension)
  • \(p_{i,k}\) — bit for permission \(k\) in APK \(i\)
  • \(\mathbf{p}_i\) — permission feature row fed to regression

Component B — Multiple linear regression (coefficient learning)

What it analyzes

Labeled training pairs \((\mathbf{p}_i, y_i)\) where \(y_i \in \{0,1\}\) encodes class (paper: 0 = malware, 1 = benign).

Why this input was chosen

Linear models train in milliseconds, require no GPU, and yield interpretable \(\beta_k\): positive \(\beta_k\) means permission \(k\) pushes the score toward benign. Least squares has a closed-form solution on moderate \(M\).

Step-by-Step Process

  1. Form label vector \(\mathbf{y} \in \mathbb{R}^N\) from training malware/benign flags.
  2. Build \(\mathbf{X}\) with rows \(\mathbf{p}_i^T\) (add column of ones if using intercept \(\beta_0\)).
  3. Solve normal equations for coefficients \(\boldsymbol{\beta}\).
  4. Store \(\beta_0, \beta_1, \ldots, \beta_M\) for deployment (ONNX: single Linear(M,1)).
  5. At inference, compute continuous score \(\hat{y}_i\) for each new APK.

Mathematical Formulation

Model: \[ \hat{y}_i = \beta_0 + \sum_{k=1}^{M} \beta_k \, p_{i,k} = \beta_0 + \boldsymbol{\beta}^T \mathbf{p}_i \]

Training (least squares): \[ \boldsymbol{\beta}^* = \arg\min_{\boldsymbol{\beta}} \|\mathbf{y} - \mathbf{X}\boldsymbol{\beta}\|_2^2 \quad \Rightarrow \quad \boldsymbol{\beta}^* = (\mathbf{X}^T\mathbf{X})^{-1}\mathbf{X}^T\mathbf{y} \]

  • \(\hat{y}_i\) — continuous predicted score (not yet a class label)
  • \(\beta_0\) — intercept bias term
  • \(\boldsymbol{\beta}\) — weight vector over permissions
  • \(\mathbf{X}, \mathbf{y}\) — training design matrix and labels

Component C — LinRegDroid1 (threshold classifier, Algorithm 1)

What it analyzes

Continuous score \(\hat{y}_i\) from Component B for a single test APK.

Why this input was chosen

Regression outputs real numbers, not probabilities. A fixed threshold at 0.5 (midpoint between encoded labels 0 and 1) is the simplest calibration-free decision rule — same spirit as sigmoid + 0.5 cutoff.

Step-by-Step Process

  1. Compute \(\hat{y}_i = \beta_0 + \boldsymbol{\beta}^T \mathbf{p}_i\) for the APK.
  2. Compare \(\hat{y}_i\) to threshold \(t = 0.5\).
  3. If \(\hat{y}_i \geq 0.5\), assign benign; else malware.
  4. Return hard label (and optionally \(\hat{y}_i\) as confidence proxy).

Mathematical Formulation

\[ \text{class}_i = \begin{cases} \text{benign} & \text{if } \hat{y}_i \geq 0.5 \\ \text{malware} & \text{otherwise} \end{cases} \]

  • \(t = 0.5\) — fixed decision threshold (paper Algorithm 1)
  • \(\hat{y}_i\) — regression output before thresholding

Component D — LinRegDroid2 (nearest-class rule, Algorithm 2)

What it analyzes

Same continuous \(\hat{y}_i\) as LinRegDroid1; alternative discretization when scores cluster away from 0.5.

Why this input was chosen

If \(\hat{y}_i = 0.72\), threshold rule says benign; if \(\hat{y}_i = 0.48\), threshold says malware. Nearest-class assigns whichever of {0, 1} is closer in absolute distance — handles scores that drift above 1 or below 0 from linear extrapolation.

Step-by-Step Process

  1. Compute \(\hat{y}_i\) as in Component B.
  2. Consider candidate encodings \(c \in \{0, 1\}\) (malware, benign).
  3. Pick \(c^* = \arg\min_{c} |\hat{y}_i - c|\).
  4. Map \(c^*\) back to class name.

Mathematical Formulation

\[ \text{class}_i = \arg\min_{c \in \{0,1\}} |\hat{y}_i - c| \]

Example: \(\hat{y}_i = 0.35\) → distances 0.35 and 0.65 to 0 and 1 → choose 0 (malware).

  • \(c\) — encoded class value (0 malware, 1 benign in paper)
  • \(|\hat{y}_i - c|\) — distance used for nearest-label assignment

8. Ensemble / bagging mechanism

The paper improves LinRegDroid with bagging (bootstrap aggregating): train multiple models on random subsets of training APKs, aggregate votes.

Ensemble-1: Five multiple linear regression models on bootstrap samples → majority vote on LinRegDroid1/2 labels.

Ensemble-2: Mix linear regression, linear-SVM, and decision trees on subsets → majority vote.

\[ \hat{y}_{\text{ens}} = \frac{1}{B}\sum_{b=1}^{B} f_b(\mathbf{p}), \quad \text{or} \quad \text{class} = \mathrm{mode}\big(\{f_b(\mathbf{p})\}_{b=1}^{B}\big) \]

  • \(B\) — number of bagged models (paper uses 5 for linear ensemble)
  • \(f_b\) — base learner trained on bootstrap sample \(b\)
