MLDP Permissions + Dex Header Cascade Filter

Cross-paper: IJACSA 2020 Permission Extraction Framework (MLDP ~30-d) + MSFDroid 2022 (Dex header H 104-d, MLP)

Prerequisites

MLDP-pruned permissions

Three-stage filter (PRNR → support → association rules) reduces ~135 permissions to ~20–40 high-risk bits. See mldp_pruned_permission_classifier.html.

Dex header H (104-d)

Bytes 8–111 of each classes.dex header (after magic), scaled to [0,1], min–max normalized, sum-pooled across multidex. Structural metadata only — no bytecode scan. Same as deployed MLP(H).

Cascade / multistep detection

Run cheapest models first; early exit if \(s < t_{\mathrm{low}}\) (benign) or \(s > t_{\mathrm{high}}\) (malware); else escalate to expensive models (thesis Task 2).

Fused single-pass variant

Alternatively concatenate \(\mathbf{x}^{(S)}\) and \(\mathbf{H}\) → one tiny MLP (\(\sim 150 o 64 o 1\)) — still <1 ms on mid-range phones.

1. Overview

Problem: Running ByteCNN, ASCNN(C), and XGBoost on every APK wastes battery. Solution: Combine the two cheapest static domains in the thesis: (1) MLDP-pruned permissions \(\mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|}\), \(|\mathcal{S}| pprox 30\); (2) Dex header \(\mathbf{H} \in [0,1]^{104}\). Deploy as Mode A fused vector \(\mathbf{x} \in \mathbb{R}^{150}\) through tiny MLP, or Mode B cascade (MLDP linear → optional MLP(H) → expensive stack). Goal: filter ~70% of APKs in one pass before manifest BoW or raw bytes.

2. Component A — MLDP permission vector x^(S)

What it analyzes

Binary vector over frozen permission subset \(\mathcal{S}\) selected by Multi-Level Data Pruning on the training corpus — only high-risk, malware-skewed permissions.

Why this input was chosen

Full permission lists are noisy; MLDP removes permissions common in both classes. Manifest-only parse — no Dex — fastest semantic signal.

Step-by-Step Process

  1. Offline: run MLDP (PRNR → support filter → association rules) on labeled training APKs → set \(\mathcal{S}\), \(|\mathcal{S}| pprox 20 ext{–}40\).
  2. Freeze \(\mathcal{S}\) for deployment.
  3. At inference: decode manifest; list declared permissions.
  4. Set \(x^{(S)}_j = 1\) if permission \(j \in \mathcal{S}\) appears, else \(0\).
  5. Output \(\mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|}\) (typically ~30-d).

Mathematical Formulation

\[ x^{(S)}_j = \mathbb{1}[\mathrm{perm}_j \in \mathrm{Manifest} \cap \mathcal{S}], \quad \mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|} \]

  • \(\mathcal{S}\) — MLDP-selected permission index set
  • \(x^{(S)}_j\) — \(j\)-th pruned permission bit

Architecture Flowchart

Training corpus (offline)
  │
  ▼
MLDP → S (|S|≈30)
  │
Inference: Manifest → x^(S) (1×30)

Output and how it connects to the next stage

Mode A: concatenate with \(\mathbf{H}\). Mode B: feed to Stage-1 linear scorer \(s_1\).

Key Advantage / Novelty

Key novelty: Curated manifest risk in ~30 dims vs 2500-d deployed XGBoost — ideal cascade front-end.

3. Component B — Dex header vector H (104-d)

What it analyzes

Normalized bytes 8–111 from each `classes.dex` header: section sizes, offsets, map_off, link_size, etc. (MSFDroid §3.3).

Why this input was chosen

Malware often has abnormal Dex layout (oversized string pools, odd offsets) even when manifest is minimal. Header read is O(1) in file size — no string scan.

Step-by-Step Process

  1. Unzip APK; enumerate all `classes*.dex`.
  2. Verify 8-byte magic (`dex\n035` or variant).
  3. Read bytes 8–111; encode \(h_b = \mathrm{byte}_b / 255\).
  4. Apply per-dimension min–max normalization from training statistics.
  5. Multidex: element-wise sum-pool \(\mathbf{H} = \sum_{\mathrm{dex}} \mathbf{h}^{(\mathrm{dex})}\).

Mathematical Formulation

\[ h_b = \frac{\mathrm{byte}_b}{255}, \quad \mathbf{H} = \sum_{d=1}^{D_{\mathrm{dex}}} \mathbf{h}^{(d)} \in [0,1]^{104} \]

  • \(D_{\mathrm{dex}}\) — number of dex files in APK
  • \(\mathbf{H}\) — pooled header feature vector

Architecture Flowchart

classes.dex
  │
  └─► bytes [8:112] → normalize
         │
         ▼
    H (1×104)

Output and how it connects to the next stage

Mode A: \(\mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}]\). Mode B: MLP(H) when Stage 1 uncertain.

Key Advantage / Novelty

Why with MLDP: Permissions = declared risk; header = structural risk — orthogonal cheap signals.

4. Component C — Fused tiny MLP (Mode A, 150-d)

What it analyzes

Single forward pass on concatenated MLDP + header vector; 2-layer MLP with sigmoid output.

Why this input was chosen

When latency budget allows one network call but not two-stage logic, fusion is simpler to deploy in ONNX than cascade thresholds.

Step-by-Step Process

  1. Concatenate \(\mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}] \in \mathbb{R}^{|\mathcal{S}|+104}\) (~134–150-d).
  2. MLP layer 1: \(\mathbf{h} = \mathrm{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)\), hidden dim 64.
  3. Output: \(\hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h} + b_2)\).
  4. Calibrate thresholds \(t_{\mathrm{low}}, t_{\mathrm{high}}\) on validation for early exit to rest of stack.
  5. Export ONNX; target model size < 20 KB.

Mathematical Formulation

\[ \mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{H}] \in \mathbb{R}^{150}, \quad \hat{y} = \sigma(\mathbf{W}_2\,\mathrm{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1) + \mathbf{b}_2) \]

  • 150 — typical fused dimension (\(30 + 104 + bias terms\))
  • \(\hat{y}\) — malware probability from single pass

Architecture Flowchart

x^(S) (30-d) ──┐
                     ├──► x (150-d) ──► MLP(150→64→1) ──► ŷ
H (104-d) ───────┘

Output and how it connects to the next stage

\(\hat{y}\) may trigger early benign/malware exit or escalate if \(t_{\mathrm{low}} < \hat{y} < t_{\mathrm{high}}\).

Key Advantage / Novelty

Key advantage: One ONNX graph, one manifest + header read — simplest integration for Step 1 filter.

5. Component D — Two-stage cascade (Mode B)

What it analyzes

Stage 1: logistic/linear on MLDP only (fastest). Stage 2: MLP(H) only if Stage 1 score in uncertain band.

Why this input was chosen

Splits manifest-only and dex-header costs — skip header read for confident Stage-1 decisions (optional optimization).

Step-by-Step Process

  1. Stage 1: \(s_1 = \sigma(\mathbf{w}_1^T \mathbf{x}^{(S)} + b_1)\).
  2. If \(s_1 < t_{\mathrm{low}}\) → label benign, STOP.
  3. If \(s_1 > t_{\mathrm{high}}\) → label malware, STOP.
  4. Else Stage 2: \(s_2 = \sigma(\mathrm{MLP}(\mathbf{H}))\).
  5. If still uncertain → pass to D2 ByteCNN, D4 Pattern A, ANASTASIA+BoW, etc.

Mathematical Formulation

Stage 1: \[ s_1 = \sigma(\mathbf{w}_1^T \mathbf{x}^{(S)} + b_1) \]

Stage 2: \[ s_2 = \sigma(\mathrm{MLP}(\mathbf{H})) \]

  • \(t_{\mathrm{low}}, t_{\mathrm{high}}\) — cascade thresholds tuned on validation
  • STOP — early exit saves average latency

Architecture Flowchart

APK → x^(S) → s1
              │
              ├─ s1 < t_low  ──► BENIGN (done)
              ├─ s1 > t_high ──► MALWARE (done)
              └─ else → H → MLP → s2
                      │
                      ├─ confident → done
                      └─ else → expensive models...

Output and how it connects to the next stage

Stage outputs gate multistep pipeline; ~70% APKs may exit after Step 1 when well tuned (thesis estimate).

Key Advantage / Novelty

Why different from Mode A: Interpretable staging — permission risk first, structural confirm second.

Why combine: MLDP catches permission-heavy trojans; header catches structurally anomalous dex without any permission signal. Together they approximate a large fraction of MSFDroid's cheap signal at ~1/30th the dimension of BoW models.

Expected F1: Moderate alone — purpose is latency and exit rate, not maximum accuracy. Pair with high-F1 models downstream for full stack performance.

7. Full end-to-end pipeline summary

Mode A (single-pass):
  APK → Manifest → x^(S) (30-d)
     → classes.dex → H (104-d)
     → x = [x^(S) || H] (150-d) → MLP → ŷ → exit or escalate

Mode B (cascade):
  APK → x^(S) → s1 ──► confident? → DONE
              │
              └─ uncertain → H → MLP → s2 ──► confident? → DONE
                                    │
                                    └─ uncertain → ByteCNN / ASCNN / XGBoost ...
