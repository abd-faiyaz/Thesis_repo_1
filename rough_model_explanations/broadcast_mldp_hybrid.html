Broadcast Receiver + MLDP Permission Hybrid

Cross-paper: Mohsen et al. 2017 (broadcast receivers) + IJACSA 2020 Permission Extraction Framework (MLDP)

Prerequisites (beginner)

MLDP-pruned permissions: Instead of ~135 permission bits, offline training selects ~20–40 “dangerous” permissions using PRNR, support, and association rules (see mldp_pruned_permission_classifier.html).

Broadcast receiver actions: Binary flags for system events the app listens to via <receiver> in the manifest (e.g. BOOT_COMPLETED). See Mohsen et al. 2017.

Concatenation [a | b]: Place vector a first, then b, forming one longer vector — early fusion (same as \([\mathbf{a} \| \mathbf{b}]\) in math notation).

Tiny MLP: A small neural network (e.g. 80 → 64 → 1) that can learn mild nonlinear combos like “SMS permission AND boot receiver together.”

1. Overview

On a corpus of 50,000 APKs, you want a manifest-only detector that is small enough for mid-range phones yet more expressive than permissions alone. Full permission vectors (~200–400 dims with receivers) are noisy; MLDP-only (~30 dims) misses when the app wakes up; receiver-only models miss curated dangerous permissions. This cross-paper hybrid concatenates ~20–40 MLDP-selected permission bits (IJACSA 2020) with ~30–80 broadcast receiver action bits (Mohsen 2017) into one vector of roughly 80–120 dimensions, then classifies with a tiny MLP (~80 → 64 → 1) exported to ONNX. No Dex decompilation, no 2500-d bag-of-words — two orthogonal manifest signals in one pass.

2. Component A — MLDP permission sub-vector

What it analyzes

Only permissions in the frozen MLDP set \(\mathcal{S}\) from offline pruning on the training corpus.

Why this input was chosen

Full permission space is redundant; MLDP keeps permissions that skew toward malware and appear in high-confidence association rules — the “what may this app do?” signal in compact form.

Step-by-Step Process

  1. Offline on labeled training APKs: run PRNR → support filter → association-rule mining → freeze \(\mathcal{S}\), \(|\mathcal{S}| \approx 20\)–40.
  2. At inference: parse manifest; for each \(\text{perm}_j \in \mathcal{S}\), set \(x^{(S)}_j = 1\) if declared, else \(0\).
  3. Output \(\mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|}\), e.g. \(1 \times 30\).

Mathematical Formulation

\[ x^{(S)}_j = \begin{cases} 1 & \text{if } \text{perm}_j \in \mathcal{S} \land \text{declared} \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{x}^{(S)} \in \{0,1\}^{|\mathcal{S}|} \]

  • \(\mathcal{S}\) — MLDP-frozen permission subset
  • \(\mathbf{x}^{(S)}\) — pruned permission feature block

Architecture Flowchart

Offline: 50k APKs → MLDP → set S
Inference:
  Manifest → x^(S)  (1×|S|)  e.g. 1×30

Output and how it connects to the next stage

Outputs \(\mathbf{x}^{(S)}\). First block of concatenated vector \(\mathbf{x}\).

Key Advantage / Novelty

Key novelty: Curated permission dimensions — not the full Android enum — reduce noise vs Mohsen’s full-permission branch.

3. Component B — Broadcast receiver sub-vector

What it analyzes

Intent android:name strings under <receiver><intent-filter><action> in the manifest.

Why this input was chosen

Captures event-driven behavior orthogonal to permissions: malware registers boot/SMS/connectivity receivers far more often than benign apps (Mohsen empirical study).

Step-by-Step Process

  1. Parse the same AndroidManifest.xml.
  2. Collect all <action> names under static <receiver> elements.
  3. Build receiver vocabulary \(\mathcal{A}\) from training corpus (\(R \approx 30\)–80).
  4. Set \(x^{(R)}_k = 1\) if action \(k\) present, else \(0\).
  5. Output \(\mathbf{x}^{(R)} \in \{0,1\}^{R}\), e.g. \(1 \times 50\).

Mathematical Formulation

\[ x^{(R)}_k = \begin{cases} 1 & \text{if } \text{action}_k \in \text{Receivers}(\text{APK}) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{x}^{(R)} \in \{0,1\}^{R} \]

  • \(R\) — receiver-action vocabulary size
  • \(\mathbf{x}^{(R)}\) — receiver feature block

Architecture Flowchart

Manifest
  │
  └─► <receiver> / <action>
         │
         ▼
   x^(R)  (1×R)  e.g. 1×50

Output and how it connects to the next stage

Outputs \(\mathbf{x}^{(R)}\). Second block appended in fusion.

Key Advantage / Novelty

Key novelty: Receiver domain unchanged from Mohsen — proven complementary to permission signals.

4. Component C — Early fusion (concatenation)

What it analyzes

Single manifest feature vector combining MLDP permissions and receiver actions.

Why this input was chosen

Early fusion lets the MLP learn cross-domain interactions (e.g. dangerous permission + boot receiver) in one weight matrix.

Step-by-Step Process

  1. Concatenate: \(\mathbf{x} \leftarrow [\mathbf{x}^{(S)} \| \mathbf{x}^{(R)}]\).
  2. Total dimension \(d = |\mathcal{S}| + R\), typically \(d \approx 80\)–120 (e.g. \(1 \times 100\)).
  3. Feed \(\mathbf{x}\) to the tiny MLP.

Mathematical Formulation

\[ \mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{x}^{(R)}] \in \{0,1\}^{|\mathcal{S}| + R} \]

  • \(\|\) — concatenation operator
  • \(d\) — fused input dimension (~80–120)

Architecture Flowchart

x^(S) (1×|S|) ──┐
                    ├──► x (1×d)  e.g. 1×100
x^(R) (1×R)   ────┘

Output and how it connects to the next stage

Outputs unified \(\mathbf{x}\) for the classifier. No separate scores merged later.

Key Advantage / Novelty

Key advantage: ~5× smaller than Mohsen full-perm+receiver (~280+) while keeping both signal types.

5. Component D — Tiny MLP classifier

What it analyzes

Fused binary vector \(\mathbf{x} \in \{0,1\}^{d}\).

Why this input was chosen

Linear models handle most manifest signal, but a single hidden layer captures conjunctions (permission ∧ receiver) without a large DNN or RBF SVM on device.

Step-by-Step Process

  1. Hidden layer: \(\mathbf{h} = \text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)\), \(\mathbf{W}_1 \in \mathbb{R}^{64 \times d}\).
  2. Output: \(\hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h} + b_2)\).
  3. Train with binary cross-entropy on labeled APKs; export ONNX.
  4. Typical architecture: \(d \to 64 \to 1\) (e.g. \(100 \to 64 \to 1\)).

Mathematical Formulation

\[ \mathbf{h} = \max(0, \mathbf{W}_1 \mathbf{x} + \mathbf{b}_1), \quad \hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h} + b_2) \]

Binary cross-entropy loss for label \(y \in \{0,1\}\):

\[ \mathcal{L} = - \bigl( y \log \hat{y} + (1-y) \log(1-\hat{y}) \bigr) \]

  • \(\mathbf{W}_1, \mathbf{b}_1\) — first-layer weights and bias
  • \(\mathbf{w}_2, b_2\) — output layer
  • \(\hat{y}\) — malware probability

Architecture Flowchart

x (1×d)  e.g. 1×100
  │
  ▼
Linear d→64 + ReLU
  │
  ▼
Linear 64→1 + σ
  │
  ▼
P(malware)

Output and how it connects to the next stage

Final domain score for multistep scanning or ensemble with Dex-header / byte models.

Key Advantage / Novelty

Key advantage: Model size often < 20 KB; inference < 1 ms after manifest parse.

6. Ensemble or fusion mechanism

Early fusion at the feature level (not late fusion of two separate classifiers):

\[ \mathbf{x} = [\mathbf{x}^{(S)} \| \mathbf{x}^{(R)}], \quad \hat{y} = ext{MLP}(\mathbf{x}) \]

Manifest parse
      │
 ┌────┴────┐
 ▼         ▼
x^(S)    x^(R)
1×|S|    1×R
 │         │
 └────┬────┘
      ▼
  x (1×d)   d ≈ 80–120
      ▼
  Tiny MLP (d→64→1)
      ▼
  ŷ ∈ [0,1]

Offline, MLDP’s internal cascade (PRNR → support → rules) is separate from receiver vocabulary mining — both freeze before mobile deployment.

7. Experimental results

Model variantApprox. dimsSignals capturedExpected tradeoff
MLDP only~20–40Curated permissionsFastest; misses receiver behavior
Mohsen full (perm + receiver)~200–400All perms + receiversHeavier; noisy permissions
Broadcast only (no MLDP)~30–80ReceiversMisses curated dangerous perms
Broadcast + MLDP hybrid~80–120Curated perms + receiversBest manifest-only balance (thesis recommendation)

Why this hybrid should win: MLDP removes permission noise that dilutes linear separators; receivers add behavioral timing signal Mohsen demonstrated empirically. Together you get ~3× fewer dimensions than full Mohsen with two complementary semantics — “dangerous capabilities” plus “sensitive event subscriptions.”
