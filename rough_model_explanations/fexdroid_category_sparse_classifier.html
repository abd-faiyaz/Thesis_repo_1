FexDroid Category-Pruned Sparse Classifier

Paper: ICCAI 2018 — Effective and Explainable Detection of Android Malware (FexDroid / ProDroid family)

Prerequisites

Drebin feature space: Famous Android malware benchmark. Each APK maps to a sparse binary vector — one dimension per unique static string (API, permission, URL, activity, …). Joint vocabulary can exceed 545,333 dimensions.

Sparse vector: Almost all entries are 0; only present terms are 1. Storage and dot-products must exploit sparsity.

Linear SVM (LibLinear): Finds a hyperplane \(w^T x + b = 0\) that separates classes with margin; efficient on sparse high-D data in the paper.

Category taxonomy: FexDroid groups features into 10 semantic buckets so pruning is interpretable (drop whole noisy categories, not arbitrary indices).

1. Overview

Imagine 50,000 APK files and a Drebin-style extractor that could produce a vector with 545K+ dimensions — impossible to train or run on a phone. ProDroid/FexDroid (ICCAI 2018) attack this by (1) organizing features into 10 categories (permissions, API calls, intents, …), (2) pruning rare and high-uncertainty categories (URLs, activities), shrinking space toward ~49K, and (3) training a linear SVM for fast sparse classification (~94% TPR reported in the family). Your thesis FexDroid-lite caps each category at ~500 top terms → 3K–5K frozen dimensions + ASCNN or MLP for ONNX. Extraction needs manifest + Dex static analysis — highest cost among single-pass suggestions except full Drebin.

Component A — Static multi-source extraction (Drebin-style)

What it analyzes

Manifest declarations (permissions, components, intent filters) plus Dex/static strings: API invocations, method call patterns, URLs, provider names, etc.

Why this input was chosen

Drebin proved that joint static features discriminate malware well; FexDroid keeps that expressiveness but structures it for explainability and pruning.

Step-by-Step Process

  1. Unzip APK; parse AndroidManifest.xml for permissions, activities, services, receivers, providers, intent filters.
  2. Disassemble or statically analyze all classes*.dex files (Androguard / equivalent).
  3. Collect API call signatures, call-graph edges, embedded URL/host strings, hardware uses-feature entries.
  4. Normalize strings (e.g. permission names to real_permission form).
  5. For each extracted term, record which category it belongs to (next component).

Mathematical Formulation

Per-term indicator: \[ f_j = \mathbb{1}[\text{term}_j \in \text{APK}] \]

Before pruning, dimension index \(j\) runs over full Drebin vocabulary \(|\mathcal{V}| \approx 545{,}333\).

  • \(f_j\) — binary feature for term \(j\)
  • \(\mathbb{1}[\cdot]\) — indicator: 1 if term present, else 0
  • \(|\mathcal{V}|\) — full joint vocabulary size before reduction

Output and how it connects to the next stage

Outputs unstructured multiset of labeled static terms. Fed into category bucketing (Component B).

Key Advantage / Novelty

Key novelty: Same information source as Drebin but pipeline designed for explainable category-wise analysis, not a flat hash of strings.

Component B — Ten-category bucketing

What it analyzes

All extracted terms partitioned into fixed semantic categories (see table in paper).

Why this input was chosen

Pruning and explanation work per category — e.g. drop url entirely because domains change daily; keep api_call because malware API sequences are stable.

Step-by-Step Process

  1. Assign each term to exactly one category label \(c \in \mathcal{C}\), \(|\mathcal{C}| = 10\).
  2. Build per-category vocabularies \(\mathcal{V}_c\).
  3. Concatenate category blocks (order fixed at training) into global index set.
  4. Maintain category metadata for explainability (which APIs fired, etc.).

Mathematical Formulation

Categories \(\mathcal{C}\): \(\{\text{real\_permission}, \text{feature}, \text{api\_call}, \text{call}, \text{permission}, \text{provider}, \text{intent}, \text{service\_receiver}, \text{activity}, \text{url}\}\).

\[ \mathbf{f} = [\mathbf{f}_{c_1} \| \mathbf{f}_{c_2} \| \cdots \| \mathbf{f}_{c_{10}}] \]

  • \(\mathcal{C}\) — set of 10 category names
  • \(\mathcal{V}_c\) — vocabulary for category \(c\)
  • \(\mathbf{f}_c\) — binary sub-vector for category \(c\)

Output and how it connects to the next stage

Outputs structured sparse vector with category boundaries. Feeds pruning (Component C).

Key Advantage / Novelty

Why this is different from flat Drebin: Enables whole-category removal (URLs, activities) based on uncertainty analysis — not just global frequency cuts.

Component C — Category & frequency pruning (FexDroid / ProDroid)

What it analyzes

Full 545K-dimensional space and per-category statistics: term frequency, class-conditional probability, uncertainty.

Why this input was chosen

Rare terms (≤5 occurrences) add noise and memory; URL/activity categories have high entropy — dropping them shrinks ~545K → ~40K–49K with small accuracy loss (paper).

Step-by-Step Process

  1. ProDroid step: Remove features appearing ≤5 times in training corpus.
  2. Remove features with high uncertainty (weak class separation).
  3. FexDroid step: Drop entire categories url and activity (noisy, unstable).
  4. Rebuild vocabulary \(\mathcal{V}'\) with \(|\mathcal{V}'| \approx 49{,}000\) (paper reduction path).
  5. Re-index APK features into pruned space.

Mathematical Formulation

Pruned dimension: \[ D_{\text{Fex}} \ll 545{,}333, \quad D_{\text{Fex}} \approx 4 \times 10^4 \]

Retention rule (conceptual): keep term \(j\) if \(\mathrm{freq}(j) > \tau_f\) and \(\mathrm{uncertainty}(j) < \tau_u\), with category-level overrides.

  • \(\tau_f\) — minimum frequency threshold (e.g. 5)
  • \(D_{\text{Fex}}\) — dimension after FexDroid pruning
  • url / activity — categories removed wholesale

Architecture Flowchart

f_full  (545K+ sparse)

    ├─► drop high-uncertainty terms
    └─► drop url + activity categories
            │
            ▼
    f_pruned  (~49K sparse)

Output and how it connects to the next stage

Outputs \(\mathbf{f}' \in \{0,1\}^{D_{\text{Fex}}}\). For mobile thesis path, passes to lite cap (Component D) before classifier.

Key Advantage / Novelty

Key advantage: ~10× dimension reduction with explainable rules; ~94% TPR reported in ProDroid/FexDroid line on Drebin-style evaluation.

Component D — FexDroid-lite vocabulary cap (thesis deployment)

What it analyzes

Pruned feature space per category after Component C.

Why this input was chosen

49K is still large for on-device ONNX; capping top 500 terms per category yields **3K–5K** dims — fits ASCNN/MLP and multistep cascade stage 3+.

Step-by-Step Process

  1. For each category \(c\), rank terms by training frequency (or mutual information).
  2. Keep top \(K_c \approx 500\) terms; map OOV to drop or rare bucket.
  3. Freeze lexicon for inference.
  4. Build \(\mathbf{f}_{\text{lite}} \in \{0,1\}^{D}\), \(D \approx 3000\)–5000.

Mathematical Formulation

\[ D_{\text{lite}} = \sum_{c \in \mathcal{C}'} |\mathcal{V}_c^{\text{top-}K}|, \quad \mathcal{C}' = \mathcal{C} \setminus \{\text{url}, \text{activity}\} \]

  • \(K_c\) — max terms kept per category (~500)
  • \(D_{\text{lite}}\) — final deployable dimension (~3K–5K)
  • \(\mathcal{C}'\) — categories retained after FexDroid drops

Architecture Flowchart

    │
    ▼

    │
    ▼
 f_lite  (1×3000–5000)  frozen vocab

Output and how it connects to the next stage

Outputs \(\mathbf{f}_{\text{lite}}\) to classifier (Component E). Used when cheaper models (header, MLDP) are uncertain in cascade.

Key Advantage / Novelty

Thesis novelty: Same semantic categories as paper, but vocabulary sized for mobile inference — not paper's full 49K LibLinear run.

Component E — Linear SVM classifier (paper) / ASCNN or MLP (thesis)

What it analyzes

Sparse binary vector \(\mathbf{f}\) or \(\mathbf{f}_{\text{lite}}\).

Why this input was chosen

Linear SVM scales to very high sparse dimension with hinge loss; thesis may swap ASCNN from MSFDroid for denoising high-D sparse input before sigmoid.

Step-by-Step Process

  1. Train LibLinear SVM on \((\mathbf{f}_i, y_i)\) with labels \(y_i \in \{-1,+1\}\) or \(\{0,1\}\).
  2. Hyperparameter \(C\) controls margin vs misclassification (grid search in paper).
  3. Decision: \(\mathrm{sign}(\mathbf{w}^T \mathbf{f} + b)\) or probability via Platt scaling.
  4. Thesis alternative: \(\hat{y} = \sigma(\mathrm{MLP}(\mathbf{f}_{\text{lite}}))\) or ASCNN embedding → MLP.

Mathematical Formulation

Linear SVM (paper): \[ \min_{\mathbf{w},b} \frac{1}{2}\|\mathbf{w}\|^2 + C \sum_i \max(0, 1 - y_i(\mathbf{w}^T \mathbf{f}_i + b)) \]

MLP (thesis ONNX): \[ \hat{y} = \sigma(\mathbf{W}_2\,\mathrm{ReLU}(\mathbf{W}_1 \mathbf{f}_{\text{lite}} + \mathbf{b}_1) + \mathbf{b}_2) \]

  • \(\mathbf{w}, b\) — SVM hyperplane weights and bias
  • \(C\) — regularization constant
  • \(\hat{y}\) — malware probability or score

Architecture Flowchart

f_lite  (1×D)
    │
    ├─► Paper: Linear SVM  →  sign(w^T f + b)
    └─► Thesis: ASCNN/MLP  →  σ(·)  →  P(malware)

Output and how it connects to the next stage

Outputs malware score in \([0,1]\). Feeds ensemble or multistep policy as high-cost high-F1 stage.

Key Advantage / Novelty

Key advantage: Paper SVM is proven on sparse Drebin family; thesis MLP/ASCNN unifies export format with MSFDroid stack.
