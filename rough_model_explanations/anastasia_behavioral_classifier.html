ANASTASIA Behavioral Feature Classifier (ANASTASIA-lite)

Paper: Fereidooni et al., NTMS 2016 — ANASTASIA: Android mAlware detection using STAtic analySIs of Applications · Thesis variant: top-128 + MLP-lite

Prerequisites (beginner)

Static vs dynamic analysis: Static inspection reads APK files without running them (safe, fast, on-device friendly). Dynamic analysis runs the app in a sandbox (accurate but slow, heavy battery).

Dalvik / Dex: App code lives in classes.dex. Static tools scan Dex strings and API references to see what the code actually calls, not only what the manifest declares.

Declared vs used permissions: Manifest says what the app may request; Dex analysis finds what code references — malware can hide behavior in bytecode.

uniPDroid: Tool used in the paper to extract ~560 binary behavioral features from manifest + Dex.

Feature selection (Extra Trees): Train an ensemble of randomized trees, rank feature importances, keep top \(K\) (e.g. 128) for a smaller mobile model.

XGBoost / MLP: Paper’s best accuracy uses gradient-boosted trees (~97.3% TPR reported); thesis ANASTASIA-lite uses a 2-layer MLP for ONNX size limits.

1. Overview

Given 50,000 APKs to classify, permission-only manifest models miss fraud that lives in bytecode — sending SMS via API without declaring it, running su, or loading dex dynamically. ANASTASIA (Fereidooni et al., NTMS 2016) extracts a fixed 560-dimensional binary behavioral profile from manifest and Dex using uniPDroid (intents, used permissions, shell commands, suspicious APIs, activity flags), then trains XGBoost (paper best: ~97.3% true positive rate, ~2.7% false negative on ~30k apps). For mobile deployment, ANASTASIA-lite applies offline Extra Trees selection to keep the top 128 dimensions and replaces XGBoost with a small MLP (128 → 128 → 1) exported to ONNX — same semantic categories, smaller model.

2. Component — uniPDroid 560-d behavioral extraction

What it analyzes

Manifest + all classes*.dex files: intents, used permissions, system commands, suspicious API calls, malicious-activity boolean flags.

Why this input was chosen

Bytecode captures actual operations; manifest alone under-reports abuse. The paper defines ~560 hand-crafted templates matched by static scanning (no app execution).

Step-by-Step Process

  1. Unzip APK; load AndroidManifest.xml and every classes*.dex.
  2. Disassemble or string-scan Dex (Androguard-style pipeline in paper; lightweight pattern matcher for thesis).
  3. Category 1 — Intents: intent actions/filters in manifest and code → set bits for known IPC/event triggers.
  4. Category 2 — Used permissions: permissions referenced in Dex (may differ from declared list).
  5. Category 3 — System commands: strings like chmod, su, sh, ps in bytecode.
  6. Category 4 — Suspicious APIs: e.g. sendTextMessage, Runtime.exec, getDeviceId.
  7. Category 5 — Activity flags: booleans for IMEI read, dynamic code load, reflection, network socket, etc.
  8. For each of 560 predefined behaviors \(i\), set \(f_i = 1\) if detected, else \(0\).

Mathematical Formulation

\[ \mathbf{f} \in \{0,1\}^{560}, \quad f_i = \mathbb{1}[\text{behavior}_i \text{ detected in APK}] \]

Category partition (conceptual):

\[ \mathbf{f} = [\mathbf{f}^{(\text{intents})} \| \mathbf{f}^{(\text{usedPerm})} \| \mathbf{f}^{(\text{syscmd})} \| \mathbf{f}^{(\text{api})} \| \mathbf{f}^{(\text{flags})}] \]

  • \(\mathbf{f}\) — full 560-d behavioral vector
  • \(f_i\) — indicator for behavior template \(i\)
  • \(\mathbb{1}[\cdot]\) — 1 if condition true, else 0

Output and how it connects to the next stage

Outputs full \(\mathbf{f}\). Fed to offline feature selection; at inference only top-\(K\) indices are retained.

Key Advantage / Novelty

Key novelty: Behavioral static features beyond Drebin-style permissions — captures command execution and API abuse paths.

3. Component — Offline top-K feature selection (Extra Trees)

What it analyzes

Importance scores of all 560 dimensions on labeled training APKs.

Why this input was chosen

560 dims is sparse and redundant for mobile; Extra Trees (paper uses impurity-based importance) picks the most discriminative 128 features while preserving category coverage.

Step-by-Step Process

  1. Train Extra Trees classifier on \(\mathbf{f}\) with malware/benign labels (paper also tried SVM, RF, XGBoost on full 560-d).
  2. Compute mean decrease in impurity (or permutation importance) per dimension \(i\).
  3. Rank features by importance \(s_i\) descending.
  4. Select index set \(\mathcal{K}\) of top \(K=128\) features (thesis default; paper used full 560 for XGBoost).
  5. Freeze mask matrix \(\mathbf{M} \in \{0,1\}^{K \times 560}\) mapping \(\mathbf{f} \mapsto \mathbf{x}\).

Mathematical Formulation

\[ \mathbf{x} = \mathbf{M} \mathbf{f}, \quad \mathbf{M} \in \{0,1\}^{K \times 560}, \quad \|\mathbf{M}\|_0 = K \]

Equivalent indexing:

\[ x_k = f_{\mathcal{K}_k}, \quad k = 1,\ldots,K \]

  • \(s_i\) — importance score for feature \(i\)
  • \(\mathcal{K}\) — set of selected indices (\(|\mathcal{K}|=128\))
  • \(\mathbf{x}\) — reduced vector for deployment (\(1 \times 128\))

Output and how it connects to the next stage

Outputs \(\mathbf{x} \in \{0,1\}^{128}\) (or \(\mathbb{R}^{128}\) after optional scaling). Input to MLP-lite.

Key Advantage / Novelty

Key novelty (thesis): Same 560-d philosophy as paper; ~4× smaller input than full vector with most impurity retained in top 128 dims.

4. Component — ANASTASIA-lite MLP classifier

What it analyzes

Reduced behavioral vector \(\mathbf{x} \in \mathbb{R}^{128}\) (binary 0/1 or float).

Why this input was chosen

Paper’s 6-layer DNN [3200…100] and XGBoost are too heavy for on-device; a 2-hidden-block MLP matches MSFDroid-style deployment while preserving nonlinear decision boundaries.

Step-by-Step Process

  1. Layer 1: \(\mathbf{h}_1 = \text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1)\), \(\mathbf{W}_1 \in \mathbb{R}^{128 \times 128}\).
  2. Layer 2 (optional same width in paper DNN; lite uses one wide hidden): \(\mathbf{h}_2 = \text{ReLU}(\mathbf{W}_2 \mathbf{h}_1 + \mathbf{b}_2)\).
  3. Output: \(\hat{y} = \sigma(\mathbf{w}_3^T \mathbf{h}_2 + b_3)\) — scalar malware probability.
  4. Train with Adam + binary cross-entropy; early stopping on validation F1.
  5. Export ONNX (~50–150 KB depending on width).

Mathematical Formulation

\[ \mathbf{h}_1 = \text{ReLU}(\mathbf{W}_1 \mathbf{x} + \mathbf{b}_1), \quad \hat{y} = \sigma(\mathbf{w}_2^T \mathbf{h}_1 + b_2) \]

Two-layer lite stack (thesis): 128 → 128 → 1.

Compare to paper XGBoost: \\(\\hat{y} = \\sigma\\left(\\sum_{t=1}^{T} \\eta \\, f_t(\\mathbf{x})\\right)\\) with \\(f_t\\) regression trees — higher accuracy, larger model.

  • \(\mathbf{x}\) — 128-d selected behavioral input
  • \(\hat{y}\) — malware probability
  • \(f_t\) — XGBoost weak learners (paper only)

5. Ensemble or fusion mechanism

Base ANASTASIA is a single pipeline (extract → classify). The 560 features are already a concatenation of five semantic categories inside uniPDroid — not separate classifiers fused late:

\[ \mathbf{f} = [\mathbf{f}^{(1)} \| \cdots \| \mathbf{f}^{(5)}], \quad \mathbf{x} = \mathbf{M}\mathbf{f}, \quad \hat{y} = ext{MLP}(\mathbf{x}) \]

Five category blocks inside uniPDroid
  │
  ▼
f (1×560)
  │
  ▼
Top-128 mask M
  │
  ▼
x (1×128) ──► MLP-lite ──► ŷ

Paper ensemble comparison: XGBoost vs RF vs SVM trained on the same \(\mathbf{f}\) — XGBoost wins; no multi-model vote at inference in the deployed lite variant.

Why XGBoost / behavioral features work: Dex captures executed capabilities (API calls, shell commands) that manifest omits. Boosted trees exploit sparse 560-d interactions (e.g. “uses SMS API” ∧ “reads IMEI” ∧ “no launcher activity”). Why lite may trade a little F1 for size: Top-128 selection drops tail features; MLP approximates tree boundaries with far fewer parameters than hundreds of XGBoost trees.
