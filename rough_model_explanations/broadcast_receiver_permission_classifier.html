Broadcast Receiver + Permission Classifier

Paper: Mohsen et al., CIC 2017 — Detecting Android Malwares By Mining Statically Registered Broadcast Receivers

Prerequisites (beginner)

APK: A ZIP archive containing AndroidManifest.xml (what the app declares) and classes.dex (compiled code). You can scan APKs without running them — that is static analysis.

Permissions (<uses-permission>): capabilities such as SEND_SMS or READ_CONTACTS. Each declared permission is visible in the manifest.

Broadcast receiver: An Android component that runs code when a system event fires — e.g. BOOT_COMPLETED (phone finished booting), SMS_RECEIVED (new text). Malware often registers receivers so it wakes in the background.

Feature vector: A fixed-length list of 0/1 values — one bit per permission or intent action in a vocabulary learned from your training set.

Binary classification: The model outputs a malware probability; if it exceeds a threshold (usually 0.5), the APK is labeled malware.

1. Overview

Imagine you must screen 50,000 APK files before they reach users’ phones. Most detectors use only manifest permissions, but benign games and banking apps often request INTERNET and READ_PHONE_STATE just like trojans — so permission-only models plateau. Mohsen et al. (CIC 2017) add a second manifest signal: which broadcast receivers and intent actions each app registers statically. Malware disproportionately listens for boot, SMS, and connectivity events to persist and intercept data. The architecture has three blocks: (1) a permission binary vector, (2) a receiver-action binary vector, (3) early fusion via concatenation plus an SVM with RBF kernel in the paper (logistic regression or tiny MLP for ONNX deployment). Everything is manifest-only — no Dex decompilation.

2. Component A — Permission feature vector

What it analyzes

Every android:name in <uses-permission> tags inside AndroidManifest.xml.

Why this input was chosen

Permissions are Android’s primary static security declaration: malware that sends premium SMS, steals contacts, or records audio must often declare dangerous permissions visible to users and stores.

Step-by-Step Process

  1. Unzip the APK (it is a ZIP archive); locate AndroidManifest.xml (binary XML on disk — decode with AAPT2, Apktool, or an AxmlReader).
  2. Enumerate all <uses-permission android:name="…"> strings for this APK.
  3. From the training corpus only, build vocabulary \(\mathcal{P} = \{\text{perm}_1,\ldots,\text{perm}_P\}\) (typically \(P \approx 150\)–300 over ~50k APKs).
  4. For each APK \(i\), set \(p_{i,j}=1\) if \(\text{perm}_j\) appears in its manifest, else \(0\).
  5. Freeze \(\mathcal{P}\) at inference; permissions not in the vocabulary are ignored or optionally bucketed as “other.”

Mathematical Formulation

\[ p_{i,j} = \begin{cases} 1 & \text{if } \text{perm}_j \in \text{Manifest}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{p}_i \in \{0,1\}^{P} \]

  • \(P\) — permission vocabulary size (number of dimensions)
  • \(p_{i,j}\) — bit for permission \(j\) on APK \(i\)
  • \(\mathbf{p}_i\) — permission feature row for one APK

Architecture Flowchart

Raw APK
  │
  └─► AndroidManifest.xml
         │
         └─► <uses-permission> tags
                │
                ▼
         Permission vector  (1×P)
         e.g. 1×200  binary

Output and how it connects to the next stage

Outputs \(\mathbf{p} \in \{0,1\}^{P}\). This vector is the first half of the fused input \(\mathbf{x}\) before the classifier.

Key Advantage / Novelty

Key novelty: Standard baseline domain; the paper includes it so receiver features can be proven to add value beyond permissions alone.

3. Component B — Broadcast receiver intent-action vector

What it analyzes

Intent android:name strings under <receiver><intent-filter><action> — statically registered broadcast receivers only.

Why this input was chosen

Receivers define when code runs without the user opening the app. Malware uses BOOT_COMPLETED to survive reboots and SMS_RECEIVED to intercept texts. The paper’s manual study (400 APKs) and large-scale experiments show malware registers more receivers and more sensitive actions than benign apps.

Step-by-Step Process

  1. Parse the same AndroidManifest.xml as Component A.
  2. Find every <receiver> element (exported or not; static registration only).
  3. For each receiver, collect all <action android:name="…"> inside nested <intent-filter> blocks.
  4. Build training vocabulary \(\mathcal{A}\) of distinct action strings from the corpus (\(R \approx 50\)–100).
  5. Set \(r_{i,k}=1\) if action \(k\) appears in any receiver filter for APK \(i\), else \(0\).
  6. Freeze \(\mathcal{A}\) for inference.

Mathematical Formulation

\[ r_{i,k} = \begin{cases} 1 & \text{if } \text{action}_k \in \text{Receivers}(i) \\ 0 & \text{otherwise} \end{cases}, \quad \mathbf{r}_i \in \{0,1\}^{R} \]

  • \(R\) — receiver-action vocabulary size
  • \(r_{i,k}\) — bit for intent action \(k\)
  • \(\mathbf{r}_i\) — receiver feature vector for APK \(i\)

Architecture Flowchart

AndroidManifest.xml
  │
  └─► <receiver> → <intent-filter> → <action>
         │
         ▼
   Receiver-action vector  (1×R)
   e.g. 1×80  binary

Output and how it connects to the next stage

Outputs \(\mathbf{r} \in \{0,1\}^{R}\). Concatenated with \(\mathbf{p}\) to form the classifier input \(\mathbf{x}\).

Key Advantage / Novelty

Why this is different from standard permission-only detectors: Drebin-style work rarely treats receiver actions as a dedicated feature block; Mohsen et al. show they improve accuracy when combined with permissions.

4. Component C — Fusion and classifier

What it analyzes

The concatenated vector \(\mathbf{x} = [\mathbf{p} \| \mathbf{r}]\). Paper: C-SVM with RBF kernel; thesis/ONNX: logistic regression or a 1-hidden-layer MLP.

Why this input was chosen

After concatenation, the joint space is still sparse and moderate-dimensional; a linear boundary often works, but SVM with RBF handles mild nonlinear interactions (e.g. rare permission + boot receiver together).

Step-by-Step Process

  1. Concatenate: \(\mathbf{x} \leftarrow [\mathbf{p}; \mathbf{r}]\) → dimension \(P+R\) (e.g. \(1 \times 280\)).
  2. Train on labeled APKs (malware = 1, benign = 0) with stratified cross-validation.
  3. Paper: grid-search SVM hyperparameters \(C\) (margin penalty) and \(\gamma\) (RBF width).
  4. ONNX path: train \(\mathbf{w}, b\) for logistic regression or small MLP; export to mobile runtime.
  5. At inference: build \(\mathbf{x}\) for a new APK → score → compare to threshold \(\tau\) (often 0.5).

Mathematical Formulation

SVM decision (paper):

\[ f(\mathbf{x}) = \mathrm{sign}\left(\sum_{i \in SV} \alpha_i y_i K(\mathbf{x}_i, \mathbf{x}) + b\right) \]

RBF kernel: \[ K(\mathbf{x}, \mathbf{x}') = \exp\left(-\gamma \|\mathbf{x} - \mathbf{x}'\|_2^2\right) \]

Logistic regression (ONNX-friendly):

\[ \hat{y} = \sigma(\mathbf{w}^T \mathbf{x} + b) = \frac{1}{1 + e^{-(\mathbf{w}^T \mathbf{x} + b)}} \]

  • \(SV\) — support vectors (training points that define the SVM boundary)
  • \(\alpha_i, y_i\) — dual coefficients and labels for support vectors
  • \(C\) — SVM regularization (trade-off margin vs misclassification)
  • \(\gamma\) — RBF kernel width
  • \(\mathbf{w}, b\) — logistic weights and bias
  • \(\hat{y}\) — estimated malware probability

Architecture Flowchart

Permission p (1×P) ──┐
                        ├──► Concat  x (1×(P+R))  ──► Classifier  ──► P(malware)
Receiver r (1×R) ─────┘
              e.g. (1×200)+(1×80) = (1×280)

Output and how it connects to the next stage

Final output: malware probability or hard label. In a multistep VigiDroid stack, this score is one domain among others (Dex header, tail bytes, etc.).

Key Advantage / Novelty

Key advantage: Manifest-only parsing; typical extraction < 100 ms; model < 50 KB. Complements structural (Dex header) and raw-byte models without overlapping their feature domains.

5. Ensemble or fusion mechanism

This model uses early fusion (feature-level concatenation before a single classifier), not late fusion or score voting:

\[ \mathbf{x} = [\mathbf{p} \| \mathbf{r}], \quad \hat{y} = f(\mathbf{x}) \]

  • \(\|\) — vector concatenation (append \(\mathbf{r}\) after \(\mathbf{p}\))
  • \(f\) — SVM or logistic/MLP; one joint decision boundary in \((P+R)\)-dimensional space
  • There is no separate score per branch averaged at the end — both domains are learned jointly.
p (1×P) ──┐
          ├──► x (1×(P+R))  e.g. 1×280 ──► f(·) ──► ŷ ∈ [0,1]
r (1×R) ──┘

6. Experimental results

Feature configurationAccuracy / role (paper)Notes
Permissions only~76% (reported SVM baseline on one split)Useful but insufficient alone
Receivers onlyWeaker than permissions aloneStill adds complementary signal
Permissions + receiversBest — combined feature setManual study on 400 APKs; large-scale ML on 5,723+5,723 APKs

Why improvement happened: Permissions capture capability (what the app may do). Receivers capture event-driven behavior (when background code runs). A benign game may declare INTERNET but rarely pairs it with BOOT_COMPLETED and SMS_RECEIVED — a pattern common in banking trojans and SMS fraud malware.
