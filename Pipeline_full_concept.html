New Model Pipeline — Implementation Guide

How to take a malware-detection model from a paper and implement it end-to-end: static features from APKs, PyTorch training on a PC, ONNX export, and on-device inference in an Android app (VigiDroid-style). This document is for new models only — design your phases around it on your own machine and workspace.

For AI planners

You have a rough plan for a paper’s model. Output implementation phases that follow this pipeline. Each phase should list deliverables, scripts, and exit criteria. In the thesis_vigidroid monorepo, reuse Shared_pipeline_Files/ for corpus indexing, metrics schemas, and batch tools — but keep paper-specific features and training inside <ModelFolder>/ (see Shared_pipeline_Files).

Assign up front:

  • model_id — snake_case id for artifacts and Android assets (e.g. paper_xyz_detector)
  • domain — short name for the feature type (e.g. api_ngrams, dex_header_manifest)
  • Whether the model is on-device feasible or offline-only (too slow/heavy for phone)

Pipeline flow

Two codebases cooperate. Training and evaluation happen on a PC; scanning happens on Android. Features at inference time must match training semantics.

┌──────────────────────── OFFLINE (Python) ─────────────────────────┐ │ APK corpus (by year folders) │ │ → feature extraction → train → evaluate (test years) │ │ → export .onnx + preprocessing assets + parity_samples │ └────────────────────────────────────────────────────────────────────┘ │ ▼ ┌──────────────────────── ON-DEVICE (Java / Android) ────────────────┐ │ Trigger (manual / download / schedule) │ │ → extract features (must match Python) → ONNX Runtime │ │ → score + latency/memory logs (JSON per scan) │ └────────────────────────────────────────────────────────────────────┘ │ ▼ Evaluation & thesis plots (accuracy from offline test · latency/CPU/mem from device)
SideResponsibility
PythonFeature engineering at scale, training, test-set metrics (ACC, F1, AUC), ONNX export, parity samples
AndroidParse APK on phone, build feature tensors, ONNX inference, structured scan metrics
Train/serve parity: If Java features differ from Python, reported accuracy is meaningless. P8 and A4 exist to catch this before deployment.

Dataset handling & splits

Corpus layout

APKs live on disk outside git. Organize by year and label (benign / malware). Example:

apk_root/
├── 2020/
│   ├── benign/
│   └── malware/
├── 2021/
│   ├── benign/
│   └── malware/
├── 2022/
│   └── ...
└── 2023/
    └── ...

Train / test policy (required)

When indexing, preprocessing, training, and evaluating a model, use this split:
  • Train: all APKs under 2020/ and 2021/
  • Test: all APKs under 2022/ and 2023/

Implement this in dataset code explicitly — e.g. walk apk_root, assign split from parent year folder, or build manifest CSV with a split column derived from year. Preprocess and train only on train; report final metrics on test (temporal generalization: older years → newer years).

Validation: hold out a fraction of train (e.g. 10% of 2020+2021) for early stopping and threshold tuning if needed. Do not use 2022/2023 for validation or hyperparameter search.

Indexing checklist (P1)

  • SHA-256 per APK; skip corrupt zips (shared build_apk_manifest.py or model indexer)
  • Record: path, label, year, sha256, optional apk_size_bytes, num_dex_files
  • Apply train = {2020, 2021}, test = {2022, 2023} (temporal_year) or shared train.txt/test.txt
  • Deduplicate identical hashes before training
  • Never copy the full corpus into the model repo — only manifests under Shared_pipeline_Files/data/manifests/ or model-local lists

Preprocess (P2)

Read APKs in place from apk_root. Write sharded features under artifacts/processed/. Log failures to failed_apks.log. Training loops load tensors only — no APK I/O during epochs.

Shared_pipeline_Files (thesis monorepo)

Yes — this folder holds what is reused across models. It is the cross-model layer described in PIPELINE_IMPLEMENTATION_PLAN.md §7–§9: one APK corpus pointer, optional shared manifest/splits, standardized metrics JSON, and batch export/parity/plotting tools. It does not contain paper-specific feature extractors or PyTorch architectures; those stay in each <ModelFolder>/src/.

Setup before a new model (once per machine)

  1. Edit Shared_pipeline_Files/data/dataset_paths.yaml: set apk_root and project_root to your paths (APKs stay outside git).
  2. From repo root, build the corpus index (P1 helper):
    python Shared_pipeline_Files/tools/build_apk_manifest.py --config Shared_pipeline_Files/data/dataset_paths.yaml
    → data/manifests/apk_index.csv (columns: apk_path, sha256, label, year, split).
  3. Choose a split policy (see below). Either implement splits inside <ModelFolder> (recommended for temporal eval) or generate shared split lists with split_dataset.py.

Split policies (pick one and document it)

Temporal (thesis default for D3–D5): train on years 2020+2021, final test on 2022+2023. Implement in <ModelFolder> via split_mode: temporal_year and train_years / val_years in config/default.yaml. Validation = holdout from train years only — never tune on test years.

Shared stratified splits (optional): Shared_pipeline_Files/tools/split_dataset.py assigns train/val/test (~70/15/15) stratified by label on the full manifest. Use when you need identical APK lists across models for ablation tables. Point the model at shared files with pipeline.use_shared_splits: true and paths under data/splits/train.txt, val.txt, test.txt (Pattern A/B support this via pipeline_integration.py).

Do not mix policies silently: temporal-year test metrics are not comparable to stratified-random test metrics. State which policy each model_id uses in thesis text and in exported JSON (train_years / split fields).

Wiring a new model folder

Assign domain id per PIPELINE_IMPLEMENTATION_PLAN.md §2 (e.g. D3 mlp_dex_header, D4 pattern_a_combined). In <ModelFolder>/config/default.yaml:

paths:
  apk_root: /path/to/apk_corpus    # should match dataset_paths.yaml

pipeline:
  enabled: true
  model_id: <snake_case>           # matches artifacts/export and Android assets
  domain: <short_feature_name>
  export_offline_json: true         # write P6 JSON to Shared_pipeline_Files/results/offline/
  use_shared_splits: false          # true only if using shared train.txt / val.txt
  shared_splits_dir: Shared_pipeline_Files/data/splits
  shared_manifest_csv: Shared_pipeline_Files/data/manifests/apk_index.csv

After P6 evaluation, call shared export from training code (copy Pattern A/B src/pipeline_integration.py or invoke tools/offline_metrics_export.py). Local copies under <ModelFolder>/artifacts/metrics/ remain the model’s source of truth; shared results/offline/ aggregates runs for plotting.

Metrics and schemas (plan §7)

  • Offline eval JSON → Shared_pipeline_Files/results/offline/<model_id>_<split>_*.json (schema: schemas/offline_eval.schema.json)
  • On-device scan JSON → app writes per schema schemas/device_scan.schema.json; pull with tools/pull_device_metrics.sh → results/device/
  • Thesis figures → tools/plot_metrics.py → results/figures/

ONNX and parity (after P5–P7 in each model)

  1. Each model: <ModelFolder>/scripts/export_onnx.py → artifacts/export/<model_id>/ (manifest, thresholds, features/, parity_samples/).
  2. Batch driver (when checkpoints exist): bash Shared_pipeline_Files/tools/export_all_onnx.sh → copy bundles to vigidroid/app/src/main/assets/models/<model_id>/.
  3. Parity: model-local P8, then repo helper Shared_pipeline_Files/tools/parity_check.py (PyTorch vs ONNX ≤ 1e-4 on parity_samples/).
  4. Android A4: instrumented test against the same parity_samples/.

New-model checklist (shared + local)

  • model_id and domain assigned; documented in export manifest
  • dataset_paths.yaml apk_root matches model paths.apk_root
  • Manifest built; dedupe by sha256 before training
  • Split policy chosen (temporal_year vs shared stratified) and recorded
  • P0–P8 complete under <ModelFolder>/; P6 also exports to results/offline/ if pipeline.export_offline_json: true
  • Export bundle copied to VigiDroid assets; device metrics pulled to results/device/

Parity (P8 / A4)

Before treating on-device results as valid, verify every item below:

  • Same APK parts read (manifest, dex files, byte ranges) as in Python
  • Same normalization stats loaded from export features/
  • Same vocabulary / UNK rules for discrete features
  • If multidex: same aggregation (document in export_manifest.json)
  • ONNX input dtype and shape match manifest
  • Same post-processing (sigmoid vs softmax vs raw margin)
  • Scores on parity_samples/ within 1e-4 of Python reference

Android integration (A1–A4)

Target pattern: pluggable extractors + ONNX runner + scan orchestrator (exact class names may vary).

StepWork
A1Implement feature extractor from Python src/features/ and export features/ assets
A2Load model.onnx; build input tensors per export_manifest.json; apply correct score transform
A3Register model_id; on each APK scan append one stages[] entry (domain, timings, score)
A4Instrumented test: Java features + ONNX vs parity_samples/

Per-scan flow: baseline timing/memory → extract features → ONNX inference → append stage metrics → optional fusion if multiple models run in one app.

On-device — resource & latency

One JSON file per APK scan on the phone (path via app external storage). Used for thesis plots: parse_ms, vectorize_ms, inference_ms, score, mem/cpu deltas.

{
  "scan_id": "<uuid>",
  "apk": {"name": "app.apk", "size_bytes": 0},
  "trigger": "manual | download | scheduled",
  "stages": [{
    "domain": "<model_id or domain>",
    "parse_ms": 0, "vectorize_ms": 0, "inference_ms": 0,
    "score": 0.0, "mem_delta_bytes": 0
  }],
  "totals": {"wall_ms": 0, "cpu_ms": 0}
}

Pull JSON from device with Shared_pipeline_Files/tools/pull_device_metrics.sh (or adb) into Shared_pipeline_Files/results/device/ for plot_metrics.py.

Orchestration (optional, later)

Only after a single model works end-to-end:

  • Sequential: run all registered models on every APK; log each stage.
  • Multistep cascade: cheap model first; run expensive models only if score is in an uncertain band (t_low, t_high from validation on train holdout).
  • Ensemble: weighted average of calibrated scores in [0,1]; weights from validation, shipped as JSON in assets.

If the paper’s model is too heavy for on-device SLOs, stop after P6/P8 and document as offline-only baseline.
